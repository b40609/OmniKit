調研日期：2026-11-19  
調研員：Antigravity Agent（遵循 omnikit-research 飽和調研規範）  
目標對象：OmniKit GitHub Pages 看板（改版前架構與競品借鏡）  
調研狀態：長尾未飽和（★1,000 以上候選連續 3 組無新名字，符合停止條件）

## 1. 調研背景與看板現況診斷

OmniKit 目前的 GitHub Pages 看板（由 `engine/scripts/build.py` 產出、`.github/workflows/pages.yml` 部署）是內部決策與工具名冊的呈現窗口。隨著工具與模型數量增加，當前看板暴露了嚴重的操作與架構痛點：

### 現況痛點分析
1. **首頁第一屏失焦（查閱成本過高）**：
   - 第一屏被 8 個統計方塊、新模型提醒、長篇決定紀錄佔滿。
   - 使用者（Ryan 與團隊）每天最核心的動作是查詢「**現在做任務 X，該選什麼模型、搭配什麼工具**」，卻需要向下滾動數屏才能看到。
2. **雜訊干擾嚴重（124/139 項為待評估）**：
   - 全站 139 個工具項目中，高達 124 個處於「待評估」狀態，連同尚未填寫卡片的空白槽位，全部平鋪在同一個超長頁面上。
   - 真正已驗證且可立即採用的「預設」、「試用」工具被大量雜訊淹沒。
3. **內部術語壁壘（外部與新進者難懂）**：
   - 頁面充斥「槽位（Slot）」、「第 2 層（Layer 2）」、「主動找（Active Discovery）」等專案內部概念，同事試用或未來公開分享時不易直覺理解。
4. **評估結論隱形（只見連結不見結果）**：
   - 歷史決定紀錄僅呈現一長串 Markdown 檔案連結，第一眼看不到「採納理由」、「淘汰原因」或「核心優劣比較」。
5. **缺少 GitHub 與即時檢索入口**：
   - GitHub 原始碼入口縮在標題下方的一行小字；缺少即時模糊搜尋（Type-to-filter）與情境化標籤過濾。

## 2. 三大類競品詳細分析

本次飽和調研涵蓋三大面向：**技術雷達開源方案**、**AI 工具與生態目錄**、**模型比較與選型平台**。

### 類別一：技術雷達開源產生器 (Technology Radar)

#### 1. Thoughtworks Build Your Own Radar (BYOR)
- **網址**：`https://radar.thoughtworks.com/`（開源專案：`thoughtworks/build-your-own-radar`，★2,600，AGPL-3.0）
- **首頁第一屏回答了什麼**：
  - 核心互動雷達圖，展示當前組織在四個象限（Techniques, Tools, Platforms, Languages & Frameworks）中的技術採納成熟度分佈。頂部直接提供資料源切換（Google Sheets / CSV / JSON URL）與樣板示範。
- **資訊架構**：
  - 2D 空間化視覺（象限 Quadrant + 成熟度環 Ring：Adopt, Trial, Assess, Hold）。
  - 右側為條目清單與編號；點擊條目可在側欄彈出卡片，顯示該技術的背景、評估依據與版本歷程。
- **怎麼呈現結論或狀態**：
  - 透過條目所在的「同心圓環」定義狀態：Adopt（正式採用）、Trial（可在小型專案試用）、Assess（觀察探索）、Hold（暫緩或謹慎使用）。
- **怎麼處理大量「未評估」項目**：
  - **雷達本身完全不收錄未評估項目**。所有上榜項目至少進入「Assess（已展開評估）」；待評估的素材留在團隊內部 Backlog 或 Issue 庫中，徹底隔絕主畫面雜訊。
- **值得 OmniKit 抄的做法**：
  - 四層生命週期分級（Adopt / Trial / Assess / Hold）精準對應 OmniKit 的「預設 / 試用 / 待評估 / 淘汰或拒絕」。
  - 嚴格分離「已定案雷達視圖」與「待評估後備池」。
- **不適合抄的地方**：
  - 純 SVG 圓形雷達圖在項目超過 100 個時會極度擁擠、點位重疊；在手機或窄螢幕上難以閱讀，日常速查時不如表格或卡片直觀。

#### 2. Zalando Tech Radar
- **網址**：`https://opensource.zalando.com/tech-radar/`（開源專案：`zalando/tech-radar`，★1,954，MIT）
- **首頁第一屏回答了什麼**：
  - 「Zalando 內部對各項軟體技術的官方態度與支援標準」。
- **資訊架構**：
  - 左側 D3.js 渲染的同心圓雷達圖，右側緊湊條目列表。滑鼠懸停於清單時，雷達上的圓點即時放大對應；支援按象限切換篩選。
- **怎麼呈現結論或狀態**：
  - 採用數字編號標記雷達點，並用 Adopt / Trial / Assess / Hold 四個同心圓區隔。
- **怎麼處理大量「未評估」項目**：
  - 僅收錄經過工程架構委員會評估定案的技術，未評估項目不予呈現。
- **值得 OmniKit 抄的做法**：
  - 依賴單純的前端指令碼與輕量 SVG，無重型框架依賴，非常適合靜態 GitHub Pages 快速加載。
- **不適合抄的地方**：
  - 條目偏向靜態歸檔，缺乏「任務情境導向」（例如無法回答「寫爬蟲要用什麼」），使用者必須預先知道技術名稱才能查詢。

#### 3. AOE Technology Radar
- **網址**：`https://github.com/AOEpeople/aoe_technology_radar`（開源專案：`AOEpeople/aoe_technology_radar`，★419）
- **首頁第一屏回答了什麼**：
  - 整合首頁雷達全景與即時搜尋欄，顯示最新發布版本與近期技術變動。
- **資訊架構**：
  - 首頁雷達概覽 + 獨立的 Markdown 詳情頁面 + 歷史版本變更紀錄（Changelog）。
- **怎麼呈現結論或狀態**：
  - 每個技術條目帶有醒目的狀態徽章，並明確標記「New（本期新增）」或「Changed（評級變更）」。
- **怎麼處理大量「未評估」項目**：
  - 只呈現定案技術；每個項目的演進都有獨立的 Git Markdown 檔案支撐。
- **值得 OmniKit 抄的做法**：
  - 每個決定對應一份清晰的評估檔案與狀態變更紀錄，並具備即時搜尋與標籤過濾。
- **不適合抄的地方**：
  - 採用較重的 Next.js 靜態網站生成架構，對 OmniKit 目前簡單的 Python 腳本產生器來說稍微繁瑣。

### 類別二：AI 工具與生態目錄 (MCP / Skill Directories)

#### 4. Smithery.ai
- **網址**：`https://smithery.ai`
- **首頁第一屏回答了什麼**：
  - 「為 Claude Desktop、Cursor 等客戶端快速尋找並安裝經過驗證的 MCP 伺服器」。
  - 第一屏是極大化中央搜尋框 + 常用功能分類標籤（Web Scraping, Database, Developer Tools 等）。
- **資訊架構**：
  - 搜尋與過濾標籤 -> 網格卡片清單（Grid）-> 詳情頁（含參數設定表單）。
- **怎麼呈現結論或狀態**：
  - 卡片上清楚展示安裝次數、社群星數、「Verified」標記，並提供一鍵複製 CLI 安裝指令：
    `npx -y @smithery/cli install <name> --client claude`
- **怎麼處理大量「未評估」項目**：
  - 預設首頁只展示熱門（Trending）與官方精選，長尾或品質未驗證的項目沉底或需主動搜尋才出現。
- **值得 OmniKit 抄的做法**：
  - **「一鍵複製設定」**：卡片直接提供可直接粘貼到 `claude_desktop_config.json` 或終端機的指令。
  - **用途一句話**：每張卡片只保留核心一句話，降低認知負擔。
- **不適合抄的地方**：
  - 介面帶有商業平台與宣傳橫幅氣息，過多行銷圖示不符合純工具介面定位。

#### 5. Glama.ai MCP Directory
- **網址**：`https://glama.ai/mcp/servers`
- **首頁第一屏回答了什麼**：
  - 「哪些 MCP 伺服器健康可用、安全無毒、值得整合進 Agent」。
- **資訊架構**：
  - 頂部搜尋 + 左側屬性篩選器（傳輸協議 Stdio/SSE、程式語言、安全等級、存活狀態 Alive/Broken）+ 結果列表。
- **怎麼呈現結論或狀態**：
  - 自動化品質與安全評級徽章（綠色 Grade A、黃色 Grade B、紅色 Grade F）以及伺服器端點連通性監控。
- **怎麼處理大量「未評估」項目**：
  - 透過機器人定期自動掃描給予初步評分，未達標準或離線項目在預設排序中降權。
- **值得 OmniKit 抄的做法**：
  - 客觀的品質狀態徽章（綠/黃/紅），能迅速傳達工具的維護狀態與成熟度。
- **不適合抄的地方**：
  - 介面展示過多通訊層參數（如 raw schema、SSE endpoints），對日常工具選型而言過度技術化。

#### 6. mcp.so
- **網址**：`https://mcp.so`（開源專案：`chatmcp/mcpso`，★2,121，Apache-2.0）
- **首頁第一屏回答了什麼**：
  - 集合式的 MCP 開源導航，以簡潔分類呈現目前社群最受歡迎的工具清單。
- **資訊架構**：
  - 頂部類別導航（開發工具、效率辦公、資料查詢等）+ 單頁格狀卡片。
- **怎麼呈現結論或狀態**：
  - 標記支援的 Agent 客戶端（Cursor、Claude、Windsurf）與 GitHub 星數。
- **怎麼處理大量「未評估」項目**：
  - 採人工審核收錄制，未審核通過者不進入公開頁面。
- **值得 OmniKit 抄的做法**：
  - 高度緊湊的卡片佈局，清晰的分類錨點跳轉。
- **不適合抄的地方**：
  - 只有簡單的收錄列表，缺乏不同工具間的橫向對比與推薦決策依據。

#### 7. cursor.directory
- **網址**：`https://cursor.directory`
- **首頁第一屏回答了什麼**：
  - 「為你正在使用的技術棧（React、Next.js、FastAPI 等）直接複製最佳的 Cursor Rules」。
- **資訊架構**：
  - 搜尋框 + 滿版框架標籤列（Horizontal Scroll Chips）+ 熱門規則卡片流。點擊標籤即時無刷新過濾。
- **怎麼呈現結論或狀態**：
  - 依社群使用量與點讚數排序，最優質的規則置頂，卡片直接提供「Copy」按鈕。
- **怎麼處理大量「未評估」項目**：
  - 低讚與長尾規則排至末頁，第一屏完全保留給精選項目。
- **值得 OmniKit 抄的做法**：
  - **極致的「零廢話、找了就用」工具感**：點選語言或場景，立即得到可用的規則文本，沒有多餘的前言或說明文字。
- **不適合抄的地方**：
  - 無版本變更紀錄與決策歷程追蹤，不適用於需要維護長期決策理由的架構治理。

### 類別三：模型比較與選型平台 (Model Leaderboard & Selection)

#### 8. Artificial Analysis
- **網址**：`https://artificialanalysis.ai`
- **首頁第一屏回答了什麼**：
  - 「當前市場上各主流與開源模型在品質、速度、價格上的綜合排行與帕雷托最佳解（Pareto Frontier）」。
- **資訊架構**：
  - 首頁即為互動式散佈圖（Quality vs. Cost / Throughput）+ 下方詳細規格對比表格（支援自訂勾選比較欄位）。
- **怎麼呈現結論或狀態**：
  - 在散佈圖上清楚標記「帕雷托前沿（Pareto Frontier）」，處在前沿上的模型即為當前預算與延遲下的最優推薦。
- **怎麼處理大量「未評估」項目**：
  - 未經基準跑分的模型不列入主排行，歸入「Unrated / In Testing」獨立專區。
- **值得 OmniKit 抄的做法**：
  - **「第一屏直接給出最優選」**：不讓使用者自己比對幾百筆數據，直接給出各價位與性能區間的第一名推薦。
- **不適合抄的地方**：
  - 依賴較重的前端圖表運算，且側重即時 API 延遲監控，對 OmniKit 靜態看板而言稍微過重。

#### 9. Models.dev
- **網址**：`https://models.dev`
- **首頁第一屏回答了什麼**：
  - 「各模型支援的精確技術規格：上下文窗口、Tool Calling 支援、結構化輸出支援、快取讀寫定價」。
- **資訊架構**：
  - 高密度資料表（Dense Table View），支援按供應商（Anthropic, OpenAI, Google, DeepSeek...）快速切換，提供即時全文搜尋。
- **怎麼呈現結論或狀態**：
  - 透過緊湊的勾選圖示（Icon）與清晰數字，一目了然呈現各模型的能力邊界。
- **怎麼處理大量「未評估」項目**：
  - 僅收錄具備明確規格說明的模型；測試中模型標記「Preview / Experimental」。
- **值得 OmniKit 抄的做法**：
  - **高密度工程視圖（High Information Density）**：避免大字塊與空洞留白，在一屏內塞入最多有效決策資訊，非常受工程師歡迎。
- **不適合抄的地方**：
  - 偏向純客觀規格表，缺乏「在何種情境下優先使用該模型」的主觀任務指引。

#### 10. OpenRouter Models
- **網址**：`https://openrouter.ai/models`
- **首頁第一屏回答了什麼**：
  - 「當前實際被開發者調用最多的熱門模型排行與即時推理單價」。
- **資訊架構**：
  - 緊湊的列表視圖，左側為模型名稱與作者，右側清楚標出每百萬 Token 價格、上下文上限與每週跑量趨勢。
- **怎麼呈現結論或狀態**：
  - 排行榜名次 + 官方/精選徽章。
- **怎麼處理大量「未評估」項目**：
  - 透過調用量權重自然下沉冷門或無效模型。
- **值得 OmniKit 抄的做法**：
  - 清晰緊湊的清單佈局，搜尋響應極快。
- **不適合抄的地方**：
  - 與商業 API 充值及調用路由深度綁定。

## 4. 給 OmniKit 看板的改版資訊架構方案

依據「**先給 Ryan 自己每天查用、跑通後給同事試用、最後公開分享**」的定位，且「**介面走實用工具風（unslop），不做花俏行銷頁**」，我們提出三套不同側重點的架構方案：

---

### 方案 A（推薦）：任務導向決策矩陣（Task-First Matrix）

#### 核心設計理念
看板的第一目的不是「炫耀我們看了多少工具」，而是「**回答當下的選型問題**」。
首頁第一屏不放任何廢話統計，直接放「**工作任務場景速查（Task Selector）**」與「**決策推薦卡片（推薦模型 + 推薦工具 + 一句話理由 + 一鍵設定）**」。

#### 如何解決現況痛點
1. **處理 124 個待評估項目**：

## 5. 方案評選與推薦理由

### 推薦採用：方案 A（任務導向決策矩陣 Task-First Matrix）

### 推薦理由
1. **最高契合當前日常查用需求（Ryan 第一優先）**：
   - 使用者打開看板的最強烈動機不是欣賞圖表，而是「**現在要幹活了，我該用哪個工具和模型？**」。方案 A 第一屏開門見山回答這個問題，零翻頁、零多餘滾動。
2. **徹底消除 124 個項目的雜訊污染**：
   - 方案 A 將「已定案的日常工具（15 項）」與「長尾待評估庫（124 項）」物理隔開。首頁只呈現經過檢驗的精華，待評估項目放入次級頁籤，既保留後備庫又不干擾日常工作。
3. **利於後續給同事試用與公開分享**：
   - 同事或外部開發者不需要理解 OmniKit 的內部術語（槽位、第 2 層）。他們只需要找到自己關心的任務（例如「代碼重構」或「競品調研」），就能看到推薦的工具、模型與背後的論證。
4. **實現成本低且完全符合 unslop 純工具原則**：
   - 方案 A 不需要引入龐大的 D3.js 複雜雷達數學運算或肥大的圖表函式庫，純 HTML/CSS 與簡單的 JavaScript 篩選即可達到極致的流暢度與響應速度。
