## 先講清楚：三組都是 Codex 在審

讀過兩個挑戰者的原始碼（2026-11-19，掃描過的那個 commit）：

- codex-plugin-cc 的 `/codex:review` 指令檔寫「Run a Codex review through the shared built-in reviewer」，跟 Codex 內建 `/review` 是同一個審查器，只差從哪裡叫，所以不另外測。會不一樣的是 `/codex:adversarial-review`（可以給重點的對抗式審查），指令檔裡實際跑的是 `node scripts/codex-companion.mjs adversarial-review "$ARGUMENTS"`，再把輸出原樣交回。
- claudex-loop 的 `codex-review` 審的是「實作計畫」，不是程式碼。審程式碼的是主流程最後一步：runner 的 `inspect` 模式，把建置前的 commit 與計畫交給另一家，在新 session 審完整改動。

所以三組直接用指令跑，不經過 Claude 轉手（轉手只是把輸出原樣貼回，不影響審查內容）：

| 組 | 指令 | 說明 |
|---|---|---|
| 現任 | `codex review --commit <SHA>` | Codex 內建 `/review` 的非互動版本 |
| codex-plugin-cc | `node <plugin>/scripts/codex-companion.mjs adversarial-review --wait --base <父 commit>` | 不加重點文字，照預設 |
| claudex-loop | `python <skill>/scripts/runner.py inspect --host claude --builder claude --repo . --plan plan.md --base <父 commit>` | 計畫就是該 commit 的說明（改動的意圖） |

- 版本：codex-plugin-cc `db52e28`、claudex-loop `53cddc4`（都是 2026-11-19 第 0 層掃描的 commit）；Codex CLI 0.168.0。
- 模型：三組都照 `~/.codex/config.toml` 的預設（`gpt-5.6-terra`、推理 low），這是 Ryan 平常實際的設定，不另外覆蓋。claudex-loop 的 runner 會關掉 Codex 的 plugin、app 與 MCP，另外兩組沒關。
- 每組每題在一份拋棄式副本裡跑（從 GitHub clone 的 OmniKeep，detached 在題目的 commit）。`~/.codex` 的 sandbox 是 `danger-full-access`，跑完檢查副本有沒有被改；有改就記下來。

## 決策規則（實測前寫下）

1. **硬性條件**：在 Windows 非互動地跑得完；不改副本裡的檔案。不過的組那一題記失敗。
2. **主要依據：抓到標準答案的題數。** 評審判斷審查意見有沒有指出「後來修正的那個問題」：抓到（同一個缺陷，講得出原因或症狀）、部分（指到同一段程式但講的是別的原因）、沒抓到。T2 有兩個問題，各算半題。
3. **次要依據：雜訊。** 評審把其他意見分成「成立」「不成立」「不確定」，算不成立的比例。
4. **評審**：Claude（跟審查的 Codex 不同家），只看標準答案的修正 diff 與三份匿名的審查意見（隨機標成甲、乙、丙），不知道組別。兩個獨立評審各評一次、順序不同；兩個評審不一致的題目由主控讀原文判，並寫明。
5. **判定**：
   - 挑戰者比現任多抓 2 題以上，而且不成立的比例沒有高出 20 個百分點：建議試用（12-01 之後定）。
   - 多抓不到 2 題：差不多，維持現任。
   - 比現任少抓：不採用。
   - 只有 5 題、每題 1 次，差 1 題在雜訊範圍內，不當定論。
