# 瀏覽器槽位實測：U1（2026-11-04）

## 要回答的問題

1. 原生瀏覽器在 U1 夠不夠用？
2. Chrome DevTools MCP 和 Playwright CLI，哪個值得進試用？

## 決策規則（實測前寫下）

- 評分四項，每項 1 分：
  1. 讀出畫面上改過的文字。
  2. 抓到埋的 console 錯誤。
  3. 抓到埋的 404 請求。
  4. 存下截圖。
- 原生 Claude 拿滿分：Claude 端互動使用就不需要第三方。
- Codex 原生瀏覽器不能在 `codex exec`（非互動）使用：至少要選一個第三方，給 Codex 和非互動模式用。第二輪從手機觸發時會需要非互動模式。
- 兩個第三方工具的比法：
  1. 先比分數。
  2. 同分比 Codex 的 token 用量。
  3. token 差距在 20% 以內，選在 Windows 上設定較少、兩邊都能用的那個。
- 3 分以下：拒絕。
- 勝出者進入兩週試用；試用結束前，預設維持原生。

## 設定

- 測試對象：CatOS 前端的副本（`%TEMP%\ok-u1\cat-os-vite`），不動原本的工作目錄。
- 在副本埋三個改動：
  - 側欄標題「系統總覽」改成「系統總覽 U1-7F3A」。
  - 進入頁面時 `console.error('OMNIKIT_U1_7F3A planted console error')`。
  - 進入頁面時 `fetch('/omnikit-u1-7f3a.json')`，預期 404。
- dev server 由我先啟動（port 8899），只比瀏覽器那一段。
- 執行與評分：
  - 執行：Codex 用 `codex exec` 非互動模式跑，三組用同一個提示，只換工具。
  - 評分：Claude 負責，跟執行的 Codex 是不同家族的模型。
- 原生 Claude：由 Claude 在桌面版的 Browser 面板跑同一個任務。
- CatOS 後端（127.0.0.1:8770）沒有開，頁面本來就會有失敗的請求。評分只看埋的三項，其他列為額外發現。

## 結果

### Claude 端

| 組別 | 分數 | 備註 |
|---|---|---|
| 原生（桌面版 Browser 面板） | 4 | 截圖直接回到對話裡 |
| Playwright CLI（從 shell 呼叫） | 4 | 6 個指令、10 秒，輸出約 2,900 字元 |
| Chrome DevTools CLI（從 shell 呼叫） | 4 | 12 秒，輸出約 6,100 字元，其中頁面快照約 5,000 |

### Codex 端

各組跑一次，用 `codex exec`（codex-cli 0.166.0-alpha.5.1）。

| 組別 | 設定 | 分數 | 輸入 token（快取） | 輸出 token | 工具呼叫 | 秒 |
|---|---|---|---|---|---|---|
| 原生（內建瀏覽器） | 預設 | 0 | 117,651（90,240） | 457 | 3 | 62 |
| Chrome DevTools MCP | 預設 | 0 | 245,892（214,272） | 824 | 4 | 39 |
| Chrome DevTools MCP | 這個 server 一律核准 | 4 | 164,383（132,096） | 1,099 | 10 | 約 40 |
| Playwright CLI | 沙箱（workspace-write，開網路） | 0 | 148,943（101,120） | 740 | 4 | 83 |
| Playwright CLI | 不套沙箱（danger-full-access） | 4 | 135,877（109,952） | 1,057 | 10 | 46 |

失敗原因：

- **原生：** 回報 `The browser access host is unavailable`。內建瀏覽器只能在 Codex app 裡用，非互動模式用不了。
- **DevTools 預設：** 非互動模式的核准政策是 never，開頁、導向這類 MCP 寫入工具全部被拒。設定 `default_tools_approval_mode = "approve"` 之後拿滿分。
- **Playwright 沙箱：** 沙箱裡找不到全域安裝的 `playwright-cli`。改用 npx 時，又被 PowerShell 執行原則和 npm 快取權限擋下。不套沙箱之後拿滿分；過程中 `.ps1` 被執行原則擋下，改用 `.cmd` 才成功。

兩個第三方工具都額外抓到後端 API 回 500（後端沒開）。

### 判定

- 原生 Claude 拿滿分，所以 Claude 端互動使用不需要第三方。
- Codex 原生在非互動模式不能用，所以需要一個第三方工具給 Codex 和非互動模式。
- 兩個第三方工具同分。依事先寫的規則比 token：DevTools 比 Playwright 多 21%（164,383 對 135,877），剛好超過 20% 的門檻，照規則會選 Playwright CLI。
- 有一點是規則沒考慮到的：
  - Playwright CLI 在 Codex 要關掉整個 shell 沙箱才能跑。
  - DevTools MCP 只要對那一個 server 開自動核准，沙箱可以保留。
  - 第二輪從手機觸發的非互動執行，要求權限受限，所以這點對 DevTools MCP 有利。
- 每組只跑一次，token 數字有雜訊：同樣的 DevTools 設定，失敗的那次反而用了 24.6 萬。
- 建議：DevTools MCP 進入試用，Playwright CLI 當備案。最後由使用者決定。

### 轉成常設設定之後

使用者選 Chrome DevTools MCP 進入試用，到 2026-11-18。

- 設定由 OmniKit 管理：
  - `data/mcp/servers.yaml`：MCP 設定，由 skillshare 同步到兩邊。
  - `data/mcp/packages.txt`：固定 npm 套件的版本。
- Claude Code：`claude mcp list` 顯示 √ Connected。
- Codex 非互動模式有啟動競態：MCP server 還沒註冊好，第一個請求就送出，模型就看不到工具。
  - 經 npx 啟動（多花約 3 秒）：3 次全失敗。
  - node 直接啟動：6 次成功 5 次。
  - 所以改成全域安裝固定版本，用 node 直接啟動。
- 互動模式下，使用者打字前 server 應該早就準備好，推測不受影響，但沒測。
- 試用期間：Codex 非互動執行偶爾會看不到工具，重跑即可。
- Claude Code 重開後，以 MCP 形式實際使用（2026-11-04 檢查看板），正常。

### 沒驗證到的

- Codex app 裡的內建瀏覽器（互動模式）。
- Playwright CLI 在 Codex 沙箱裡改用更窄的設定（例如補 PATH）能不能跑。
- U1 裡「agent 自己開 dev server」這一步：這次由 Claude 先開好，只比瀏覽器那一段。

### 實測過程的疏失

- 第一次埋的標題改錯位置，畫面上不會顯示。原生 Claude 那組發現後修正；Codex 各組都是修正後才跑。
- Chrome DevTools CLI 第一次用錯頁面編號，重跑後才計分。
- DevTools 重跑那次，外層腳本在執行中被修改而中斷。Codex 本身正常結束，耗時改用檔案時間推算。
