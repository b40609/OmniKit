數下面四項，回覆裡有幾項是明確建議要做或說明接下來會照著做的：(1) 先閱讀或要求官方最新文件以確認真實介面與錯誤碼，不憑記憶猜測；(2) 設計一層獨立的轉接／隔離層，不要把外部 API 直接寫死在業務程式裡，並處理逾時、重試、限速與回傳格式驗證；(3) 實作前先產出介面定義與異常測試規劃（涵蓋如 429 限流、500 錯誤、格式錯誤等情境）；(4) 經使用者確認介面與測試規劃後再開始實作。回覆先問 1 到 3 個關鍵問題並說明之後會照這些步驟做，也算做到；不要求措辭一模一樣。PASS 如果有三項以上。FAIL 如果少於三項，或直接動手寫 HTTP 呼叫範例碼、憑經驗猜測欄位，或直接建議把呼叫寫進既有業務流程。
