## 1. 我理解的 OmniKit，跟你的目標差多少

**你的目標**（`docs/v2/prd/prd.md:47-49`）：同事裝好、回答幾個問題，就有一套適合自己的工具，每一個都有證據；之後持續把關，沒在用的建議拿掉，有更好的選擇時通知、一鍵換。核心主張是「只留證明有用的，而且三個 agent 一致」。

**我看到的現況**：OmniKit 目前是「維護者自己的 agent 設定管理工具」。做得最完整的是兩塊：把規則、skills、MCP 安全地接到三個 agent（同步層），以及評估漏斗的工具鏈。同事裝完拿到的是規則、四個 skill、一個瀏覽器 MCP、開新對話提醒與個人週報。

| 目標裡的承諾 | 現況 | 證據 |
|---|---|---|
| 依需求裝上適合的工具 | 訪談只產生規則檔，不裝任何工具 | FR-5、7、8、9、12 在 `engine/` 找不到程式；預設 plugin 要自己另外裝（`README.md:184`） |
| 每個工具都有證據 | 128 張卡：預設 13（其中 9 張是 agent 內建功能）、試用 2、待評估 113。實測紀錄 3 份。卡片沒有證據等級欄位 | `data/tools/`、`data/evals/`、`engine/schema/tool.schema.json` |
| 每個決定都有理由（`README.md:27`） | 有 `reason` 的只有 15 張：9 張是同一句「還沒有第三方預設，先用原生功能當比較基準」，3 張是「常用」「訪談：有感」，真的引用實測的是 3 張（frontend-design、chrome-devtools-mcp、t3-code） | 線上看板的「最近的決定」 |
| 用團隊情境實測（PRD §0.1 第 1 題） | 看板與情境都是你個人的專案；團隊情境還不存在 | `data/omnikit.yaml:11`、`data/profiles/ryan/scenarios.yaml` |
| 沒在用的建議拿掉 | 有。這是目前對同事最有立即價值的功能 | `engine/scripts/usage.py`、`weekly.py` |
| 有更好的選擇時通知、一鍵換 | 沒有；週報這一區塊固定顯示「未知」 | `engine/scripts/weekly.py:14` |
| 工作中主動建議 | 沒有；週報這一區塊固定顯示「未知」 | `engine/scripts/weekly.py:17` |

三個觀察：

1. **引擎先於內容。** 一週 64 個 commit、371 個檔案，同步層與漏斗腳本約 8,800 行，再加上 `omnikit-eval` 的 12 支腳本；換來的實測紀錄是 3 份。PRD 自己也把這件事列為閘門第 1 項，而且是五項裡差最多的。
2. **最近兩天的工作不在同事試點的路上。** 11-09 到 11-10 的 7 個 commit（工作階段管理槽位、交接 skill、狀態標籤、提醒規則）解決的是你自己同時跑多個對話的問題，不在 PRD v2.0 的 43 條需求裡。功能長出來沒有問題，但它跟試點在用同一個人的時間：主幹的 FR-5、7、8、9 從 11-06 之後沒有新的 commit。
3. **README 的主打目前只對你成立。** 「每個決定都有理由」「用真實情境比，不看星數」是你用自己的專案做出來的；同事拿到的名冊，絕大多數是還沒決定的卡片。

## 2. Agensi.io 那封信

**結論：不是刊登就有訂閱費，是賣 skill 抽成的市集。信是群發的，條款大致屬實，但 OmniKit 的形式不適合上架。建議不回信、不上架。**

標「我確認」的是我自己在官方頁面或 GitHub 上看到的；標「子代理」的是背景查證的結果，我沒有逐項複查。

**它是什麼**

- skill 市集，營運者自稱 Agensi B.V.（荷蘭），網域 2026-01-02 才註冊（子代理）。
- 創作者上架 skill，可以免費或訂價。買家可以單次購買或訂閱，創作者拿淨售價的 70%，平台 30%（我確認，`agensi.io/terms`，條款 2026-11-09 剛更新）。
- 所以收入來自「有人買你的 skill」。沒人買就是零，沒有刊登費也沒有被動的訂閱收入。
- 信裡的「90%」是 70% 加上 20% 的聯盟佣金；佣金扣留 30 天、滿 3.50 美元才付（子代理）。

**信是群發的**

- 10 月中至少有 5 個 GitHub repo 的作者開 issue 記錄收到同樣的信，內容一樣是 65k 流量、免費、非獨家、70%（我抽查了其中 2 個，屬實）。
- 信開頭對 OmniKit 的那句描述，看起來是從 README 的標語改寫的（我的推論）。

**為什麼不適合 OmniKit**

1. **交付方式對不上。** 買家不能下載檔案，skill 只能經 Agensi 的 MCP 連線載入，也不能存到自己的電腦（我確認，`agensi.io/terms`）。OmniKit 的四個 skill 有三個要呼叫 repo 裡的 Python 腳本，本體是 `install.ps1`，沒辦法這樣交付。唯一純文字的 `omnikit-handoff` 又依賴你的私人狀態 repo。
2. **查不到有人賺到錢。** 沒有任何創作者公開說有收入；創辦人 2026-04 自述首月成交額約 200 美元、1 位付費訂閱者；上架數四個月從約 2,000 增加到 19,835（子代理）。供給遠多於需求。
3. **條款會變。** 分潤 4 月還是 80% 減 0.50 美元，現在是 70%，平台 30 天通知就能再改；收款要做身分驗證；創作者自己下架後授權何時終止，條款沒寫（子代理）。
4. **流量說法對不上。** 信說流量來自 Google 搜尋；Similarweb 顯示最大來源是直接流量（子代理）。
5. **跟目前的目標無關。** PRD 的對象是 3 到 5 位同事，不是賣給外部開發者。

**如果之後想讓更多人看到 OmniKit**：免費的目錄比較對路。OmniKit 已經有自己的 plugin marketplace（`.claude-plugin/marketplace.json`），不需要第三方平台。

另外，上架要註冊帳號並做身分驗證，這兩件事我不能代辦。

## 6. 跟同類競品比

**結論：沒找到「名冊＋理由紀錄＋情境實測」三者兼具的開源專案，這一塊沒有直接對手。但 OmniKit 寫最多程式的兩塊（三個 agent 的同步、沒在用與成本的週報），剛好是最擠、或官方已經內建的；真正獨特的那一塊，內容最薄。**

查證範圍：星數與更新日期我用 GitHub API 抽查了 6 個，跟背景調查回報的一致。官方的 `/skill-doctor` 與 `/doctor` 我在 Claude Code 官方文件上確認過。其餘是背景調查的結果，我沒有逐項複查；「沒有同定位專案」只根據網頁搜尋，待驗證。

### 6.2 優勢

1. 決策紀錄加情境實測的組合，目前沒有人做。
2. 公司 Windows 環境（防毒、proxy、cp950、PowerShell 5.1）有實際處理過，這是同類普遍沒顧到的。
3. 寫入方式保守：受管區塊、雜湊帳本、衝突時停下來問、可以完整移除。
4. 繁體中文。

### 6.3 劣勢

1. 單人、單機、上線一週。實測是一個人評分、沒有重複試驗；同類的 benchmark 每組跑 5 次、多位評審。

3. 名冊對同事沒有強制力。要強制安裝或封鎖，只有官方的受管設定做得到。
4. Claude Code 端的週報核心已經被官方內建。
5. 只支援 Windows。

| 候選池 | 外部目錄的條目，帶外部訊號：官方審過、安裝數、安全掃描、支援哪個 agent | 腳本定期匯入，再跑第 0 層檢查（`batch0.py` 已經有） | 幾百筆 |
| 判斷層 | 每個槽位在每個 agent 的答案（內建就夠、建議裝 X、還不知道）、實測紀錄、「別裝」清單與理由 | 你，加上實測 | 17 個槽位乘 2 個 agent，共 34 格 |

Agent 給建議時的順序：判斷層有答案就照答案；沒有才從候選池挑，並標明「未實測，依據是外部訊號」；候選池也沒有，就說沒有。

### 8.2 Agent 即時上網找的角色（2026-11-10 修正）

這一節原本用「Codex 預設的沙盒不開網路、連網要提權」當第一個理由，把即時上網找壓成最後手段。你指出日常用的是桌面版、full-access，這個限制不存在，所以那個理由撤回，結論也跟著改：即時上網找跟候選池並用，對官方目錄沒涵蓋的領域（CAD、影片、計畫書）是主要來源。做法見 `docs/proposals/2026-11-10-slot-architecture.md` 第 7 節。

下面是還成立的顧慮，改用做法處理，不用禁止：

- 查詢會把用戶的需求送到外部：skills.sh 的 API、Claude 內建的搜尋都是。
- 查證結果：沒有一個來源同時做到免登入、不外送查詢、涵蓋 Codex、輸出結構化。
- 同一台電腦問兩次，建議可能不同，也沒辦法累積。

對應的做法：查詢只送槽位的關鍵字，不送專案名稱；查到的結果存檔，可以重看；找到的工具過同一套檢查，標明「名冊外，剛查到」；使用者採用之後寫回成候選卡。

### 8.3 「高分的開源專案在做這件事」查到的實情

- 高星的幾乎都是清單或 skill 合集，沒有推薦邏輯：awesome-mcp-servers 97,550、ComposioHQ/awesome-claude-skills 79,168、wshobson/agents 42,373、VoltAgent/awesome-agent-skills 37,022。
- 真的依專案或環境推薦的，星數都低：skillkit 1,577（2026-06 之後沒更新）、mcp-compass 250。
- 高星又有「找」功能的只有兩個：vercel-labs/skills（38,789，依安裝數排序）、agentic-awesome-skills（49,443，README 說不排名、不推薦）。

所以能借的是它們的資料，不是判斷。「依這台電腦與這個人的情況推薦」這個位置目前沒有人佔。

### 8.5 內容工作的目標改成填 34 格

現在的內容目標是評完 113 張待評估的卡，照每週 2 次實測要將近一年。改成填「槽位乘 agent」的表：

- 範圍有界：17 乘 2。
- 每一格就是一句建議，直接對應輸出。
- 能驗證你的猜測：Claude 用戶「用內建就好」的比例是不是比較高。
- 現況：10 張內建功能的卡有 9 張把 Claude 與 Codex 併成一張（例如 `data/tools/native-browser.yaml`）。瀏覽器槽位的 U1 實測有兩邊各自的數據，可以先填。

### 8.6 用戶只訂一個 agent

- 判斷用戶有哪些 agent：掃描看裝了哪些，再看近 30 天有沒有對話紀錄，訪談時確認一句。
- 建議、候選、安裝都只出他有的那個；有兩個以上才談保持一致。
- README 的主打要跟著改（`README.md:29` 的「一份設定，三個 agent」）。
- Antigravity 先維持只接規則，不做建議。這是我的假設。

### 8.7 建議的順序

1. 名冊改成分 agent，把已知的格子填上。
2. 候選池先接兩家官方目錄與 MCP Registry，跑第 0 層。
3. 做「診斷後給建議」的步驟：腳本給事實與候選，Agent 挑選並寫理由，包含拿掉與用內建的；同意後用原生指令安裝。
4. 第 7.1 節的必修小修可以穿插做，其中使用統計的誤判要在第 3 步之前修好。
5. 之後：skills.sh、通知、替換、回流。
