# 問法庫：真實糾正題（方向 6）

日期：2026-11-18。接續 [擴充到 79 題那一輪](2026-11-17-ask-eval-expanded.md)。那份的分數有一個最大的打折：題目和評分標準都是從問法庫的情境檔產出的，等於考題跟課本同一個人出。這一輪改用真實的人與 coding agent 對話紀錄出題，評分標準只看「使用者後來真正要的是什麼、agent 原本錯在哪」。

腳本：`data/pilot/ask-eval/agy_eval.py --set real`。題目：`data/pilot/ask-eval/real/`（41 題，說明見該資料夾的 README）。結果摘要：`data/pilot/ask-eval/results/2026-11-18-agy-flash-real.json`。

## 結論

**換成真實題目、評分標準不跟問法庫同源之後，問法庫幾乎沒有效果。**

- **品質**：只裝全域 0.60 分，都沒有 0.55 分，差 +0.03。38 題成對比較：5 題變好、3 題變差、30 題一樣。79 題那一輪的差距是 +0.35（0.80 比 0.45）。
- **使用者真正要的**（`need` 評分項）：有它 18/38、沒它 17/40 通過，兩組都不到一半。agent 原本的錯（`pitfall`）兩組都大多避開了（32/38、32/40）。
- **叫用**：
  - 使用者描述處境、問怎麼辦的 18 題（`stuck`）：叫用 10/18（56%）。訓練題的基本說法是 56/59（95%）。
  - 使用者直接糾正 agent 的 22 題（`correction`）：叫用 10/22（45%）。照問法庫的說明，講清楚要做什麼的請求應該直接做；訓練用的負面題誤叫用是 4/20（20%）。
- **只裝全域時**，有叫用的回合 0.70 分、沒叫用的 0.50 分；但會叫用的題目本來可能就比較容易，這個差距不能當成因果。
- **`stuck` 那 18 題**兩組都是 0.76 分，差 0。分數的差全部來自 `correction`（0.45 比 0.38）。

我的判斷：79 題那一輪的 +0.35，大部分來自評分標準跟問法庫同源（評分項列的正是問法庫建議的做法）。在真實需求上，Gemini 3.8 Flash 本身就答得差不多好；它答不好的地方（例如要用使用者的實際資料重現、要先問清楚是哪一塊空白）問法庫目前也沒有幫上忙。**不要照這組的結果改問法庫**（它是外部驗證題）；要改的話要先換一批題目。

## 資料來源與授權

- **「SWE-chat」是什麼**：Baumann、Padmakumar、Li、Yang、Yang、Koyejo，[SWE-chat: Coding Agent Interactions From Real Users in the Wild](https://arxiv.org/abs/2604.20779)（COLM 2026）。資料集在 [Hugging Face `SALT-NLP/SWE-chat`](https://huggingface.co/datasets/SALT-NLP/SWE-chat)：
  - v2（2026-10-02）有 17,968 段對話、229,909 句使用者訊息，Claude Code、Codex、Gemini CLI、Cursor 等都有。
  - 使用者訊息有 LLM 標註的反駁類別（`prompt_pushback`：correction、rejection、failure_report）。
  - 授權標 ODC-BY。下載要登入 Hugging Face 並同意分享帳號資訊（gated: auto）。這台的 `hf` 沒有登入，所以這輪沒有用 Hugging Face 上的版本。
- **實際用的**：SWE-chat 的上游。公開 GitHub repo 裡由 [Entire.io](https://entire.io) CLI 存的 checkpoint（`refs/entire/checkpoints/*`），每段對話有 `prompt.txt`（使用者訊息）、`metadata.json`、`transcript.jsonl`。不用登入，`git fetch` 就拿得到。
  - 用 GitHub 程式碼搜尋 `.entire/settings.json` 找到 300 個 repo，其中 99 個有 checkpoint。依數量挑了 10 個來抓，最後出題用到 3 個：
    - `entireio/cli`：MIT
    - `thedannywahl/pantoken`：MIT
    - `getnao/nao`：沒有標授權
- **repo 裡只存改寫後的繁體中文題目與出處，不存原文**。每題的 `source` 寫 repo、checkpoint ref、檔案路徑、第幾句與 session id，可以回去查。抓下來的原始資料只放在這次對話的暫存資料夾。
- **沒有用的替代來源**：沒有另外比較其他資料集（例如 WildChat 一類的通用對話）。SWE-chat 已經是「真實使用者對 coding agent、附反駁標註」最直接的來源，上游又能直接取得。

## 出題方式

1. 從 10 個 repo 抓約 2,700 段對話、14,249 句使用者訊息（`entireio/cli` 佔 11,227 句）。只抓小檔，大的 transcript 不下載。
2. 用關鍵字（still、again、you said、forgot、revert、why did you、too much…）篩出 567 句「強」候選。抽樣約 300 句人工看，挑出 41 句，再看每句的前兩句與後兩句，判斷使用者後來真正要什麼。
3. 改寫成單輪繁體中文題目：
   - 去掉個人路徑、帳號與連結。
   - 分兩種：`stuck`（18 題，描述處境問怎麼辦，該叫用）、`correction`（23 題，直接糾正，照說明該直接做）。
   - 各題標出對應的問法庫情境；沒有對應的 10 題標「沒有對應情境」，留給方向 5。
4. 評分項：
   - `need`（權重 2）：使用者後來真正要的（多半取自那句之後的訊息）。
   - `pitfall`（權重 1）：agent 原本錯在哪，回覆有沒有避開。
   - 兩項都由我（Claude Opus）照原始對話寫，沒有讀問法庫的情境檔。
5. 跑法：
   - `--arms global,without`，帳號 ava，Gemini 3.8 Flash（High），每題每組 1 次，`-j 3`。
   - 評分者：本機 Claude Code 的 Sonnet。
   - 跑完用同一個 `--out` 補跑錯誤與翻到評測資料夾的回合。

- **變好的題目**：
  - `real-agent-interactive-shell`、`real-agent-lint-still-fails`：叫用後都要求用實際執行結果確認，各 +0.67。

- **變差的題目**：
  - `real-ui-too-much-spacing`（0 比 0.67）：叫用後給了一大段「可以貼給另一個 agent 的問法」，直接把所有間距一起改。使用者要的其實是先確認是哪一塊空白。
  - `real-agent-not-convinced-needed`（0.33 比 1.0）：叫用後給了一般性的判斷清單。使用者要的是一個用專案慣例佐證的答案，或者換一個模型給第二意見。
  - `real-agent-worse-refactor`（0.67 比 1.0）。
- **兩組都 0 分**：
  - `real-agent-blames-stale-binary`：沒有自己用同一個指令重現，又把排查丟回使用者。
  - `real-debug-trim-not-function`：猜對 content 是陣列，但沒有要求用使用者那筆 Gemini 資料驗證。
  - `real-ui-broke-button-group`。

  這幾題是問法庫可以補的地方，但要照訓練題的方式另外出題，不要直接拿這幾題改。

### 跟 79 題那一輪比

| | 79 題（11-17，同源評分） | 訓練題 59 題（11-18 定稿） | 真實糾正題（這一輪） |
|---|---|---|---|
| 只裝全域 | 0.80 | 0.85 | 0.60 |
| 都沒有 | 0.45 | 沒跑 | 0.55 |
| 差距 | +0.35 | 沒跑 | +0.03 |
| 該叫用的叫用率 | 64/79 | 56/59 | 10/18 |
| 不該叫用的誤叫用 | 0/30 | 4/20 | 10/22 |

- **「都沒有」差最多**：從 0.45 變 0.55。同一個模型，沒有問法庫也能拿到一半以上的分數，代表舊評分標準在獎勵「照問法庫的格式回答」（例如「有可以直接貼的句子」）。新的標準只看有沒有解決使用者的問題。
- **真實的「卡住」說法叫用率低很多**（56% 比 95%）：真實使用者不會說「我不知道怎麼問」，比較常是帶著專案細節抱怨。
- **糾正句的誤叫用率高**（45%）。叫用後的回覆常變成「教使用者怎麼問」，而使用者要的是直接修。

## 要打折看的地方

- **每題每組只跑 1 次**，差距 +0.03 在雜訊範圍內。這輪能說的是「看不出效果」，不能說「確定沒效果」。
- **單輪、空資料夾**：原始對話有 repo 與前文，這裡 agent 只能給方向。很多 `need` 要的是「用使用者的實際資料重現」，單輪本來就很難拿分，兩組都會被壓低。
- **挑題和評分標準都是同一個模型（Claude Opus）寫的**，沒有人工複核；評分者是 Sonnet，同家。跟問法庫不同源，但跟評分者同源。
- **題目分佈不平均**：agent、debug 佔一半；requirements、research、ux 沒有題目；`entireio/cli` 佔 26 題。使用者多是英文、Claude Code 早期採用者。
- **排除了 4 個回合**：都是翻到了評測資料夾（`peeked`），其中 1 個同時 600 秒逾時，1 個讀到 11-17 那輪留在暫存資料夾的評分標準。
  - `real-agent-double-redaction` 兩組在兩次嘗試裡都逾時或去翻資料夾，這題沒算分。
  - `real-arch-rename-recap`、`real-debug-ci-a11y-vague` 只有沒它那組算分。
- **叫用率**包含那 3 個翻到評測資料夾、但沒有錯誤的回合（叫用判定跟算分分開）。

## 過程中踩到的

1. **第一輪作廢**：題目原本沒有說明「專案不在這台電腦」。沒有前文的糾正句（「你剛剛改的…」）讓 Gemini 在整個使用者資料夾找專案：翻到 OmniKit 的 `data/pilot/ask-eval`（連這組的評分標準都讀到），還有好幾題 600 秒逾時。
   - 改法：每題最後加一句固定說明。`agy_eval.py` 新增 `peeked`：工具參數出現 `ask-eval` 的回合不算分。
   - 加了說明之後，82 回合裡仍有 7 回合去翻，補跑後剩 4 回合。
   - **這也是安全上的發現**：Flash 在完整權限下會主動搜尋整個使用者資料夾找脈絡。之後的評測應該把工作資料夾隔離得更徹底（例如另一個 Windows 帳號或容器）。
2. **誤殺另一條對話的程序**：要停自己第一輪的評測時，我把方向 4 那條對話（kai 帳號的 `multiturn_eval.py`）的 python 當成自己的，結束了它和底下的 agy 程序。已經傳訊息通知那條對話，用同一個 `--out` 重跑可以補回。之後只用自己記下的 PID 或 Job Object 停程序。
3. **額度**：ava 的 Gemini 5 小時視窗從 1% 用到 28%，週額度從 15% 到 24%。

## 之後

- 這組留作外部驗證，問法庫改版定案時再跑一次，同樣不照它調。
- 10 題「沒有對應情境」交給方向 5：看要不要新增情境，例如「改了範圍外的程式」「誤解需求方向（改 A 變成退回 B）」「卡在互動式指令」。
- 值得另外討論、這輪沒有動：問法庫在使用者直接糾正 agent 時要不要保持安靜。這輪 45% 誤叫用，叫用後也沒有比較好。
