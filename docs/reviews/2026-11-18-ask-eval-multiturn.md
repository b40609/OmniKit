# 問法庫：小型壞專案 + 多輪模擬使用者

日期：2026-11-18。被測：Antigravity 的 Gemini 3.8 Flash（thinking high），kai 帳號。模擬使用者：Claude Sonnet（`claude -p`）。

## 結論

在小型真專案、多輪對話下，**裝不裝問法庫，結果差不多**：

- 兩組都 26/26 修好（13 題、每組每題 2 次，每題 2 次都修好 13/13）。
- 平均 agent 輪數：只裝全域 2.04、沒裝 1.92。平均糾正：0.38 對 0.42。
- 單輪評測在同樣 13 題的分數差是 0.97 對 0.54（+0.44），這個差距**沒有變成「少修正幾輪」**。

差在哪裡：

- **需求不清、介面文案這兩類有幫到**。req-unclear 平均 4.0 輪對 5.0 輪、糾正 1.5 對 3.0；
  ux-technical-copy 2.0 輪對 3.0 輪。問法庫讓 agent 先問清楚，少走冤枉路。
- **能直接重現的 debug、ui 題反而多一輪**。有裝時 agent 第一輪常先教「你可以直接貼這句給我」，
  再問要不要動手：第一輪就修好只有 5/26，沒裝是 10/26；第二輪使用者只回「好，直接做」的有 14/26，沒裝是 9/26。

要決定的事：問法庫在「工作資料夾裡就能重現」的情況，要不要改成先動手修、問法建議放最後（見「下一步」）。

## 為什麼要換量法

單輪評測（[2026-11-17-ask-eval-expanded.md](2026-11-17-ask-eval-expanded.md)）量的是「回覆有沒有照好的做法」：
工作資料夾是空的、只問一次、評分標準跟問法庫同源。它答不了使用者真正在意的事：照著做，**實際少修正幾輪、最後有沒有修好**。

這次改成：每題一個很小的真專案（幾個檔案），有可重現的 bug、亂掉的畫面或需求不清；
模擬使用者只知道處境與想要的結果，依 agent 的回覆回話，最多 6 輪；成敗用隱藏的自動檢查判，不靠 LLM 評分。

## 業界做法與比較

子代理照 `omnikit-research` 查了 12 組關鍵字（只用英文網頁搜尋與兩次全文讀取；沒跑帳本、GitHub topic、HN、中文，
所以**不算飽和**，是「12 組到上限先回報」）。

| 名稱 | 模擬使用者怎麼寫、怎麼結束 | 成敗判定 | 指標 | 借用了什麼 |
|---|---|---|---|---|
| [tau-bench](https://arxiv.org/abs/2406.12045) / [tau2](https://arxiv.org/pdf/2506.07982) | 每輪一句、只講當前需要的、不知道就說沒有；達成時輸出 `###STOP###`（[user.py](https://raw.githubusercontent.com/sierra-research/tau-bench/main/tau_bench/envs/user.py)） | 自動：比對最後的資料庫狀態 | pass^1、pass^k | 只給目標不給解法、自動判成敗、同題重跑看「k 次都過」 |
| [Ambig-SWE](https://arxiv.org/html/2502.13069v3) | 把 SWE-bench issue 摘成資訊不足版給 agent；模擬使用者看得到完整 issue，只能照它回答 | 自動：SWE-bench 測試 | 隱藏／互動／完整三種設定的解決率、提問數 | 完整需求藏在使用者手上，被問到才講 |
| [Ask or Assume?](https://www.alphaxiv.org/abs/2603.26233)、[LHAW](https://github.com/scaleapi/lhaw) | 同型：只能用被隱藏的原文回答 | 自動：測試 | 解決率、提問次數 | 同上 |
| [UserBench](https://arxiv.org/abs/2507.22034v1) | 使用者一開始目標模糊、偏好一點一點透露 | 自動：是否符合全部意圖 | 意圖命中率 | 「漸進透露」的使用者 |
| [CRMArena-Pro](https://arxiv.org/pdf/2505.18878) | 使用者分批釋出資訊 | 自動 + LLM（細節待驗證） | 單輪 vs 多輪成功率（數字是二手，待驗證） | 同上 |
| [ColBench / SWEET-RL](https://arxiv.org/abs/2503.15478) | 模擬人類看得到參考成品，只回答 agent 的疑問 | 自動：功能測試、相似度 | 成功率 | 使用者握有參考答案但不主動給 |
| [MINT](https://arxiv.org/abs/2309.10691) | GPT-4 給自然語言回饋，多輪 | 自動 | 隨輪數的成功率 | 輪數當指標 |
| [IntellAgent](https://arxiv.org/abs/2501.11067) | 從政策圖抽情境，使用者 agent 對話 | LLM 分析 | 各難度成功率 | 只參考 |
| [SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/) | 單輪、沒有模擬使用者 | 自動：FAIL_TO_PASS 全過、PASS_TO_PASS 不壞 | % resolved | 隱藏測試；「修好的要過、原本好的不能壞」 |
| [Terminal-Bench](https://www.tbench.ai/docs/task-overview) | 沒有模擬使用者 | 自動：每題附 tests/ | 通過率 | 每題 = 環境 + 參考解 + 測試 的資料夾結構 |

已知的坑（研究裡有寫的）：模擬使用者比真人配合、愛問、客氣；光換使用者模型成功率就差到約 9 個百分點
（[Lost in Simulation](https://arxiv.org/html/2601.17087v2)）；同家模型互評會偏袒（這次是推論到模擬使用者，**待驗證**）。

## 這次的設計

| 決定 | 做法 | 理由 |
|---|---|---|
| 題目 | 13 題，全是訓練題（base 不在 `holdout.txt`）：debug 5、agent 3、ui 2、ux 1、req 1、arch 1 | 涵蓋要求的 ui、debug、agent、req；每類挑得出「小專案就能重現」的情境 |
| 壞專案 | `data/pilot/ask-eval/multiturn/<題目>/project/`，複製到暫存資料夾並 `git init` 當工作資料夾 | 仿 Terminal-Bench 的每題資料夾；git 讓 agent 能看 diff |
| 成敗判定 | 每題 `check.py`（agent 看不到），每輪 agent 回完就跑；通過就結束 | SWE-bench 的隱藏測試；同時檢查「該修好的」與「原本好的不能壞」（例如 debug-side-effect 的會員資料與匯出） |
| 參考修法 | 每題 `reference/`；`--selftest` 確認 check 對壞專案判失敗、對參考修法判通過，CI 每次跑 | 先證明檢查本身是對的 |
| 模擬使用者 | Claude Sonnet（`claude -p`，關工具、MCP、設定檔），只拿「處境、想要的結果、細節」；不准講解法、檔名、程式碼；只回答被問到的那幾點 | 跟被測的 Gemini 不同家；不吃 kai 的 Gemini 額度；跟單輪評測的評分者同一套呼叫，維護一份 |
| 使用者「試用」 | 只有 agent 說改好或請他試時，才拿 check 印的「症狀」（使用者看得到的現象，不含原因）回報 | 真人會打開來看；症狀一次只給一個，跟真人一次看到一件事一樣 |
| 結束 | check 通過、或 6 輪用完、或模擬使用者放棄（kind=stop，相當於 `###STOP###`） | tau-bench 的結束標記；上限 6 輪參考 Ambig-SWE 的提問上限 |
| 記錄 | 修好沒、第幾輪修好、agent 回幾輪、使用者回話種類（糾正／回答／請它繼續）、有沒有叫用問法庫 | 「糾正」是模擬使用者自己標的，見打折 |
| 組別 | `global`（只裝全域，實際情況）vs `without`（overlay 拿掉 omnikit-ask、ok、ok-ask） | 沿用 agy_eval.py |
| 重跑 | 每題每組 2 次，報修好率與「每題 2 次都修好」（pass^2） | tau-bench 的 pass^k |

跑法：

```bash
uv run data/pilot/ask-eval/multiturn_eval.py --selftest
```

```bash
uv run data/pilot/ask-eval/multiturn_eval.py --account kai --model gemini-3.8-flash-high --arms global,without --runs 2 -j 3
```

試跑時發現模擬使用者在需求題（req-unclear）被問到三個選項時，一口氣把六條隱藏需求全講出來，等於洩漏答案；
正式跑之前把規則改成「只回答被問到的那幾點、它的預設跟你要的一樣就同意」。

### 讀對話看到的

- **有裝時第一輪多半先教問法**：例如 debug-flaky 的回覆是「你可以直接貼這句給我：先不要改程式碼，請列出 3 個可以被驗證的假設……」，
  最後問「要我直接開始嗎」；ui-vague 也是先給一段可以貼的問法，再列診斷清單等使用者挑。開場本來就是「我該怎麼請你做」，
  這樣回答不算錯，但在真專案裡多了一來一回。
- **沒裝時也常先停下來確認**：debug-side-effect 兩組第一輪都是「【等你決定】要我直接修嗎」。這來自工作資料夾裡的 OmniKit 規則
  （AGENTS.md 的狀態標籤），不是問法庫造成的。
- **需求題的差距是真的**：沒裝的 req-unclear #1 被糾正 4 次（英文表頭、多了狀態欄、金額有小數、沒照日期排），每次只修使用者剛抱怨的那一點；
  有裝的兩次都在動手前先問格式、狀態與欄位。
- **ux 題**：有裝時第一輪就列出改寫對照表請使用者確認，使用者只補一句「422 是沒選對帳狀態」；沒裝時先改成「請檢查輸入欄位」這種籠統說法，又多一輪。

## 跟單輪結果對照

同樣這 13 題（base 一樣）在單輪評測的分數：

| | 單輪分數（Sonnet 評分） | 多輪：平均輪數 | 多輪：平均糾正 | 多輪：修好 |
|---|---|---|---|---|
| 只裝全域 | 0.97（2026-11-18 最終說明，12 題滿分、arch-db-migration 0.67） | 2.04 | 0.38 | 26/26 |
| 沒裝 | 0.54（2026-11-17 有它與沒它對照） | 1.92 | 0.42 | 26/26 |
| 差距 | +0.44 | +0.12 | -0.04 | 0 |

單輪差最多的題目，多輪幾乎沒差：debug-env-diff、debug-error-output 單輪沒裝都是 0 分，多輪沒裝卻 1 到 2 輪就修好、零糾正。
原因：單輪的評分標準問的是「有沒有教使用者怎麼問、有沒有先查證」，空資料夾裡 agent 只能用講的；
放進真專案後，沒裝的 agent 直接讀檔、重現、修好，結果一樣好。單輪分數量到的是「回覆像不像好的問法建議」，不是「少走幾輪」。

反過來，單輪也看不到 req、ux 這兩類在多輪裡真的少了糾正。兩種量法要一起看：單輪看叫用與建議內容，多輪看實際結果。

## 要打折看的地方

- **天花板**：兩組修好率都是 100%。題目對 Gemini 3.8 Flash（high）太簡單，修好率分不出差別，只剩輪數可比。
- **樣本小**：每題每組 2 次，輪數差 +0.12 在雜訊範圍內；req、ux 的好處各只有 1 題、2 次。
- **開場就是在問做法**：題目沿用問法庫的情境（「該怎麼請你做」），本來就邀請 agent 先給建議；先建議再等確認被算成多一輪，對問法庫不利。
  使用者如果直接說「幫我修」，問法庫照說明不該叫用，這種情況沒量。
- **兩組都會先停下來問**：工作資料夾放了平常的 OmniKit 規則（AGENTS.md），它的「【等你決定】」狀態標籤讓兩組都常在第一輪先確認。
- **模擬使用者太配合**：幾乎都是一句「好，直接做」就放行；真人可能照著建議的問法重講一遍，或根本不看。研究也指出模擬使用者比真人配合、客氣。
  沒有換使用者模型（例如 Gemini）看結果會不會變。
- **模擬使用者沒完全守規則**：有時 agent 還沒說改好，它就拿試用的症狀出來講（症狀都是開場已知的現象，沒有原因或解法）；
  沒裝的 req-unclear #2 回答問題時順便講了沒被問到的欄位要求，對沒裝組有利。正式跑之前已經收緊過一次（見設計）。
- **「糾正」是模擬使用者自己標的**：回答問題時順便否定 agent 的預設值也標成糾正。主要看修好與輪數，糾正只當參考。
- **檢查的嚴格度**：第一版 agent-notdone 的檢查只接受「整項再算稅」，把「每件含稅後乘數量」也判錯，還回報成「還是未稅」誤導使用者；
  修正後這題 4 段對話重跑，舊結果不算。ui-vague 的字級上限（5 種放寬到 6 種）、req-unclear 的金額千分位逗號也在正式跑之前放寬。
  其他題仍可能有「合理但不同」的做法被判錯，這次讀到的失敗都是真的沒做到。
- **出題者同源**：題目、人設與檢查都是這條對話寫的；成敗由程式判，比單輪的 LLM 評分客觀，但「使用者想要什麼」仍是出題者定的。
- **只用訓練題**：13 題的 base 都不在 holdout.txt，保留題沒碰。
- **只有一個被測模型、一個帳號**：Gemini 3.8 Flash high、kai 帳號。
- **調研不飽和**：只查 12 組英文網頁，沒查 GitHub topic、HN、中文。
- **跑的過程**：第一次跑到第 7 段時程序中斷（exit 127）。原因是方向 6 的對話停自己的評測時誤殺了這個程序（它事後來訊說明）。
  被殺當下還在跑的對話沒有寫出結果檔，不會留下錯誤紀錄；用同一個結果資料夾接著跑，只補缺的，最後 52 段都是完整跑完的對話（0 錯誤）。

## 用掉的額度

- kai 帳號 Gemini：週額度 12.0% → 23.7%，5 小時窗 8.2% → 58.3%（`~/.t3/caches/antigravity_kai.json`，含 3 段試跑與被中斷那輪）。
- 模擬使用者（本機 Claude Code 的 Sonnet）：約 55 次 `claude -p`，每次幾千個輸入 token。
- 時間：正式跑約 2 小時（`-j 3`）。

## 下一步（建議）

1. **問法庫加一條：工作資料夾裡就能重現時，先動手修，問法建議放最後一段**。用這套多輪題驗證（看第一輪就修好的比例與 debug、ui 的輪數），
   不要拿保留題調。
2. **加難度**：題目改到 Flash 會失敗的程度（更多檔案、更多隱藏需求、兩個互相牽動的 bug），或改測比較弱的模型，讓修好率不再滿分。
3. **補「直接說要做什麼」的開場**：同一個壞專案配一個不問做法的開場，看問法庫會不會誤叫用、拖慢。
4. **換模擬使用者模型**（例如 Gemini Pro）各跑一次看敏感度，並人工抽讀幾段對話。
5. **每題跑 3 次以上**，報 pass^3。
