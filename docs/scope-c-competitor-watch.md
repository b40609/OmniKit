# 範圍 C：外部競品與收錄交叉檢視固定流程

> 誕生背景（2026-11-27，2026-11-28 升級為所有 OmniKit＋OmniKeep 用戶開箱通用的增量雙層架構）：內部健康檢查與程式碼巡檢（範圍 A／B）只看自家程式碼，容易陷入「以為全部完工、卻早已在外部工具生態重造輪子或明顯落後」的盲區。本流程把「外部競品 × OmniKeep 近期收錄 × 我方活躍專案定位」交叉檢視做成可重複執行的低雜訊常態機制。

## 定位與邊界（所有 OmniKit＋OmniKeep 用戶通用）

- **落地位置**：OmniKit（作為跨專案治理與審查層；不把跨專案競品分析塞進 OmniKeep 內建小模型）。
- **零設定開箱支援**：
  - 自動偵測本機 `omnikeep.db`（支援 `--db`、環境變數 `OMNIKEEP_DB` 或 `~/.omnikit/watch.yaml`），一律採 SQLite URI `?mode=ro` ＋ `PRAGMA query_only = ON` 唯讀存取。
  - 自動掃描 `~/.omnikit/status/*/NOW.md`（同步狀態 repo）與 `~/.omnikit/local-status/*/NOW.md`（免帳號本機模式），並依各專案 `NOW.md` 內容自動推導領域關鍵詞。
  - 進階使用者可在 repo 外的 `~/.omnikit/watch.yaml` 自訂專案關鍵詞、額外狀態目錄與工程放行詞，絕不污染公開 repo。
- **增量水位線與歸併防護**：
  - 水位線存在 `~/.omnikit/state/watch_cursor.json`，`--since-last` 只撈上次檢視後新增或更新的收錄；`--mark-seen` 於結案後推進水位線。
  - 查詢同時比對 `created_at` 與 `updated_at`，解決 OmniKeep 將新社群貼文歸併進既有 GitHub 卡片時只改 `updated_at` 導致漏掃的問題。

## 三種觸發方式

| 觸發模式 | 適用情境 | 執行方式 |
| :--- | :--- | :--- |
| **1. 每週定時（T3 排程）** | 常態防盲區，每週固定時間自動巡檢上次之後的新收錄並推摘要 | T3 排程啟動隔離記憶對話，執行 `competitor_watch.py scan --since-last`，產出兩層簡報＋推進水位線 |
| **2. 手動一句話觸發（三家通用）** | 剛滑手機收了一大批連結，想立刻對照討論 | 在 Claude Code／Codex／Antigravity 直接說「**巡一下 OmniKeep**」「**看 OmniKeep 新連結**」，或輸入 `/omnikit-watch` |
| **3. 丟特定專案即時對決** | 滑到某個開源專案，想立刻知道值不值得改接或借鏡 | 丟出 GitHub URL／`owner/repo` 並呼叫 `/omnikit-watch <repo> [專案名]`，執行 `competitor_watch.py target <repo>` |

## 兩層輸出與降噪漏斗（嚴防報告水化與額度失控）

### 第 1 段：確定性前置篩選（`competitor_watch.py`）
1. **只掃手動收錄並排除自我回寫**：預設僅讀取 `origin='manual'` 且排除 `source_type='insight'`（避免 agent 透過 `writeback_insight` 寫回的報告下一週再進漏斗造成自我迎合迴圈）。
2. **必查快車道（Fast Track）與星標／備註加權**：僅使用者備註明確帶競品標記（`#競品`、`#watch`、`重造輪子`）走必查快車道（+60，不受分類過濾影響）；單純加星（+25）與一般手動備註（+10）只做加權、仍須經過非工程分類雜訊過濾。
3. **細化非工程雜訊濾除**：美食、旅遊、八卦與純喊單投資文自動剔除；但若命中任一活躍專案關鍵詞、含 GitHub repo，或內容含工程方法論詞（回測、過擬合、設計系統、彈出層、MCP、CLI、OCR 等）則自動放行。
4. **兩層輸出**：
   - **Layer A（各專案關聯全景）**：將所有相關候選按專案分組呈現，30 秒掃完全景。
   - **Layer B（最多 3 項深挖）**：同 repo 去重後，最多 3 項進入一手原始碼深挖。

### 第 2 段：一手原始碼與反例深挖（主力 Coding Agent）
對選出的最多 3 項標的，嚴格要求：
1. **一手實測數據**：所有星數、授權、最後 push、最新 release 必經本機 `gh api` 查證並標註日期；禁止抄貼文或二手摘要數字。
2. **必看實際原始碼**：檢查關鍵檔案（如 `SKILL.md`、MCP tool schema、`package.json`／`pyproject.toml`、核心邏輯），禁止只看 README 行銷文案下結論。
3. **強制反例與邊界**：每一項至少寫出 1 條具體缺點、Windows／本機環境相容性限制或社群反例。
4. **強制改判條件**：明確寫出「什麼可檢驗的未來事實出現時，應該推翻今天的結論」。

## 強制五選一處置（嚴禁建立 `pending` 墳場）

每項深挖標的結案時，必須歸入下列 5 種處置之一，**不允許以「再觀察看看／待決定（pending）」含糊帶過**：

1. **`adopt_or_integrate`（直接導入／改接）**：確認外部方案已成熟且免我方重造輪子，列出最小改接步驟或開立待辦。
2. **`steal_pattern`（借鏡設計模式）**：不整包換掉，但明確點出要借鏡的具體規格／做法與落點檔案。
3. **`replace_or_retire`（取代／退役自家方案）**：確認我方既有實作過重或維護成本過高，提出減法／退役計畫。
4. **`watch_with_trigger`（帶改判條件的觀望）**：暫不改動，但寫死明確可檢驗的觸發門檻（例如「支援 Windows 原生沙盒」或「發佈 v2.0 正式版」）。
5. **`dismiss_with_evidence`（附證據排除）**：證實不適合或弱於現任，記錄拒絕證據（必要時透過 `record_decision.py` 寫入名冊防日後重複踩坑）。

## 防迎合與記憶隔離守則

- **記憶隔離**：每週排程與跨家盲審對話一律以隔離記憶／乾淨 session 啟動，第 1 段只以腳本輸出為準。
- **反順從原則**：使用者丟出特定專案即時詢問時，**不得假設使用者想導入該專案**；必須先站在「維持現狀是否更好」的對立立場找反例，再平衡給出五選一建議。
- **重大架構改動升級**：若範圍 C 檢視得出「需要推翻核心架構或更換主路線」的結論，不可直接開工，必須啟動 OmniKit 兩階段防迎合盲審（Stage 1 零錨定獨立設計 → Stage 2 正面對決＋改判條件）並由異家同級模型審查。
