# 範圍 C：外部競品與收錄交叉檢視固定流程

> 誕生背景（2026-11-27）：內部健康檢查與程式碼巡檢（範圍 A／B）只看自家程式碼，容易陷入「以為全部完工、卻早已在外部工具生態重造輪子或明顯落後」的盲區。本流程把「外部競品 × OmniKeep 近期收錄 × 我方活躍專案定位」交叉檢視做成可重複執行的低雜訊常態機制。

## 定位與邊界

- **落地位置**：OmniKit（作為跨專案治理與審查層；不把跨專案競品分析塞進 OmniKeep 內建小模型）。
- **資料來源**：唯讀讀取本機 `omnikeep.db`（`?mode=ro` ＋ `PRAGMA query_only = ON`）、`~/.omnikit/status/*/NOW.md`（各活躍專案定位卡）與 `data/tools/*.yaml`（已評估／已拒絕名冊）。
- **執行引擎**：主力 Coding Agent 搭配確定性前置腳本 `engine/scripts/competitor_watch.py` 與 `gh api`＋一手原始碼檢核。

## 三種觸發方式

| 觸發模式 | 適用情境 | 執行方式 |
| :--- | :--- | :--- |
| **1. 每週定時（T3 排程）** | 常態防盲區，每週自動掃過去 7 天手動收錄 | T3 排程於每週固定時段啟動隔離記憶對話（`No project`），執行 `competitor_watch.py scan --days 7` 並對 Top 3 做深評 |
| **2. 手動觸發** | 隨時想清點最近收錄跟自家專案的落差 | 對話呼叫 `/omnikit-watch` 或直接說「做一次範圍 C 競品檢視」 |
| **3. 丟特定專案即時觸發** | 滑到某個開源專案，想立刻知道值不值得改接或借鏡 | 丟出 GitHub URL／`owner/repo` 並呼叫 `/omnikit-watch <repo> [專案名]`，執行 `competitor_watch.py target <repo>` |

## 兩段降噪漏斗（嚴防報告水化與額度失控）

### 第 1 段：確定性前置篩選（`competitor_watch.py`）
1. **只掃手動收錄**：預設僅讀取 `origin='manual'`，過濾自動雷達未經人眼確認的雜訊。
2. **必查快車道（Fast Track）與星標加權**：使用者備註含 `#競品`、`#watch`、`對比`、`比較`、`重造輪子`、`取代` 或帶有明確提問備註的收藏走必查快車道（+60，不受分類過濾影響）；單純加星（`is_starred=1`）則對工程／專案相關項目額外加權（+25），避免順手加星的生活或投資文章擠掉技術競品名額。
3. **非工程雜訊濾除**：投資、股市、生活、旅遊、美食、新聞娛樂等非工程分類（且無 GitHub repo、未進快車道）自動剔除並附略過理由。
4. **名冊查重與專案配對**：自動從 URL、`item_citations` 與摘要萃取 GitHub `owner/repo`，比對 `data/tools/*.yaml`（立即標示曾被 `rejected` 或現任 `default`）與 `~/.omnikit/status/*/NOW.md` 活躍專案定位。
5. **硬上限截斷**：每次僅取分數最高的 **最多 3 項** 進入第 2 段深挖（其餘僅列標題在備選區，不展開）。

### 第 2 段：一手原始碼與反例深挖（主力 Coding Agent）
對選出的最多 3 項標的，嚴格要求：
1. **一手實測數據**：所有星數、授權、最後 push、最新 release 必經本機 `gh api` 查證並標註日期；禁止抄貼文或二手摘要數字。
2. **必看實際原始碼**：檢查關鍵檔案（如 `SKILL.md`、MCP tool schema、`package.json`／`pyproject.toml`、核心邏輯），禁止只看 README 行銷文案下結論。
3. **強制反例與邊界**：每一項至少寫出 1 條具體缺點、Windows／本機環境相容性限制或社群反例。
4. **強制改判條件**：明確寫出「什麼可檢驗的未來事實出現時，應該推翻今天的結論」。

## 強制五選一處置（嚴禁建立 `pending` 墳場）

每項深挖標的結案時，必須歸入下列 5 種處置之一，**不允許以「再觀察看看／待決定（pending）」含糊帶過**：

1. **`adopt_or_integrate`（直接導入／改接）**：確認外部方案已成熟且免我方重造輪子，列出最小改接步驟或開立待辦。
2. **`steal_pattern`（借鏡設計模式）**：不整包換掉，但明確點出要借鏡的具體規格／做法與落點檔案。
3. **`replace_or_retire`（取代／退役自家方案）**：確認我方既有實作過重或維護成本過高，提出減法／退役計畫。
4. **`watch_with_trigger`（帶改判條件的觀望）**：暫不改動，但寫死明確可檢驗的觸發門檻（例如「支援 Windows 原生沙盒」或「發佈 v2.0 正式版」）。
5. **`dismiss_with_evidence`（附證據排除）**：證實不適合或弱於現任，記錄拒絕證據（必要時透過 `record_decision.py` 寫入名冊防日後重複踩坑）。

## 防迎合與記憶隔離守則

- **記憶隔離**：每週排程與跨家盲審對話一律開在 `No project`（中性目錄），避免記憶系統把上週或主線的既有立場提前注入造成迎合。
- **反順從原則**：使用者丟出特定專案即時詢問時，**不得假設使用者想導入該專案**；必須先站在「維持現狀是否更好」的對立立場找反例，再平衡給出五選一建議。
- **重大架構改動升級**：若範圍 C 檢視得出「需要推翻核心架構或更換主路線」的結論，不可直接開工，必須啟動 OmniKit 兩階段防迎合盲審（Stage 1 零錨定獨立設計 → Stage 2 正面對決＋改判條件）並由異家同級模型審查。
