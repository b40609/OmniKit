# PRD 品質審查：OmniKit v2（同事版）

- **審查對象**：`docs/v2/prd/prd.md`、`docs/v2/prd/addendum.md`（2026-11-05 草稿）
- **對照輸入**：`docs/v2/brief/brief.md`、`docs/v2/research.md`、`docs/v2/brief/.memlog.md`、`docs/v2/prd/.memlog.md`；另抽查 repo 現有程式與名冊資料，確認 brownfield 引用
- **依據**：BMAD v6.12.4 `bmad-prd/assets/prd-validation-checklist.md`（rubric walker）
- **嚴格度**：內部工具、3 到 5 人試點。不要求市場分析、商業模式、合規與正式核准流程；但「完成定義」與「成功指標」照常嚴格，因為 §7 第 3 階段的試點檢討完全靠它們。
- **嚴重度統計**：critical 0、high 6、medium 14、low 11

## 整體判定（Overall verdict）

骨架扎實：論點清楚（「只留證明有用的，而且三個 agent 一致」），詞彙表、FR-1 到 FR-34 連號、非目標、假設索引都到位，多數 FR 的可測結果可以直接寫成測試，對內部試點來說堪用。風險集中在「怎麼證明論點成立」這一層：SM-2 在 4 週試點內量不完、SM-3 對沒裝過工具的同事方向相反、E4 的「贏」沒有定義，而且「在你的情境實測」是誰的情境沒有交代。另外 MVP 與 FR 有幾處互相矛盾（FR-20、FR-27、UJ-3），現有訪談第 5 題選「先不要」會讓同事收不到週報；這些應在進入設計與實作前修正。

## 1. 決策可行性（Decision-readiness）— adequate

決策大多以決策的語氣寫出，而不是「考量」：FR-5 依狀態決定勾選方式、FR-16 的 E0 到 E4 通知規則、§5 的非目標都可以直接執行。取捨有交代放棄了什麼：addendum B 列出 8 個沒採用的方案與原因，例如 SearchPlugins 做法「花 token、佔 context；依據是目錄而不是實測」。§6.2 的 `[NOTE FOR PM]` 放在真正的張力上（使用者明確要求的功能被延後），§10 的 7 個待解問題也都是真的未知，不是自問自答。

不足有三處：第 3 階段要做的關鍵決定（是否打開主動建議提示）沒有判斷標準；最明顯的反對意見在 brief 與研究裡有，PRD 卻沒回應；待解問題沒有標出哪些會擋住試點。

### 發現

- **[medium]** 打開主動建議提示的門檻沒有定義（§6.2、§7 第 3 階段、FR-21）— §6.2 寫「等靜默記錄兩週、確認誤報率之後」，§7 第 3 階段要「決定是否打開主動建議的提示」，但沒有誤報率門檻。FR-21「靜默期結束時，週報列出各規則的預估誤報率」也沒定義什麼算誤報：靜默期不顯示任何東西，沒有使用者回應可以當基準。結果是第 3 階段無從決定，使用者明確要求的功能可能無限期延後。另外 FR-21「某條訊號規則顯示 10 次以上都沒人接受，就自動停用」在單人本機的條件下幾乎碰不到：FR-19 限每週 3 則、同一工具每 3 個 session 最多 1 次、累計 5 次沒回應就全部靜音。*修法：* 定義誤報（例如：靜默命中後，同一 session 使用者已自行用了同類工具；或維護者在週報抽樣標記「不該提」），寫出門檻，例如「每條規則誤報率 <= 30% 才打開，其餘維持靜默」並標 `[ASSUMPTION]`；FR-21 的 10 次門檻註明是單人還是全隊（全隊要等 FR-31）。
- **[low]** 主要反對意見沒有在 PRD 回應（§1）— brief 自己寫「『一份設定接多個 agent』不是護城河……屬於執行面的優勢」（brief.md:46），研究也指出 Claude Code 已有「14 天而且 10 個 session 都沒用」的原生瘦身（research.md:21）。PRD 願景只說「同類工具比的是安裝數或自家套件」，讀者自然會問「Claude Code 已經會提示沒在用，FR-13 到 FR-15 的價值在哪」，PRD 沒答。*修法：* §1 加一段「平台已經做到什麼；OmniKit 的差異只在跨三個 agent，以及有實測證據的替換」，直接引用研究結論。
- **[low]** 待解問題沒有標出哪些會擋住試點（§10）— 第 2 題（回流管道）影響 MVP 內的 FR-29 與成功指標的資料來源；第 7 題（試點同事是誰、用哪些 agent）決定第 2 階段能不能開始；第 1 題影響 FR-26。都沒有負責人或期限。*修法：* 每題加註「擋住哪個階段、誰決定、最晚何時」，至少分出「試點前必須定」與「邊做邊定」。

## 2. 實質大於形式（Substance over theater）— adequate

願景不是可以套進別份 PRD 的空話：「只留證明有用的，而且三個 agent 一致」與「在使用者自己的工作情境裡實測贏不贏」（prd.md:26）具體到可以被否證。人物只有阿哲（加上維護者 Ryan），而且真的推動了決定：他做產線資料分析，所以有 FR-6 的資料分析槽位；防毒擋下的例外對應 FR-5 的「不會裝」；他選的痛點驅動 FR-12 的第一次成功。§9.4 的非功能需求是這個產品特有的（PowerShell 5.1 與 7、cp950、長路徑、防毒鎖檔），不是「要安全、要可靠」的樣板。

形式化的地方集中在反向指標，以及 UJ-4 對維護者工作量的描述。

### 發現

- **[medium]** 反向指標有兩個是擺設，一個沒有方向（§8 SM-C1 到 SM-C3）— SM-C2「每人每週最多 1 則」是把 FR-16 的上限重講一次，不是要觀察的指標，而且跟 FR-19「每週最多 3 則」的主動建議分不清是否合計。SM-C3「換回率」已經包含在 SM-2 的定義裡（「30 天內沒換回來」），SM-2 高時 SM-C3 必然低，起不了平衡作用。SM-C1 同時說「不能靠少裝」又說「不能為了看起來豐富而多裝」，沒有方向也沒有警戒值。*修法：* SM-C1 改成「每位同事選的痛點中，有對應工具或內建功能的比例 >= X%」（防止靠少裝衝 SM-1）；SM-C2 改成「收到通知後回『不要』或靜音的比例」；SM-C3 改成「接受替換後，同一情境的檢查點通過數下降的次數」。
- **[low]** UJ-4「他只需要做兩件事」低估維護者負擔（§2.3 UJ-4，prd.md:74）— 除了盲選與勾選排程，FR-22 要維護者勾選比對不明確的 url，FR-30 要審核同事提案並回覆，FR-29、FR-31 要彙整回流資料。這正是 §11「維護者成為瓶頸」的來源，UJ 卻寫成只要兩件事。*修法：* 改成列出每週固定工作與估計時間，並連到 §11 的風險。

## 3. 策略一致性（Strategic coherence）— thin

論點明確，功能也確實圍著它轉：有證據才裝（FR-5、FR-8）→ 沒在用就建議拿掉（FR-13 到 FR-15）→ 實測勝出才通知替換（FR-16、FR-17）→ 評估漏斗供應證據（FR-22 到 FR-27）。§6.1「內容先行」的排序來自論點，不是「哪個先做比較容易」。

問題在驗證論點的那一層。三個主要指標中，SM-2 在規劃的試點時間內量不完，SM-3 對主要人物的基準方向相反，SM-1 量不到 MCP 類工具；論點的核心句「在使用者自己的工作情境裡實測」也沒有任何 FR 交代是誰的情境。使用者明確要求的主動建議則完全沒有指標。

| 指標 | 驗證的 FR | 反向指標 | 問題 |
|---|---|---|---|
| SM-1 裝了的工具有在用 | FR-5、FR-13 到 FR-15 | SM-C1 | 量不到 MCP；分母沒定義 |
| SM-2 接受換工具的建議 | FR-16、FR-17、FR-25 | SM-C2、SM-C3 | 試點內量不完；樣本太小；SM-C3 已含在定義裡 |
| SM-3 token 用量下降 | FR-5、FR-15 | 無 | 新手的基準方向相反；沒有品質的反向指標 |
| SM-4 評估產能 | FR-22 到 FR-26 | 無 | 57 張與 §7 解凍衝突；「處理完」沒定義 |
| （無） | FR-18 到 FR-21 | 無 | 使用者明確要求的主動建議沒有任何指標 |

### 發現

- **[high]** SM-2 在試點時程內量不出來（§7、§8 SM-2、UJ-2）— 試點 4 週加檢討 1 週，共約 35 天；SM-2 要「同事接受、而且 30 天內沒換回來」，所以建議必須在試點前 5 天內送出才可能量完。但 UJ-2 自己寫「一個月後」才收到第一則替換建議；E4 要靠第 0 階段的評估漏斗產生（6 到 8 週，跟開發同時進行）；FR-16 又限每人每週 1 則。3 到 5 人的試點，替換建議可能只有 0 到 5 則，「50% 以上」沒有統計意義。第 3 階段「量 SM-1 到 SM-3」對 SM-2 必然交白卷。*修法：* 擇一寫進 §7：(a) 試點延長到至少 8 週；(b) SM-2 的觀察窗改成跟 FR-16 的兩週試用一致（14 天）；(c) 樣本不足時改報絕對數字（送出 N 則、接受 M 則、換回 K 則），並寫明至少幾則才計算比例。「4 週」本身也要標 `[ASSUMPTION]`（見第 5 節）。
- **[high]** SM-3 對沒裝過工具的同事方向相反（§8 SM-3、UJ-1）— SM-3 要「對話開頭的設定負擔與每段對話的 token 比安裝前少 20% 以上」，依據是 Ryan 這台 Codex 原本載入 112 個 skill 的實測（brief addendum B）。但主要人物阿哲「沒研究過 agent 工具」（prd.md:50），安裝前幾乎沒有負擔；OmniKit 裝進 4 個工具與受管區塊之後，開頭的 token 只會增加。照現在的定義，SM-3 對主要人物必然失敗，只對已經裝了一堆的同事有意義。「同樣的試點情境」也沒定義是哪個情境、誰量、怎麼量。此外 SM-3 沒有反向指標：拿掉有用的工具同樣能讓 token 下降。*修法：* 分兩組：原本已有工具的同事量「安裝前後下降 >= 20%」；原本沒裝的同事量「OmniKit 增加的每回合 context 成本 <= N tokens」（用 FR-8 預覽的數字）。指定量測情境（例如每人 profile 的第一個情境，跑 3 次取中位數）。加一個反向指標：同一情境的檢查點通過數不能下降。
- **[high]** 「在你的情境實測」是誰的情境，沒有交代（§1、UJ-2、§3「情境」、FR-25、FR-29）— 願景說「OmniKit 比的是在使用者自己的工作情境裡實測贏不贏」，UJ-2 的通知寫「X 在你的情境實測勝過 Y」。但實測在維護者端（§4.7 標題「維護者端」），受 FR-26 的每週額度限制；FR-25「執行用使用者實際使用的模型與 agent」也沒說是哪位使用者。同事的情境寫在自己的 profile（現有設計見 engine/skills/omnikit-setup/SKILL.md:82），而 FR-29 明訂回流不含專案名稱與路徑，情境到不了維護者手上；也沒有任何 FR 讓評估在同事自己的電腦上用他的情境跑。結果是核心主張與 UJ-2 的訊息可能不實：同事收到的「你的情境」其實是維護者的情境。*修法：* 決定並寫進 §3 與 FR-25。試點期若用「團隊共用情境」（由維護者依同事的工作整理、去掉專案名稱），通知文字就改成「在團隊情境實測勝過」；若要做到個人情境，新增一條 FR（同事在本機用自己的情境跑，結果透過 FR-30 提案回流），並把 token 成本寫進 §9.3。還沒決定就列進 §10，並標 `[ASSUMPTION]`。
- **[medium]** SM-1 量不到 MCP 類工具，分母也沒定義（§8 SM-1、FR-13）— SM-1 量的是「OmniKit 裝的工具」，但 FR-13 只統計「skill 與 plugin」，現有的 engine/scripts/usage.py:5 也是。名冊裡真正要安裝的 4 個預設之一 rea 是 MCP（data/tools/rea.yaml:3 `kind: mcp`、:6 `status: default`），試用中的 chrome-devtools-mcp 也是（data/tools/chrome-devtools-mcp.yaml:3）。另外，試點中途被 FR-15 停用的工具算不算分母？寫進規則的內建功能算不算？*修法：* FR-13 補上 MCP 的使用統計，或 SM-1 明寫只算 skill 與 plugin；分母定義為「安裝當下 lock 裡需要安裝的工具，中途停用的仍計入」。
- **[medium]** SM-4 的數字與 §7 解凍衝突，「處理完」也沒定義（§8 SM-4、§7 第 0 階段）— SM-4 寫「非凍結的 57 張工具卡在 8 週內處理完」。57 張是兩個凍結槽位都不動時的數字（實際核對名冊：待評估 104 張，排除只屬於凍結槽位的之後是 57 張）；§7 第 0 階段要「解凍『規劃與開發流程』槽位」，解凍後非凍結的待評估卡片會變成 72 張。「處理完」是指走到第 0 層有結論、還是每張都有預設、試用、拒絕的決定？SM-4 也沒有反向指標，最快的達標方式是在第 0、1 層大量排除。*修法：* 改成「解凍後的 72 張（或明列範圍）在 8 週內都有第 1 層結論」之類可數的定義；加反向指標，例如「E4 判定後在試用期退步的比例」；SM-4 本身是 coach 加的，要標 `[ASSUMPTION]`（見第 5 節）。
- **[medium]** 使用者要求的「像 Claude Code 一樣主動建議，而且做得更好」沒有成為可檢核的標準（§4.6、§8）— 這是使用者的明確決定（brief .memlog.md:14）。研究 §4 列了 Claude Code 的 5 個限制（依目錄不依實測、只看自己、只加不換、公司環境門檻高、由模型搜尋花 token），PRD §4.6 採用了對應的設計，卻沒寫出「比 Claude Code 好」要好在哪、怎麼驗；§8 也沒有指標涵蓋 FR-18 到 FR-21。加上 MVP 不顯示提示、FR-20 也一起延後（見第 5 節），試點期間同事在工作中得到的建議比 Claude Code 原生的還少。*修法：* §4.6 加一組「相較 Claude Code 原生建議」的可測結果：三個 agent 共用靜音（FR-19）、每則附實測證據位置（FR-18）、會提出替換而不只新增、比對不花模型 token；§8 加 v2.1 指標（例如提示接受率 >= X%、靜音率 <= Y%），標 `[ASSUMPTION]`。
- **[low]** MVP 幾乎等於全部功能（§6.1）— 34 條 FR 有 30 條全部或部分在 MVP（見附錄 B），維護者只有一人，第 0 與第 1 階段同時進行，卻沒有 MVP 內的優先順序，也沒說時間不夠時先砍什麼。*修法：* §6.1 分出「試點開始前必須完成」與「試點期間補上」兩組，例如 FR-22 到 FR-26 只要求先跑完訪談會用到的槽位。
- **[low]** 「三個 agent 一致」沒有可驗的定義（§1）— 核心主張的後半句沒有對應的可測結果；FR-10、FR-19 各涵蓋一部分，但沒有「列出同一工具在三個 agent 狀態不一致之處」這類檢查。*修法：* 在 FR-7 的檢查模式或 FR-11 的 doctor 加一條：回報同一工具在三個 agent 的安裝與停用狀態不一致。

## 4. 完成定義清晰度（Done-ness clarity）— adequate

多數 FR 的可測結果寫得好：FR-7「實際設定與計畫不一致時回報非零的結束代碼」、FR-10「同名但不是 OmniKit 的 skill 或 MCP，不刪除也不覆蓋」、FR-17「換回之後，設定與替換前一致（依帳本比對）」、FR-19 的頻率數字、FR-32「超過 24,000 bytes 時，預覽會提出警告」，都可以直接寫成測試。模糊的地方集中在評估漏斗（也就是 MVP「內容先行」的核心）與幾個新功能。FR 混入實作細節的情況不嚴重，多半同時寫了可觀察的結果。

### 發現

- **[high]** E4 的勝出規則沒有定義「贏」與「明顯」（FR-25，prd.md:434；addendum A.6）— FR-25 寫「3 次配對至少贏 2 次、成本沒有明顯變差」，但沒說一次配對怎樣算「贏」，「明顯」也沒有界線。addendum A.6 自己的模擬顯示：兩個一樣好的工具，用「總分高就算贏」跑 3 次，有 41% 會誤判挑戰者勝出；改成「平均每次多 1 個檢查點才算贏」降到 13%（addendum.md:76）。E4 是「只留證明有用的」的閘門（FR-16 只有 E4 會主動通知），這條寫不清楚，論點就站不住。*修法：* 把勝出條件寫進 FR-25 的可測結果，例如「挑戰者平均每次比現任多通過至少 1 個客觀檢查點，而且 3 次中至少 2 次不輸；每回合 context 成本與總 token 增加不超過 10%」，數字不確定就標 `[ASSUMPTION]`。
- **[medium]** 第一次設定的確認次數與順序互相矛盾（§4.2、FR-4、FR-8、UJ-1）— §4.2 說答完之後「最後只多問一題：照建議裝，或逐項調整」；FR-4 說「最多 6 題加上 1 次確認」；FR-8 說預覽「只確認一次，預設為『否』」；FR-4 又要求「建議的選項放第一個並標明『（建議）』」。UJ-1 的順序是先「看預覽」再「選『照建議裝』」。讀者無法判斷「照建議裝」是預覽的確認（那預設就不會是「否」），還是預覽之前的另一題（那就是 6 題、1 題、再 1 次確認）。這是 UJ-1 的主流程，UX 設計會直接卡住。*修法：* 寫出唯一順序，例如「6 題 → 組工具包 → 預覽 → 一題三選：照建議裝（建議）、逐項調整、先不要」，並刪掉「預設為否」，或註明它只適用於非互動模式。
- **[medium]** 一批可測結果用了沒有界線的詞（FR-2、FR-6、FR-12、FR-13、FR-22、FR-23、FR-27、FR-31、FR-34）—

## 5. 範圍誠實度（Scope honesty）— adequate

§5 非目標做了實事：「不讓 LLM 直接寫設定檔」「不建雲端服務或帳號系統」會直接擋掉下游的延伸。§6.2 每項延後都有理由，`[NOTE FOR PM]` 放在使用者明確要求卻被延後的功能上，正是該放的位置。假設有標、有索引；數量（10 個行內 `[ASSUMPTION]`、2 個 `[NOTE FOR PM]`、7 個待解問題）對內部試點來說合理，不構成阻擋。

問題是幾處靜默的範圍調整：MVP 與 FR 之間互相矛盾，還有幾個 PRD 自己加的決定沒有標記。

### 發現

- **[high]** MVP 範圍與 FR 互相矛盾（§6.1、§6.2、FR-18、FR-20、FR-27、UJ-3、§11）—
  - FR-20（使用者明確詢問）放在 §6.2 延後，理由是「等靜默記錄兩週、確認誤報率」，但明確詢問不會打擾人，也沒有誤報問題。同時 FR-18 最後一點「Antigravity 第一階段只在週報與使用者明確詢問時建議」、§11「第一階段只用週報與明確詢問」都假設 FR-20 在第一階段可用。§6.2 的 `[NOTE FOR PM]` 只講「提示顯示」，沒有講明連明確詢問也一起延後。
  - FR-27 前半（勝出工具進兩週試用、通過才轉預設）不在 §6.1；§6.2 只延後「FR-27 的後半」。但 MVP 內的 FR-16（E4 →「建議進兩週試用」）要靠它。
  - UJ-3 整段在 MVP 不會發生，卻沒有標成 v2.1，下游可能照它做 MVP 的 UX。

- **[medium]** 幾個 PRD 自己加的決定沒有標 `[ASSUMPTION]`（§7、§8 SM-4、FR-5、FR-29）—
  - §7 第 0 階段「照研究建議解凍『規劃與開發流程』槽位」：brief .memlog.md:27 記的是「建議……（待使用者決定）」，PRD 寫成定案。

## 6. 下游可用性（Downstream usability）— adequate

這份 PRD 要交給後續的設計與實作（§0），下游可用性的要求中等。基礎都在：詞彙表 24 個詞；FR-1 到 FR-34、UJ-1 到 UJ-4、SM-1 到 SM-4、SM-C1 到 SM-C3 都連號且唯一；「第 10 節第 N 題」「FR-7 到 FR-11」等交叉引用都對得上；每個 UJ 都有具名人物。問題是同一個詞指不同東西，下游拆 story 時會拆錯。「週報」的兩種讀者混用見第 7 節的 high 發現。

### 發現

- **[medium]** 同一個詞指不同東西：試用、煙霧測試、實測（§3、FR-11、FR-12、FR-16、FR-24、FR-28、§10、§11）—
  - 「試用」三種意思：工具卡狀態（§3）、同事端的兩週試用期（FR-16、UJ-2）、「試用提示」（FR-11、FR-12、FR-28，其實是工具卡的 `try` 上手提示）。FR-12「每張預設與試用的工具卡，都有一句試用提示」讀起來像繞口令。
  - 「煙霧測試」兩個功能：FR-11 是同事裝完後在自己電腦上的選配驗證；FR-24 是維護者端第 1c 層在隔離環境的候選測試。
  - 「實測」詞彙表定義為第 2 層，但 §10 第 5、6 題「（要實測）」、§11「記錄每項是哪天在哪台實測的」、addendum A.4「2026-11-04 實測」指的是平台行為驗證。E3「OmniKit 初測」也沒定義（研究的「資格賽」沒帶進來）。

  *修法：* 「試用提示」改名為「上手提示」；FR-11 改稱「裝後試跑」，「煙霧測試」只留給 FR-24；平台行為驗證改稱「平台驗證」；詞彙表補上「初測」。
- **[medium]** 「通知、主動通知、主動建議、建議」沒有分清楚，上限是否合計也不明（§3、FR-16、FR-19、SM-2、SM-C2）— 詞彙表只定義「主動建議」（工作中、本機比對）。FR-16 的「主動通知」（E4 替換）沒有定義；FR-16 上限每人每週 1 則，FR-19 是「全部合計每天最多 1 則、每週最多 3 則」，兩者共用額度還是各算各的？SM-2 的「換工具的建議」指的是 FR-16 的通知，SM-C2 的「通知次數」又算哪一種？同事每週最多被打擾 1 次還是 4 次，答案不同。*修法：* 詞彙表加「替換通知」（FR-16），跟「主動建議」（FR-18）並列對照；FR-19 寫明「全部合計」是否包含替換通知；SM-2、SM-C2 改用定義過的詞。
- **[low]** 「痛點」三種意思，「工具」沒有定義（FR-12、FR-18、FR-26、§3）— FR-12 的痛點是訪談第 2 題的答案；FR-18 的「痛點訊號」是從工作紀錄抽出的訊號；FR-26 公式裡的「痛點」是槽位層級的缺口（研究的「槽位沒有現任、或現任沒解決問題」，research.md:185）。「工具」本身也沒定義，而名冊的類型有 skill、plugin、mcp、cli、app、service、collection、native 等，這直接影響 FR-13 與 SM-1 要算哪些。*修法：* 詞彙表加「痛點」（只指第 2 題），FR-26 改稱「槽位缺口」；加「工具」的定義，列出 v2 支援安裝的類型。
- **[low]** §4.4「只留有用的」對應錯 UJ（§4.4 說明，prd.md:262）— §4.4 寫「對應 UJ-2」，但 UJ-2 是替換流程；論點的前半「只留有用的」（週報建議停用 → 同意 → 停用 → 可以還原）沒有任何 UJ。*修法：* 改成不對應 UJ，或補一個一句話的 UJ（阿哲在週報看到 2 個工具 14 天沒用，同意停用，之後用一句話還原）。

## 7. 形狀適配（Shape fit）— adequate

形狀大致合適：內部工具、兩種角色（試點同事、維護者），用能力規格的寫法，UJ 只有 4 個而且後三個是精簡版，符合 BMAD 對內部工具的建議。篇幅偏長（主文約 660 行，BMAD 對內部工具的建議約 5 到 8 頁），主要來自 FR-22 到 FR-28 的評估方法細節。

### 發現

- **[high]** 現有訪談第 5 題選「先不要」會讓同事收不到週報，PRD 沒處理（FR-4、§3「週報」、FR-7、FR-14 到 FR-16、FR-21、UJ-4）— FR-4 寫「訪談沿用現有的 6 題」。現有第 5 題選「先不要」就「不裝評估工具的 skill，也沒有每週彙整」（engine/skills/omnikit-setup/SKILL.md:46；engine/scripts/profiles.py:60；週報腳本本身就在 omnikit-eval 裡，engine/skills/omnikit-eval/scripts/digest.py:8）。但 v2 對同事的回饋幾乎都走週報：停用建議（FR-15）、E2 與 E3（FR-16）、上游新版（FR-14）、建議接受率（FR-21）、設定被手動改過（FR-7）。「不想自己研究工具」的同事（brief 的主要對象）很可能選「先不要」，結果「只留有用的」對他們完全不運作。此外詞彙表「週報：每週彙整，供使用者與維護者閱讀」把兩種讀者混在一起：UJ-4 的第 0 層排除、第 1 層候選、「值得實測的外部證據」（也就是 FR-16 的 E2）是維護者的內容，對同事沒有意義。*修法：* 拆成「個人週報」（每位同事都有，不依賴 omnikit-eval）與「維護者週報」（UJ-4）；第 5 題改成只決定「要不要參與評估」；FR-16 寫明 E2 進維護者週報，E3 與停用建議進個人週報。
- **[low]** 沒有「現況與差距」，既有的評估資產沒被引用（§0、§4.7）— omnikit-eval 已經有第 0 層腳本（engine/skills/omnikit-eval/scripts/layer0.py）、同槽位比對（peers.py），以及第 1、2 層的資料格式（contracts/layer1.schema.json、layer2-request.schema.json、layer2-result.schema.json），FR-22 到 FR-25 讀起來卻像全部新做。FR-13 的「（已於 2026-11-05 完成）」是主文唯一標出現況的地方。*修法：* §0 或 addendum 加一張「已有、要擴充、要新做」的表，避免下游重造。
