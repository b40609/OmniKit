## 1. 願景

同事裝好 OmniKit、回答幾個問題之後，就有一套適合自己的 agent 工具，而且每一個都有證據支持。之後 OmniKit 會持續幫他把關：沒在用的建議拿掉，有更好的選擇時通知、一鍵換。工作中遇到某類任務，它會在恰當的時候提醒有更合適的工具。

核心主張是：**不是幫你裝更多，而是只留證明有用的，而且三個 agent 一致。** 同類工具比的是安裝數或自家套件；OmniKit 比的是在真實工作情境裡實測贏不贏。試點期用的是團隊情境，之後才開放用自己的情境。

## 2. 目標使用者

### 2.1 要完成的工作

- **試點同事**：
  - 不用自己研究工具，就能用上適合自己工作的工具。
  - 知道每個工具為什麼裝、裝在哪、怎麼關。
  - 設定不會越裝越亂，也不會拖慢 agent；更新不會在不知情的情況下改變設定。
  - 有人主動告訴他「這個更好」，而且說得出理由。
- **維護者**：
  - 用可負擔的成本，讓名冊各槽位的預設工具都經過實測。
  - 從同事的使用資料知道哪些工具真的有用。

### 2.2 v2.0 不服務的對象

想自己大量安裝、自己比較工具的重度玩家。他們可以直接用名冊，但 v2.0 不為他們設計流程。平台與 agent 的邊界見第 5 節。

### 2.3 主要使用情境

- **UJ-1. 阿哲第一次裝 OmniKit，二十分鐘內用上第一個工具。**
  - **人物**：阿哲是做產線資料分析的工程師，用 Codex 與 Claude Code，沒研究過 agent 工具。
  - **開始時**：安裝前檢查通過，跑完 install，agent 提示「說『幫我設定 OmniKit』」。
  - **過程**：
    1. 同意做環境掃描：OmniKit 判斷這台的顯示卡可以跑小型本機模型。
    2. 勾選要掃描的專案，OmniKit 看到 `*.ipynb` 與 pandas。
    3. 回答 6 題需求問題，大多只要確認掃描的結果。
    4. 看預覽：每個工具都附理由與實測證據，也列出會寫到哪些檔、每回合大約多少 token。
    5. 選「照建議裝」。
  - **關鍵時刻**：OmniKit 依阿哲選的痛點「改完沒驗證就說好了」，在專案的新分支上用唯讀方式實際跑一次審查工具。阿哲看到它抓出一個漏測的地方。
  - **結束時**：OmniKit 列出還要做的事：開新 session、在 Codex 信任 hook。
  - **例外**：某個工具被防毒擋下時，預覽會把它列在「不會裝」並說明原因，其他工具照常安裝。
- **UJ-2. 阿哲收到「有更好的選擇」，換了工具也不擔心。**
  - 三週後，session 開頭出現一行通知：「前端設計：X 在團隊情境的實測勝過 Y（3 次配對中，平均每次多通過 1.7 個檢查點），要換嗎？」
  - 阿哲說「套用本週建議」。OmniKit 給同樣格式的預覽，確認後替換，並寫明試用到哪一天、怎麼換回來。
- **UJ-3. 工作中，OmniKit 在對的時候提醒一次。**
  - 阿哲這週有 3 個 session，都是改完前端就說完成、沒開瀏覽器驗證。
  - 回合結束時出現一則主動建議，說明為什麼是現在、為什麼推薦這個工具、成本多少，以及怎麼裝或叫它不要再提。
  - 阿哲說「不要再建議」，三個 agent 都不會再提這件事。
- **UJ-4. 維護者每週看一次維護者週報，就把名冊顧好。**
  - Ryan 打開維護者週報，看到這些區塊：
    - 第 0 層自動排除的工具與原因；
    - 第 1 層留下的候選；
    - 值得實測的外部證據；
    - 同事回流的使用統計與提案。
  - 他只需要做兩件事：在品味題上盲選；勾選要排實測的工具。

## 3. 詞彙表

**名冊與評估**

- **名冊**：所有工具卡的集合（`data/tools/*.yaml`），是推薦的唯一來源。
- **工具卡**：一個工具一張。記錄狀態、所屬槽位、理由、證據，以及 v2 新增的欄位（FR-28）。
- **狀態**：工具卡的狀態，共五種：預設、試用、待評估、拒絕、退役。
- **槽位**：一種需求，例如前端設計、審查與驗收。每個槽位配一到數個情境，最多一個預設工具。
- **槽位的評估重點**：
  - active：主動找更好的工具。
  - watch：有新工具才看。
  - 凍結：暫停評估、不動預設。
- **情境**：真實會遇到的工作，用來當評估的題目。
- **團隊情境**：維護者依試點同事的工作整理、去掉專案名稱與路徑的情境。試點期的實測都用團隊情境。
- **內建功能**：agent 本身就有、不用另外裝的能力（卡片 id 以 native- 開頭）。
- **現任**：槽位目前的預設工具；沒有預設時，用內建功能當基準。
- **挑戰者**：跟現任比較的候選工具。
- **評估漏斗**：第 0 層到第 3 層的評估流程。前面幾層只負責排除與排序；要不要換工具，只看第 2 層實測。
- **實測**：第 2 層，用情境比較現任與挑戰者。
- **品味題**：沒有客觀對錯、要看人偏好的題目，例如介面設計。
- **盲選**：品味題由人在不知道是哪個工具的情況下選出較好的結果。
- **證據等級**：
  - E0：熱門度。
  - E1：主張。
  - E2：外部可信證據。
  - E3：OmniKit 初測，指通過煙霧測試，並在資格賽贏過現任。
  - E4：OmniKit 實測勝出。

**安裝與設定**

- **工具包**：依訪談答案與專案訊號，從名冊即時組出的一組工具；不手工維護。
- **profile**：使用者個人的規則與情境。
- **安全底線**：所有人都套用的規則（`data/rules/baseline.md`）；profile 只能更嚴，不能放寬。
- **計畫**：一次安裝、更新或移除要做的所有動作，用 JSON 表示。預覽、安裝與移除都讀同一份計畫。
- **帳本**：OmniKit 寫入過的每個項目與它的雜湊，用來判斷使用者有沒有改過。
- **受管區塊**：OmniKit 在使用者的設定檔裡管理的一段內容；區塊以外的內容不動。
- **lock**：已安裝工具包的紀錄。記錄每個工具由哪一題答案、哪個槽位、哪張卡選上，以及上游版本與內容雜湊。
- **同步層**：把規則、skills、MCP 接到三個 agent 的程式（`agents.py`、`profiles.py` 等）。
- **更新檢查**：同事明確要求時，才取得維護者的名冊更新，並產生預覽。

**通知與回饋**

- **通知**：有更好的選擇或安全事件時，在 session 開頭顯示的一行訊息（FR-16）。
- **主動建議**：工作中由本機比對訊號後，在回合結束時顯示的一則工具建議（FR-18）。
- **訊號**：從專案或工作過程中抽出的線索，例如讀了 `vite.config.ts`，或同一個 session 出現 3 次超長的指令輸出。
- **個人週報**：每位同事都有的每週彙整，列出沒在用、有新版、有更好的選擇、主動建議的統計。
- **維護者週報**：給維護者看的每週彙整，內容是評估漏斗的結果與回流資料。
- **回流**：同事同意後，把去識別的使用統計與評估結果匯出給維護者。

**人與版本**

- **試點同事**：v2.0 試點期的 3 到 5 位使用者。
- **維護者**：維護名冊與評估的人，目前是 Ryan。
- **v2.0**：這份 PRD 的 MVP，給試點期使用。
- **v2.1**：試點之後才做的項目（§6.2）。
- **試點期**：§7 的第 2 階段。

## 4. 功能

### 4.1 安裝與環境掃描

**說明**：同事 clone 下來執行安裝就好，不需要 fork，也不需要設 GitHub Actions 或 Pages。安裝前先檢查，裝不了的先講清楚原因。安裝後可以選擇做環境掃描與專案掃描。掃描結果只留在本機，只拿來預選與排序，不會隱藏任何選項。對應 UJ-1。

#### FR-35：安裝前檢查（新增）

安裝之前，OmniKit 先檢查安裝本身需要的條件，失敗時說明原因與處理方式，不會裝到一半才失敗。

**可測的結果**：

- 檢查項目：git、連得到 GitHub、npm、PyPI、proxy 設定、防毒產品、PowerShell 執行原則。
- 任一項不通過，就不寫入任何設定，並列出處理方式。
- 檢查結果只有名稱與通過與否，不上傳。

#### FR-1：免 fork 安裝

試點同事可以只用 clone 加上執行安裝，就完成安裝。對應 UJ-1。

**可測的結果**：

- 沒有 GitHub 帳號、沒有 fork，也能完成安裝與訪談。
- 看板、Actions 與 Pages 是選配；沒有設定，也不影響推薦與安裝。
- 同事版不設定 git hook，所以 `git pull` 不會自動改變任何設定（見 FR-36）。

#### FR-38：個人資料存在 repo 外（新增）

同事的 profile、訪談答案與情境，存在 repo 以外的本機位置，不會被 commit 或 push。

**可測的結果**：

- 在 repo 裡跑 `git status`，看不到任何同事的個人檔案。
- 維護者自己的 profile 維持現狀，不受影響。

#### FR-2：環境掃描（可選）

使用者同意之後，OmniKit 只收集會改變推薦或安裝方式的欄位。對應 UJ-1。

**可測的結果**：

- 收集每個 agent 實際使用的設定位置與來源，例如預設值或環境變數。
- 收集以下環境條件：
  - 能不能建立連結（需要管理員權限或開發人員模式）、長路徑支援；
  - 防毒產品名稱；
  - proxy 與 PowerShell 執行原則（只看名稱）；
  - Node、Python、uv、git 的版本。
- 硬體只用在兩件事：判斷本機模型的適配等級並附理由（依顯示卡型號、VRAM、記憶體），以及記錄環境方便除錯。
- 輸出只有名稱與數值，不含金鑰或個人資料，也不上傳。
- 使用者拒絕掃描時，訪談照常進行，掃描查不到的改用提問。

#### FR-3：專案掃描（可選）

使用者可以從三個 agent 用過的專案中勾選要掃描的。OmniKit 抽出訊號後對應到槽位，用來預選與排序。對應 UJ-1。

**可測的結果**：

- 沒勾選的專案不會被讀取。
- 每個預選都附一句理由，例如「因為 <專案> 有 <檔案>」。
- 掃描結果只影響排序與預選，不會讓任何選項消失。
- 每個偵測器都有自我測試，包含「不應該命中」的案例。

### 4.2 訪談與工具包

**說明**：訪談沿用現有的 6 題需求問題，掃描查得到的只請使用者確認。答完之後，OmniKit 依答案與專案訊號從名冊組出工具包，最後只多問一題：照建議裝，或逐項調整。對應 UJ-1。

#### FR-4：訪談

使用者回答最多 6 題需求問題，就完成需求確認。對應 UJ-1。

**可測的結果**：

- 掃描已經知道的，題目會預先帶入，使用者只需確認。
- 建議的選項放第一個並標明「（建議）」。
- 全程的互動不超過 10 次。計算方式：掃描同意、專案勾選、6 題、工具包確認、profile 名稱確認、預覽確認。
- 重新設定時，會帶入上次的答案。
- 第 5 題只決定要不要參與評估。不管怎麼答，都會收到個人週報（FR-37）。

#### FR-5：自動組出工具包

OmniKit 依「答案與專案訊號 → 槽位 → 名冊」組出工具包。名冊一改，下次組出的工具包就跟著變。對應 UJ-1。

**可測的結果**：

- 只有兩種工具會預先勾選：
  - 有 E3 以上證據的預設工具；
  - 內建功能。
- 其他工具的處理方式：
  - 沒有實測紀錄的預設工具：列成「維護者預設（尚未實測）」，不勾選。
  - 試用：列出，但不勾選。
  - 待評估：只在槽位沒有預設時，列成「社群推薦（未實測）」，也不勾選。
  - 拒絕、退役：不列出。
- 不相容這台 agent、不符合環境需求、或已知會被防毒擋下的工具，列在「不會裝」並附原因。
- 已經裝了的另外列出，不重複推薦。內建功能不安裝，改寫進規則。
- 第一次最多預先勾選 5 個需要安裝的工具。`[ASSUMPTION: 上限 5 個]`
- 每一項都附三個欄位：
  - 理由：取自工具卡。
  - 證據：評估紀錄的位置。
  - 選上的原因：由哪題答案或哪個訊號選上。
- 同一個槽位有多個候選時，依序比較：實測結果 → 決定日期 → 外部訊號。

**不包含**：手工維護的工具包清單。

#### FR-6：補上缺的槽位與候選工具

名冊新增「資料分析」槽位，讓訪談第 1 題的每個選項都有對應的槽位。

**可測的結果**：

- 訪談的每個答案都對應到至少一個槽位。
- 「資料分析」槽位至少有一個情境，以及至少 2 張經過第 1 層的候選工具卡。目前名冊裡沒有任何資料分析、Jupyter 或 pandas 相關的卡片。
- 「本機模型」要不要另開槽位：先用評估漏斗找候選工具，有 E3 以上的候選再決定（§0.1 第 8 題，已定案）。

### 4.3 預覽、安裝與驗證

**說明**：寫入之前，使用者會看到一份預覽，內容來自計畫。預覽、安裝與移除都讀同一份計畫，避免「預覽說一套、安裝做另一套」。只確認一次。安裝時保護使用者的既有設定；裝完由 agent 自己的清單獨立驗證。對應 UJ-1、UJ-2。

#### FR-7：單一計畫

預覽、安裝與移除都依同一份計畫執行。對應 UJ-1、UJ-2。

**可測的結果**：

- 計畫只記錄受管項目（MCP entry、受管區塊、skill 複製品）的雜湊，不記整個檔案。agent 自己會持續寫入的檔案（例如 `~/.claude.json`），只要受管項目沒變，就不會誤判成「被改過」。
- 預覽之後受管項目有變動，安裝會停下來，要求重新預覽。
- 有檢查模式：實際設定與計畫不一致時，回報非零的結束代碼，讓個人週報能發現「設定被手動改過」。
- 移除也能先預覽。

#### FR-8：預覽內容

每個工具在預覽中列出以下內容：

- 類型。
- 為什麼選它：槽位、理由、證據、由哪題答案選上。
- 狀態與證據等級。
- 會裝到哪些 agent、寫入哪些檔、會覆蓋什麼。
- 每回合的 context 成本。
- 能力揭露：會不會改原始碼、改寫指令、把對話送到外部、連網、寫紀錄、改權限。
- 遙測。
- 要不要免問核准：每個工具分開同意，不沿用維護者的設定。

預覽最後一次列出「要你做的事」。對應 UJ-1。

**可測的結果**：

- 只確認一次，預設為「否」。
- 「不會裝」的工具與原因列在同一份預覽。

#### FR-9：安裝

使用者確認之後，OmniKit 照計畫安裝；plugin 一律用各 agent 原生的安裝方式。對應 UJ-1。

**可測的結果**：

- 能安裝第三方工具卡上的 skill 與 MCP，依工具卡的安裝欄位執行。現有的同步層只會裝 OmniKit 自己的 skill，這是新的能力。
- 版本一律釘選並比對雜湊；任何版本變動都要使用者同意。
- 金鑰只記環境變數名稱，不收值、不印出。
- 衝突在產生計畫時就檢查；有衝突，整份計畫都不執行。
- 執行時個別失敗的項目，不會中斷其他項目；逐項顯示成功或失敗，最後給出重跑方式。
- 在非互動環境執行時，沒有明確同意的參數就不會寫入。

#### FR-10：保護既有設定

OmniKit 只動自己管理的內容。使用者改過的項目，或同名但不是 OmniKit 的項目，一律停下來問。

**可測的結果**：

- 三個 agent 的規則都用受管區塊。Codex 原有的規則在安裝後繼續生效，不只是留一份備份。
- 帳本記錄每個受管項目的雜湊。使用者改過的 MCP 參數或受管區塊內容，不會被悄悄改回。
- 同名但不是 OmniKit 的 skill 或 MCP，不刪除也不覆蓋。
- 更新 Codex 的 MCP 時，保留使用者的工具核准紀錄。
- 免問核准（例如 Claude Code 的 allow 規則、Codex 的自動核准）只在使用者於預覽中同意後才寫入。

#### FR-11：驗證

裝完之後，OmniKit 用三層確認工具真的可用。

**可測的結果**：

- **寫入檢查**：計畫中的每一項都已寫入，雜湊相符。
- **agent 自己的清單**：用各 agent 自己的工具清單確認工具已經啟用。
- **煙霧測試**（選配，會花 token，先問使用者）：用工具卡的試用提示跑一次，確認工具真的被叫到。
- doctor 指令逐項檢查上述內容。查不到的標「未知」，不當作通過。

#### FR-12：第一次成功

裝完之後，OmniKit 依使用者選的痛點挑 1 個工具，在他的真實專案上實際跑一次。對應 UJ-1。

**可測的結果**：

- 每張預設與試用的工具卡，都有一句試用提示。
- 跑之前先說明要做什麼；只用唯讀方式，或在新的分支、worktree 上跑；不 commit、不 push。
- 這一步可以跳過；跳過不影響安裝完成。

### 4.4 只留有用的與更新

**說明**：OmniKit 讀三個 agent 的本機紀錄，找出沒在用的工具，在個人週報中建議停用，使用者同意才執行。lock 讓 OmniKit 知道每個工具當初為什麼裝，使用者改了答案，就能拿掉不再需要的。名冊的更新也要先預覽、同意後才套用。對應 UJ-2。

#### FR-13：使用統計

OmniKit 統計三個 agent 中每個 skill 與 plugin 的實際使用情況，包含 Codex 的 plugin（已於 2026-11-05 完成）。

**可測的結果**：

- 「沒在用」的定義：14 天、而且 10 個 session 都沒用到。`[ASSUMPTION: 改成這個雙門檻]`
- 以下情況標成「未知」，不當成「沒在用」：
  - 紀錄解析失敗；
  - 工具的類型偵測不到使用紀錄，例如 MCP、CLI、hook、規則。
- 剛裝的、主題與輸出風格這類沒有叫用紀錄的，不判斷。
- 只輸出名稱、次數與日期，不含對話內容。

#### FR-37：個人週報（新增）

每位同事每週都有一份個人週報，跟訪談第 5 題的答案無關。

**可測的結果**：

- 內容依序是：
  1. 沒在用的工具；
  2. 上游有新版的工具；
  3. 有更好的選擇：E3 與 E4；
  4. 設定被手動改過的項目；
  5. 主動建議的接受率。
- 每週第一個 session 開頭顯示一行提示。完整內容存在本機，使用者說「OmniKit 本週週報」就會列出。
- 不連網也能產生。上游新版的部分，只在最近一次更新檢查時更新。

#### FR-14：工具包 lock

安裝之後，OmniKit 為每個工具寫入 lock：由哪一題答案、哪個槽位、哪張卡選上，以及上游版本、內容雜湊與安裝日期。

**可測的結果**：

- 使用者改了訪談答案，OmniKit 能列出因此不再需要的工具。
- 上游有新版時，個人週報能列出；任何版本變動都要使用者同意。
- lock 的格式升版時，舊資料會轉換，不會被清空。

#### FR-15：停用與移除

個人週報列出建議停用或移除的工具；使用者同意之後，OmniKit 用各 agent 支援的方式停用。

**可測的結果**：

- 沒有使用者同意，不停用也不刪除任何東西。
- 停用可以還原。
- Codex 跟帳號同步的 plugin，用 skill 名稱停用。

#### FR-36：更新要預覽、同意後才套用（新增）

維護者的名冊與程式更新，不會自動套用到同事的電腦。

**可測的結果**：

- 同事說「OmniKit 檢查更新」時才連網取得更新，並產生跟安裝一樣格式的預覽；同意後才套用。
- 每週提醒一次可以檢查更新（§0.1 第 2 題，已定案）。
- hook 的腳本內容有變動時，預覽會特別列出，並要求使用者重新信任（見 FR-39）。

### 4.5 有更好的選擇時通知

**說明**：只有 OmniKit 實測勝出（E4）時才主動通知，而且一次就好；E3 進個人週報，E2 只進維護者週報。使用者說「套用本週建議」，就走同一條預覽、確認、安裝、驗證的流程。對應 UJ-2。

#### FR-16：證據等級與通知規則

OmniKit 依證據等級決定通知方式。

**可測的結果**：

- E0、E1：不通知。
- E2：只進維護者週報，每週最多 3 則。
- E3：只進個人週報。
- E4：主動通知一次，建議進 14 天試用。
- 打平就維持現任，不通知。
- 主動通知每人每週最多 1 則。
- 同一個槽位判定之後，30 天內不再通知同一類工具，除非有新證據。
- 證據滿 90 天，或工具跨 minor 版本，就降一級。
- **例外**：現任或試用中的工具出現以下情況時，在下一次 session 開頭立即通知，不受每週上限限制：
  - 安全事件；
  - 被封存或轉移；
  - 授權變更；
  - 新版加了範圍過寬的 hook，或沒揭露的遙測。
  
  OmniKit 不常駐，所以「立即」最快是在下一次更新檢查之後的 session 開頭。`[ASSUMPTION]`
- 每則通知都附上：比較對象、用的是團隊情境、評估紀錄的位置、差距與執行次數、沒驗證到的部分、試用到期日。

#### FR-17：一鍵替換與換回

使用者可以用一句話套用建議；試用期間或結束後，也可以用一句話換回原本的工具。對應 UJ-2。

**可測的結果**：

- 替換走 FR-7 到 FR-11 的同一條流程。
- 換回時，OmniKit 寫入的項目依帳本還原；plugin 用各 agent 原生的解除安裝指令移除。換回後，各 agent 自己的工具清單與替換前一致。

### 4.6 工作中主動建議

**說明**：主動建議分兩層：

- 本機比對：被動，不花模型 token。
- 使用者明確詢問：才用到模型。

所有比對都在本機做，不把對話內容送出去。v2.0 先靜默記錄 2 週並請同事標註，誤報率夠低才打開提示。對應 UJ-3。

#### FR-18：本機比對

OmniKit 在回合結束或 session 開頭，用本機抽出的訊號比對名冊。符合條件時，最多顯示 1 則主動建議。

**可測的結果**：

- 只建議兩種工具：E4 的挑戰者，或有 E3 以上證據的預設工具；而且相容目前的 agent、還沒裝、也沒被拒絕過。試用中的工具只在使用者明確詢問時出現。
- 訊號只從使用者同意範圍內的對話紀錄抽取。`[ASSUMPTION: 跟專案掃描分開徵求同意]`
- 主動建議的格式固定：
  - 為什麼是現在：符合的訊號；
  - 為什麼是它：實測結果與證據位置；
  - 成本；
  - 怎麼裝，以及怎麼叫它不要再提。
- 每則主動建議都記在本機。使用者回「OmniKit 裝 X」或「不要再建議」時，負責處理的 skill 會讀這份紀錄，確認使用者回應的是哪一則。
- 痛點訊號要跨 2 個 session，或同一 session 出現 3 次，才算成立。
- Antigravity 在 v2.0 只在個人週報與使用者明確詢問時建議。`[ASSUMPTION: 要先實測使用者看不看得到 hook 訊息]`

#### FR-19：頻率與靜音

OmniKit 依統一的頻率規則決定要不要顯示，三個 agent 共用。對應 UJ-3。

**可測的結果**：

- 主動建議：每個 session 最多 1 則；每天最多 1 則；每週最多 3 則。
- 通知（FR-16）與主動建議合計，每週最多 3 則；安全類的例外不算在內。
- 同一個工具每 3 個 session 最多提 1 次。
- 設定完成後 7 天內不主動建議。
- 沒回應算「否」；累計 5 次就全部靜音，並告訴使用者怎麼重新打開。
- 「不要再建議」分三種範圍：單一工具、這個專案、全部；在任一個 agent 設定，三個 agent 都生效。
- 非互動執行、子 agent、CI 都不顯示。

#### FR-20：使用者明確詢問

使用者問「有沒有工具可以…」時，OmniKit 先查名冊，附理由回答，再走同一條安裝流程。

**可測的結果**：

- 預設只查名冊；外部目錄預設關閉，要使用者打開才查。
- 回答依實測結果排序，並標明每個候選的狀態與證據等級。

#### FR-21：建議的自我檢討

OmniKit 在本機記錄每則主動建議的顯示、接受、拒絕與沒回應，並自動停用沒效的規則。

**可測的結果**：

- 靜默期間只記錄、不顯示。靜默期結束時，把「本來會顯示的主動建議」列給同事標註有沒有用，算出各規則的誤報率。
- 標註為「有用」的比例達到 50% 以上，才打開提示（§0.1 第 5 題，已定案）。
- 個人週報列出主動建議的接受率。
- 某條訊號規則顯示 10 次以上都沒人接受，就自動停用，並在週報說明原因。

#### 比 Claude Code 更好的可測條件（適用 FR-18 到 FR-21）

**可測的結果**，對照 Claude Code 與 Codex 的原生建議：

- 每則主動建議都附評估紀錄的位置。原生建議只依目錄或訊號，沒有證據。
- 「不要再建議」在三個 agent 間共用。原生建議只在各自的 agent 內有效。
- 除了建議安裝，也會建議替換與停用。原生建議只建議安裝。
- 不花模型 token。原生建議由模型在對話中搜尋目錄。

### 4.7 評估漏斗（維護者端）

**說明**：補推薦內容靠評估漏斗：

- 第 0 層：腳本做身分與健康檢查。
- 第 1 層：便宜模型做情境對應、去重、比對內建功能。
- 第 1b 層：外部證據。
- 第 1c 層：煙霧測試。
- 第 2 層：情境實測。
- 第 3 層：試用與回歸。

前面幾層只負責排除與排序，要不要換工具只看第 2 層。預設假設工具「沒效果」，內建功能也算一個挑戰者。對應 UJ-4。

#### FR-22：第 0 層自動檢查

維護者可以一次對全部工具卡跑第 0 層。

**可測的結果**：

- 沒有 url 的工具卡會補出候選 repo；比對不明確的列進維護者週報，讓維護者勾選。
- 會淘汰的只有四種：
  - 已封存；
  - 確認惡意，或有未解決的高風險問題；
  - 授權不允許散布（要進 OmniKit marketplace 時）；
  - 跟 agent 不相容。
  
  其他一律只標記。
- 會加上四種旗標：
  - 冷卻期：建立不到 14 天。
  - 爆紅：近期星數成長速度是平均的 3 倍以上，而且建立不到 90 天。成長速度用 OmniKit 每週記錄的星數快照計算。
  - 停滯。
  - 未知：查不到資料。「未知」不當作通過。
- 星數與下載數只用來標記旗標與在同分時排序，不加分。

#### FR-23：第 1 層與外部證據

維護者可以用便宜模型批次處理第 1 層，並把外部證據整理成證據卡。

**可測的結果**：

- 每張卡記錄：
  - 對應的槽位與情境；
  - 可以查證的主張；
  - 是否已被內建功能涵蓋；
  - 所屬的相似群組。
- 證據卡有來源、日期與到期日；引用原文要短。
- 可以查證的負面證據，會讓工具被排除或往後排；正面證據只會提高排序。

#### FR-24：第 1c 層煙霧測試

候選工具在隔離環境中安裝，並跑一次縮小版的情境。

**可測的結果**：

- 隔離環境：獨立的使用者設定資料夾與 worktree。需要 shell 權限的套件，在 Windows Sandbox 或 WSL2 裡跑。`[ASSUMPTION: 要實測哪一種可行]`
- 記錄四件事：
  - 裝不裝得起來；
  - 有沒有被叫用；
  - Claude Code 與 Codex 的非互動模式能不能跑；
  - 每回合的 context 成本。
- 有 hook、MCP 或可執行程式的工具，另外做程式碼審查。

#### FR-25：第 2 層實測規則

每次實測比較一個槽位的「現任加最多 2 個挑戰者」，用團隊情境與同一套素材，勝出規則事先寫好。

**可測的結果**：

- 客觀檢查點每組至少跑 3 次，做配對分析。
- 勝出要同時符合三個條件：
  - 挑戰者平均每次比現任多通過至少 1 個客觀檢查點；
  - 3 次中至少 2 次不輸；
  - 每回合的 context 成本與總 token 增加不超過 10%。`[ASSUMPTION: 10%]`
  
  不符合就維持現任。
- 分開記錄「沒被叫用」與「叫用了但沒幫助」。
- 純提示型的 skill，加一組長度相同的對照。
- 品味題由維護者盲選；評分用跟執行不同家族的模型。
- 執行用試點同事實際使用的模型與 agent；便宜模型的結果不能拿來決定勝負。
- 每組都在乾淨的環境執行。

#### FR-26：排程與額度

OmniKit 依優先序排實測，並分開計算兩種額度。

**可測的結果**：

- 優先序 = 槽位權重 × 痛點 × 使用頻率 × 證據等級。
- 以下不排實測：凍結的槽位、冷卻期內的工具、停滯或未知的工具。
- 要維護者盲選的實測，每週最多 2 次。
- 不需要人參與的客觀實測，每週最多 2,000 萬 tokens，含快取讀取（§0.1 第 6 題，已定案）。用到上限後，其餘的實測排到下一週。

#### FR-27：第 3 層試用與回歸

勝出的工具先進 14 天試用；實測素材轉成回歸套件，在條件符合時重跑。

**可測的結果**：

- 試用期間有被叫用、沒有退步，才轉成預設。
- 工具大改版、模型升級，或平台出現重疊功能時，重跑該槽位的回歸套件。

#### FR-28：工具卡新欄位

工具卡新增以下欄位：

- 訊號：專案掃描與主動建議的比對條件。
- 環境需求。
- 已知阻擋：會被哪些防毒或政策擋下，附證據。
- 各 agent 的安裝方式與釘選版本，包含 Antigravity。
- 驗證方式。
- 試用提示。
- context 成本：由程式計算。
- 能力揭露。
- 替代品：由現有的取代關係反推。

**可測的結果**：

- 「適用的 agent」與安裝方式都支援 Antigravity；目前的 schema 只允許 Claude 與 Codex。
- 可以預先勾選的工具卡，必須有安裝方式、驗證方式與試用提示。
- 名冊驗證會檢查新欄位的格式。
- 由程式計算或反推的欄位不能手寫。

### 4.8 團隊回流

**說明**：同事同意之後，把去識別的使用統計與評估結果匯出給維護者；同事也能提案新工具或實測結果。這是「自我迭代」的資料來源，也讓評估可以分工。對應 UJ-4。

#### FR-29：同意制的去識別回流

試點同事可以選擇匯出回流資料，匯出前可以先預覽內容。

**可測的結果**：

- 內容只有工具 id、使用次數、評估結果、OmniKit 版本。
- 不含對話內容、專案名稱、路徑、帳號、patch 或截圖；匯出前自動去識別。
- 沒有同意就不匯出；同意可以隨時撤回。
- 匯出成本機檔案，由同事放到 Teams 試點頻道的檔案區，不走公開的 GitHub（§0.1 第 3 題，已定案）。頻道連結不寫進公開 repo。

#### FR-30：同事提案

試點同事可以用固定格式提交新工具，或某個工具的實測結果；維護者審核後才併入名冊。

**可測的結果**：

- 提案放在同一個 Teams 試點頻道。只含公開資訊的新工具提案，也可以用 GitHub issue。
- 提案會進入評估漏斗的第 0 層，不會直接改變任何人的工具包。
- 審核結果會回覆給提案人。

#### FR-31：回流資料進入排程

維護者端彙整回流資料，用在排程優先序的「使用頻率」，以及維護者週報的「團隊實際使用」區塊。`[ASSUMPTION: 依回報人數加權]`

**可測的結果**：

- 只有一個人回報的工具，不會讓優先序大幅變動。

### 4.9 同步層的修正

**說明**：研究與審查發現同步層有幾個缺陷，v2.0 要一起修。詳見 `docs/v2/research.md` §3 與 `review-adversarial.md`。

#### FR-32：位置偵測

OmniKit 依實際環境決定每個 agent 的設定位置，不寫死。

**可測的結果**：

- 有設 `CODEX_HOME`、`CLAUDE_CONFIG_DIR` 時，照它們決定位置。
- 偵測到 `AGENTS.override.md` 時提出警告，因為 Codex 會改讀它。
- Antigravity 的規則檔超過 24,000 bytes 時，預覽會提出警告。
- 每個位置都記錄是哪天、在哪台實測確認的。

#### FR-33：底線只能更嚴

名冊驗證會檢查 profile 有沒有放寬安全底線。

**可測的結果**：

- 結構化的項目（權限、MCP、hooks）由程式檢查；放寬底線的設定不能套用。這些項目預設拒絕，明確允許的才放行。
- 自然語言的規則：
  - 訪談產生的 profile，一律用固定範本，不會放寬底線；
  - 手寫的 profile，在預覽時提醒「底線優先，profile 裡放寬的寫法不會生效」。

#### FR-34：Windows 持續整合

CI 在 Windows 上跑所有自我測試與安裝預覽。

**可測的結果**：

- 測試範圍包含 PowerShell 5.1 與 7、長路徑與含空白的路徑。
- 中文語系用程式模擬 cp950 的輸出與檔名來測。CI 沒辦法改系統語系，所以真實的 cp950 環境改在試點同事的電腦上確認。
- 檔案被防毒短暫鎖住時，會重試，不會失敗。

#### FR-39：hook 的信任與效能（新增）

OmniKit 的 hook 要讓使用者知道它的內容何時改變，而且不能拖慢 agent。

**可測的結果**：

- 同事版的 hook 指令包含腳本內容的雜湊；腳本一改，Codex 就會要求重新信任。
- 單次 hook 執行的時間有上限，超時就放棄、安靜結束，不擋對話。`[ASSUMPTION: 一般 2 秒內、最多 8 秒，要在試點同事的電腦上實測]`
- 只讀新增的對話紀錄。

## 5. 非目標

- 不跟 skills.sh、aitmpl 比目錄規模。名冊只收經過篩選的工具。
- 不自己做 skill 安全掃描，直接採用既有掃描與 Snyk、Socket 的結果。
- 不在沒有使用者確認的情況下安裝、更新、停用或刪除任何東西。
- 不送遙測，也不在背景常駐或自動更新。
- 不讓 LLM 直接寫設定檔：寫入一律由腳本照計畫執行。
- 平台的內建功能足夠時，不推外掛。
- 不建雲端服務或帳號系統。
- 不支援 macOS 與 Linux；不支援 Claude Code、Codex、Antigravity 以外的 agent。

## 8. 成功指標

**主要指標**：

- **SM-1 裝了的工具有在用**：試點同事安裝 30 天後，OmniKit 裝的工具有 70% 以上在這 30 天內至少用過一次。使用紀錄是「未知」的工具不算進分母。驗證 FR-5、FR-13 到 FR-15。`[ASSUMPTION: 70%]`
- **SM-2 同事接受換工具的通知**：同事接受的通知中，在 14 天試用期內沒有換回來的，占 50% 以上。通知少於 5 則時，改報實際數字：送出幾則、接受幾則、換回幾則。驗證 FR-16、FR-17、FR-25。`[ASSUMPTION: 50%]`
- **SM-3 token 用量**：量測方式是，每位同事 profile 的第一個情境跑 3 次，取中位數。驗證 FR-5、FR-15。
  - 原本已經裝了工具的同事：對話開頭載入的設定與每段對話的 token，比安裝前少 20% 以上。
  - 原本沒裝的同事：OmniKit 增加的每回合 context 成本不超過 3,000 tokens。
  - `[ASSUMPTION: 20% 與 3,000 tokens]`

**次要指標**：

- **SM-4 評估產能**：非凍結槽位的 57 張工具卡，在第 0a 到 0b 階段（8 週內）處理完。驗證 FR-22 到 FR-26。`[ASSUMPTION: 8 週]`

**反向指標（不追求）**：

- **SM-C1 裝的工具數量**：數字變大不代表變好。用來平衡 SM-1：不能靠少裝來衝高使用率，也不能為了「看起來豐富」而多裝。
- **SM-C2 通知與主動建議的次數**：合計每人每週最多 3 則（FR-19）。用來平衡 SM-2：不能為了提高接受數而多發。
- **SM-C3 換回率**：用來平衡 SM-2；換回率太高，代表通知的品質差。
- **SM-C4 檢查點通過數**：SM-3 的同一個情境，檢查點的通過數不能下降。用來平衡 SM-3：不能靠拿掉有用的工具來省 token。

## 9. 限制與防護

### 9.1 安全

- 安全底線不能放寬，由程式檢查結構化的項目（FR-33）。
- 第三方的 hooks 與 MCP 預設不放行；免問核准要每個人自己同意（FR-10）。
- 版本一律釘選並比對雜湊；任何版本變動都要同意（FR-9、FR-14）。
- 更新與 hook 腳本的變動要預覽與重新信任（FR-36、FR-39）。
- 掃描器標出的嚴重問題只當成「要人工看」的觸發條件，不當判決。

### 9.2 隱私

- 所有掃描與比對都在本機做。
- 同事的個人資料存在 repo 以外（FR-38）。
- 回流要同意、匯出前可以預覽、自動去識別，而且不走公開的 GitHub（FR-29）。
- 外部目錄搜尋預設關閉；就算打開，也只送抽象的關鍵字，不含專案名稱與路徑。

### 9.3 成本

- 評估的客觀實測有每週 token 上限（FR-26）。
- 預覽顯示 context 成本；第一次最多預先勾選 5 個需要安裝的工具（FR-5、FR-8）。

### 9.4 共通的非功能需求

- Windows 11 優先：PowerShell 5.1 與 7、cp950、長路徑；檔案被防毒鎖住時要重試。
- 所有會寫入的步驟，都支援預覽並輸出 JSON；重跑結果一致。
- 除了使用者明確執行的步驟，不連網。
- hook 出錯或超時就安靜結束，不擋對話（FR-39）。

## 10. 風險與對策

| 風險 | 對策 |
|---|---|
| 評估的量能或 token 成本不夠 | 評估漏斗、每週 token 上限；便宜模型只用在前幾層 |
| 大多數 skill 沒有效果 | 預設假設「沒效果」；內建功能也是挑戰者；打平就維持現任；只預先勾選 E3 以上的工具 |
| 平台改版：路徑、hook、plugin 指令變了 | 位置偵測、doctor；記錄每項是哪天在哪台實測的；試點前在每位同事的電腦上重測 |
| Antigravity 的 hook 使用者看不到 | v2.0 只用個人週報與明確詢問 |
| 防毒擋下工具，或拖慢 hook | 安裝前檢查；工具卡記錄已知阻擋；hook 有時間上限 |
| hook 會在背景啟動沒有數位簽章的 uv | 這個問題 v2.0 還沒解決。試點前在同事的電腦上確認防毒的反應，並記錄結果 |
| 同事被通知打擾 | 頻率規則、自我檢討、先靜默記錄與標註 |
| 實測結果套不到同事身上 | 試點期明說用的是團隊情境；同事在本機用自己的情境評估，留到 v2.1 |
| 維護者成為瓶頸 | 同事提案、回流資料；前幾層自動化 |
