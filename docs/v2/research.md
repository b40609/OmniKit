# OmniKit v2 研究蒸餾：各家的優點、缺點，以及 OmniKit 怎麼整合

日期：2026-11-05　狀態：研究完成，待使用者確認

完整證據在 `research/` 底下：

- `research/sync.md`：「一份設定接多個 agent」，研究 7 個工具：rulesync、rulebook-ai、Ruler、skillshare、Agent OS、skills CLI、APM。
- `research/recommend.md`：「依需求推薦並安裝」與「工作中主動建議」，研究 ECC、setup-claude、find-skills、Codex、Tessl、aitmpl、BMAD、SuperClaude、Claude Code 官方，以及 VS Code、JetBrains 的先例。
- `research/eval.md`：評估怎麼規模化。

原始碼證據都標成 `repo path:line @ SHA`。

## 0. 結論

兩份獨立的研究得出同一個結論：

- 被研究的十幾個工具，只做到「同步」或「依熱門度推薦」。
- 沒有一家用使用者自己的工作情境決定推薦。
- 也沒有一家跨三個 agent 依使用紀錄汰除工具，並提出替代品。

這就是 OmniKit 的位置。但平台也在追：Claude Code 的 `/plugin` 已經會把「14 天而且 10 個 session 都沒用」的 plugin 列成 Not used recently，`/doctor` 也會建議停用。所以 OmniKit 的差異要放在兩處：

- **跨三個 agent**：一個地方看到 Claude Code、Codex、Antigravity 三邊的狀況。
- **有實測證據才建議替換**：「X 換成 Y，因為在團隊情境（之後是你自己的情境）Y 贏了，證據在這裡」，而不只是「X 沒在用」。

> 更正：`docs/proposals/2026-11-05-positioning.md` 描述的 ECC configure-ecc 是舊版 v1.10.0。現行的 v2.2.3（`b38be6a`）已改成只問 2 題、預覽後確認 1 次、交給各 agent 原生指令安裝，再用 agent 自己的清單驗證。

## 2. 流程每一步：採用誰的做法、補上什麼缺點

整體骨架照 ECC v2：腳本決定、agent 轉述；只確認一次；交給各 agent 原生指令安裝；用 agent 自己的清單獨立驗證。

| 步驟 | 做法 | 借自 | 補上各家的缺點 |
|---|---|---|---|
| 入口 | install 結束時提示「說『幫我設定 OmniKit』」；還沒建 profile 時，session 開頭再提示，最多 2 次 | Claude Code 的 session 開頭通知（合計 2 次就停） | — |
| 環境掃描（可選） | 硬體只用在兩件事：判斷能不能跑本機模型（顯示卡型號、VRAM、記憶體，VRAM 用 `nvidia-smi` 讀），以及記錄環境方便除錯。另外收集會改變安裝方式的欄位：管理員權限或開發人員模式、長路徑、防毒產品、proxy 與 PowerShell 執行原則、Node、Python、uv、git 的版本 | llm-checker、llmfit 的「適配等級加理由」 | 各家幾乎都不掃硬體；用 `Win32_VideoController` 讀 VRAM，超過 4GB 就會讀錯 |
| 專案掃描（可選） | 候選專案取自三個 agent 的本機紀錄，使用者勾選了才掃。偵測器寫成純函式並附測試。訊號格式沿用 Claude Code 的 `cwd`、`cli`、`hosts`、`filesRead`、`manifestDeps`，再加上 `files`。訊號只用來預選與排序，不隱藏任何選項，每個預選都附理由 | Claude Code relevance、JetBrains | aitmpl 的偵測條件寫錯，判斷 Django 與 Flask 的分支永遠不會成立 |
| 訪談 | 保留現有 6 題，掃描查得到的只請使用者確認；專案名稱改成從清單勾選；建議的選項放第一個。組完工具包只多問 1 題：「照建議裝（建議）／我要逐項調整」 | ECC v2（2 題加 1 次確認）、BMAD 的 Express 與 Customize | ECC v1 逐項多選，太煩 |
| 組工具包 | 答案與專案訊號 → 槽位 → 每個槽位到名冊取工具：<br>• 預設：勾選<br>• 試用：列出但不勾<br>• 待評估：只在槽位沒有預設時列成「社群推薦（未實測）」，也不勾<br>再過濾相容性（`works_with`、`requires`、`blocked_on`）；已經裝的另外列；內建功能寫進規則。第一次最多裝 5 個需要安裝的工具，並顯示 context 成本 | setup-claude（已裝的分開列、組織的優先、只挑 2 到 3 個）、Goose（同時啟用 5 個以下） | 各家都依熱門度或只推自家套件 |
| 預覽 | 一張表，每個工具列出：類型；為什麼選它（槽位、卡片理由、實測證據、由哪題答案選上）；狀態；裝到哪些 agent、寫哪些檔、會覆蓋什麼；context 成本；能力揭露（改原始碼、改寫指令、把對話送出去、連網、寫紀錄、改權限）；遙測；要你做的事。另外列「不會裝的」與原因。只確認一次，預設為否 | aitmpl 的寫入欄、ECC 的 6 類能力揭露、Vercel 的覆蓋提示、Claude Code 的 context 成本 | — |
| 安裝 | skills 與 MCP 沿用 `agents.py`；plugin 用各 agent 原生的指令（`claude plugin install`、`codex plugin add`）。版本釘選並比對雜湊；使用者改過的檔另存；金鑰只記環境變數名稱；逐項顯示成功或失敗，一項失敗不中斷整批；非互動模式一定要 `--yes` | ECC v2、BMAD 安裝器、aitmpl | ECC v1 讓 LLM 自己複製檔案；SuperClaude 的 dry-run 會印出金鑰 |
| 驗證 | 三層：<br>• 寫入檢查<br>• agent 自己的清單（`claude plugin list --json`、`codex plugin list --json`）<br>• 選配的煙霧測試：用卡片的 `try` 提示實際跑一次，確認工具真的被叫到<br>doctor 要真的檢查 | ECC v2、Claude Code plugin eval 的 `tool_used` | SuperClaude 與 aitmpl 的 doctor 檢查錯的東西 |
| 第一次成功 | 每張卡片加一句 `try` 提示；依使用者的痛點挑 1 個工具，在他的真實專案上跑一次；可以跳過 | Codex 目錄的 `default_prompts`、setup-claude 的 Try a skill | — |
| 之後 | 「沒在用」改成雙門檻：14 天而且 10 個 session 都沒用。「有新版」靠 lock 比對，每 24 小時最多查一次、可以關、跨大版本要同意。「有更好的」三種情況會通知：名冊換了預設、卡片有 `replaces`、同槽位的試用工具實測勝出。送達方式是週報，加上 session 開頭一行訊息（每週最多 1 次）；使用者說「套用本週建議」，就走同一條預覽流程 | Claude Code 的瘦身、rulesync 的 `--outdated`、Tessl 的替代品提示 | 各家只查同一個工具有沒有新版 |
| 回流 | 同事同意才送出；只送工具 id、使用次數、評估結果，送出前可以預覽內容；走 GitHub issue 或 PR，或共用資料夾 | — | skills.sh、aitmpl、Tessl 預設就送遙測 |

## 3. 同步層：OmniKit 現有要修的缺陷

| # | 現況 | 修法 | 核對 |
|---|---|---|---|
| 1 | Codex 規則整份換掉，同事原有的規則只剩備份；Claude 與 Antigravity 原有的規則照樣生效，三邊不一致 | 改成受管區塊 | 已核對 `profiles.py:189-203` |
| 2 | MCP 只比 OmniKit 自己設的欄位，不同就覆寫，使用者在 agent 裡改過的 args 會被改回；Antigravity 整個 entry 換掉；Codex 連子表格一起刪，工具核准紀錄可能跟著消失 | 帳本記每個受管項目的雜湊；被改過或同名衝突就停下來問 | 已核對 `agents.py:380-388`；子表格的部分是研究推論 |
| 3 | 受管區塊沒有雜湊，GEMINI.md 區塊裡的手改會被蓋掉 | 區塊標記帶內容雜湊 | 研究推論 |
| 4 | `install.ps1 -WhatIf` 與實際安裝是兩套判斷，只靠註解保持一致 | 改成共用 plan JSON，再加 `--check` | 研究已驗證（`install.ps1:93、349`） |
| 5 | `~/.codex` 寫死；`CODEX_HOME`、`CLAUDE_CONFIG_DIR`、`AGENTS.override.md` 都沒偵測；Antigravity 單一規則檔超過 24,000 bytes 會被截斷 | 位置由掃描偵測，加 doctor；預覽時計算 GEMINI.md 大小 | 研究已驗證 |
| 6 | CI 只跑 ubuntu，Windows 才會走到的程式（junction、唯讀屬性、硬連結）都沒測到 | 加 windows-latest：PowerShell 5.1 與 7、cp950 語系、長路徑 | 研究已驗證 |
| 7 | 移除沒有預覽，備份散在各檔旁邊 | 移除也讀 plan；還原紀錄集中存放 | 研究已驗證 |
| 8 | 「底線只能更嚴」只是文字約定 | 改成程式檢查 | 研究已驗證 |

**OmniKit 已經比各家好的地方（要保留）**：

- 只動自己的東西，同名的別人的工具一律不碰。
- 用手術的方式改 `config.toml`，讀不懂就不寫。
- Antigravity 的實測細節：skills 用複製、拿掉 BOM、保住硬連結。
- Claude 的 import 路徑轉成正斜線。
- 工具固定版本並比對 SHA256、不改 PATH。
- Codex hook 加在最後面，不代替使用者信任。
- 讀寫一律指定 UTF-8；能處理 Windows 唯讀屬性。
- 依使用紀錄瘦身、用自己的工作情境評估：七個同步工具都沒有。

## 4. 工作中主動建議：怎麼比 Claude Code 做得更好

**Claude Code 與 Codex 的限制**：

- 建議的依據是目錄、訊號或熱門度，不是「在你的工作上比較好」。
- 只看自己：Claude Code 不知道 Codex 裝了什麼，「不再建議」也不會跨 agent。
- 只加不換：會說「沒在用」，不會說「X 可以換成 Y，理由是…」。
- 公司環境門檻高：Claude Code 要 managed settings，Codex 要 ChatGPT 登入。
- 由模型在對話中搜尋，花 token 又佔 context。

**OmniKit 的兩層設計**：

1. **本機比對，被動，不花 token**：擴充現有的 Stop hook（`engine/scripts/session_nudge.py`，已經會讀 Claude Code 與 Codex 的對話紀錄）。
   - 流程：只讀新增的紀錄 → 抽出訊號 → 比對由名冊產生的訊號索引 → 經過頻率關卡 → 最多印 1 則訊息。
   - 訊息格式：「建議：X｜為什麼現在：<訊號>｜為什麼是它：<實測結果與證據檔>｜成本：<每回合約 N tokens>｜要裝就說『OmniKit 裝 X』；不想再收到就說『OmniKit 不要再建議 X』」。
2. **使用者明確詢問時，才用到模型**：新增一個 skill，在使用者問「有沒有工具可以…」時觸發。先查名冊並附理由，外部目錄預設不查；之後一律走同一條預覽、確認、安裝、驗證的流程。

**訊號**：

- 專案：讀了 `vite.config.ts`、package.json 有 react → 前端設計。
- 指令：跑了 docker、terraform → 依卡片。
- 痛點：
  - 單一指令輸出超過 2 萬字元，同一 session 3 次以上 → 指令輸出壓縮。
  - 改了前端檔案、沒開瀏覽器就回報完成 → 瀏覽器操作與驗證。
  - 一週內壓縮很多次 → 記憶與交接。
  - 使用者說「不是叫你改這個」 → 行為準則包。
- 痛點訊號要跨 2 個 session，或同一 session 出現 3 次才算。

**頻率控制**：

| 規則 | 設定 |
|---|---|
| 每個 session | 最多 1 則 |
| 全部合計 | 每天 1 則、每週 3 則 |
| 同一個工具 | 每 3 個 session 最多 1 次 |
| 寬限期 | 設定完成後 7 天內不主動建議 |
| 沒回應 | 算「否」；累計 5 次就全部靜音，並告訴使用者怎麼重新打開 |
| 不再建議 | 分三種範圍：單一工具、這個專案、全部；三個 agent 共用 |
| 不提示的時機 | 非互動執行、子 agent、CI |
| 主動提的門檻 | 只主動提實測勝出的工具；沒實測的只在使用者詢問時出現 |

依據是 Claude Code、VS Code、JetBrains 的規則（`recommend.md` §5.7）。

**自我檢討**：

- 每則建議的顯示、接受、拒絕與沒回應都記在本機，列進週報。
- 某條訊號規則顯示 10 次以上都沒人接受，就自動停用。
- 第一版先**靜默記錄兩週**，看誤報率，再打開提示。

**隱私**：

- 所有比對都在本機做，不把對話內容送出去。
- 從建議發起的安裝，一律要使用者確認。

## 5. 評估規模化：104 張不用等一年

**研究結論**（詳見 `research/eval.md`）：

1. **星數、fork、安裝數在這個生態幾乎沒有鑑別力。**
   - 名冊 50 個 repo 的星數中位數是 31,000，41 個超過 1 萬。現在「少於 50 星就警告」的規則只擋到 1 個。
   - StarScout（ICSE 2026）估計 2019 到 2024 年約有 600 萬顆疑似假星。
   - fork 與星數的比值，中位數只有 0.093。
2. **skill 平均效果小，而且不穩定。**
   - SWE-Skills-Bench：98 個軟體工程 skill 裡，92 個沒有統計上顯著的效果。
   - 網頁開發 skill 平均讓通過率下降 1.3% 到 4.2%，token 增加 72% 到 394%，而且效果換了模型就不一定成立。
   - 自己生成的 skill 比沒裝還差 8.1 到 11.5 個百分點（SkillsBench）。
   - 所以預設要假設「沒效果」，挑戰者得證明自己比現任或原生功能好。
3. **沒有任何目錄判斷「對這個使用者好不好」。** 它們只看身分、安全與熱門度。最接近的是 `claude plugin eval` 與 Tessl 的「有裝與沒裝」比較，但題目都不是你的情境。

**回答你的三個問題：**

- **可以先參考網路上的心得與影片嗎？** 可以，但只拿來排除與排序。
  - 一則可以查證的負面證據，例如不支援 Windows、非互動模式不能用，就能把工具排後面或排除。
  - 正面心得最多讓工具早一點進實測，不能跳過實測：效果綁在模型、harness 與專案上，別人的結果很難套到你的環境。
  - 影片只透過官方 API 取資訊，不批次抓字幕，以免違反條款。
- **同功能分不出好壞時，可以用星數、fork 排序嗎？** 可以，但放在最後。打平時依序比：相容性 → 成本 → 風險與權限 → 健康度 → 採用度；都分不出來就維持現任。星數只用來標記兩件事：
  - 爆紅：近期星數成長速度是平均的 3 倍以上，而且建立不到 90 天，就延後一輪再看。
  - 冷卻期：建立不到 14 天，可以先做書面篩選，但不排實測。
- **同類競品怎麼解決？** 它們不判斷好不好，只判斷安全不安全、熱不熱門：
  - skills.sh 用安裝數排名，加上 Snyk 與 Socket 的稽核。
  - Tessl 用結構評分，加上作者自己出題的「有裝與沒裝」比較。
  - 官方 marketplace 審核身分與政策。
  - awesome 清單靠人工策展，加 14 天冷卻期。
  
  OmniKit 的前幾層借用它們的做法（身分、安全、冷卻），最後一層用它們都沒有的：你的工作情境實測。

**評估漏斗**：

| 層 | 做什麼 | 誰做 | 成本 | 進下一層的門檻 |
|---|---|---|---|---|
| 0 身分與健康 | 補 url（49 張沒有）、去重；查封存、授權、所有權轉移、相容線索、既有的安全掃描；算健康與採用度指標 | 腳本 | 0 token；50 個 repo 約 2 分鐘 | 只有已封存、確認惡意或有未解決的高風險問題、授權不允許散布、跟 agent 不相容會淘汰；其他只標記 |
| 1 情境對應、去重、比原生 | 讀 README 與 SKILL.md；對應槽位與情境；列出可以查證的主張；比對原生功能；相似的工具分群，每群挑 1 到 2 個代表 | 便宜模型 | 每張 1 萬到 2.5 萬 token | 對得上 active 槽位的情境、提供現任沒有的能力、沒被原生功能涵蓋、不是群裡較弱的 |
| 1b 外部證據 | GitHub issues、HN、dev.to、影片資訊、基準論文、registry 分數，整理成有到期日的證據卡 | 腳本抓資料，便宜模型整理 | 每個 2 萬到 5 萬 token | 可查證的負面證據：排除或往後排；正面證據只提高排序 |
| 1c 煙霧測試 | 在隔離環境安裝，跑縮小版情境：裝得起來、會被叫用、Claude Code 與 Codex 的非互動模式都能跑；量 context 成本；有 hook、MCP 或程式的，再審程式碼 | 腳本加便宜模型；審程式碼用強模型 | 每個 agent 約 12 萬到 25 萬 token | 全部通過，而且不在冷卻期 |
| 2 情境實測 | 每個槽位一次比「現任加最多 2 個挑戰者」，共用同一套素材；客觀檢查點每組跑 3 次並做配對分析，勝出門檻事先寫好；記錄有沒有被叫用；純提示型的 skill 加一組長度相同的對照；牽涉品味的題目由你盲選 | 用你實際用的模型執行；評分用不同家族的模型 | 客觀短題每次 12 萬到 25 萬 token；重題每次 300 萬到 400 萬 token | 見下面的通知門檻 |
| 3 試用與回歸 | 兩週試用，看有沒有被叫用、有沒有退步；實測素材轉成回歸套件，工具改版、模型升級、平台出現重疊功能時重跑 | 腳本；你只在週報確認 | 每次 100 萬 token 以內 | 試用期間有被叫用、沒有退步，才轉成預設 |

**實測的排程**：

- 優先序 = 槽位權重（active 1、watch 0.3）× 痛點（槽位沒有現任、或現任沒解決問題的最高）× 使用頻率 × 證據等級。
- 這取代現在「依待評估張數排序」的做法。

**估算**（推論；前兩週跑完後，用實際的通過率校正）：

| 部分 | 張數 | 實測次數 | 時間 | token |
|---|---|---|---|---|
| active、watch、未分配的槽位 | 57 | 7 到 12 次 | 6 到 8 週 | 約 3,000 萬到 1.9 億，九成以上是快取 |
| 原本凍結的兩個槽位 | 47 | 3 到 5 次重題 | 再 2 到 3 週 | 約 3,000 萬到 1.5 億 |

- 這兩個槽位照第 9 節解凍，不用等 RIA。
- 對照：照現在每週 2 次、一次評一個工具，要約 52 週。
- 你的時間：盲選約 2 到 5 次，其他只需要在週報勾選。

**額度改法**：把 `eval.weekly_deep_limit: 2` 拆成兩種：

- 要你盲選的：每週最多 2 次。
- 不需要你參與的客觀實測：改用每週 token 上限。

拆開之後約 4 到 5 週可以跑完，不拆是 6 到 8 週。

**什麼時候通知「有更好的選擇」**：

| 證據等級 | 條件 | 怎麼通知 |
|---|---|---|
| E0 熱門度 | 星數、安裝數、下載數 | 不通知，只影響排序 |
| E1 主張 | README、廠商比較文、單一心得或影片 | 不通知，寫進卡片 notes |
| E2 外部可信證據 | 至少 2 個獨立來源、90 天內、版本相符、測的是同類任務 | 週報的「值得實測」，每週最多 3 則 |
| E3 OmniKit 初測 | 通過煙霧測試，並在資格賽贏過現任 | 週報的「建議排實測」 |
| E4 OmniKit 實測勝出 | 照事先寫好的規則勝出：3 次配對至少贏 2 次、成本沒有明顯變差、沒有風險旗標；或你盲選選中 | 主動通知一次，建議進兩週試用 |

- 打平就維持現任，不通知。
- 主動通知每週最多 1 則；同一個槽位判定後，30 天內不再通知同一類工具；相似的工具只通知代表；證據滿 90 天或工具跨 minor 版本，就降一級。
- **例外，立即通知**：現任或試用中的工具出現安全事件、被封存或轉移、授權變更、新版加了範圍過寬的 hook 或沒揭露的遙測。

**評估要避開的坑**：

- 把熱門度當品質；被爆紅的新專案帶著走。
- 把掃描器的嚴重度當判決：OmniKit 自己標過的高風險問題，人工看過全是誤判。
- 用通用評測代替你的情境。
- 只跑一次就下結論：兩個一樣好的工具，用「總分高就贏」的規則，有 35% 到 43% 的機率誤判挑戰者勝出。
- 用便宜模型的結果代表你實際用的模型。
- 試驗之間互相污染：每組都要用乾淨的 HOME 與 worktree。
- 忘了把原生功能也當成一個挑戰者。

## 6. 各家共同的缺點，以及 OmniKit 怎麼補

| 共同缺點 | OmniKit 的補法 |
|---|---|
| 只管同步，不管該不該裝；沒有依使用汰除，也沒有依情境替換 | 名冊、評估、使用統計，加上工具包 lock：每週列出「沒在用」「上游有新版」「同槽位有更好的」，使用者同意才換 |
| 推薦看熱門度或只推自家套件 | 實測優先，外部訊號只在同分時排先後 |
| 動到使用者的既有設定很粗糙：整份覆寫、同名就刪、MCP 整個 key 換掉 | 受管區塊加雜湊、帳本、有衝突就停 |
| Windows 是次要平台 | Windows CI、檔案鎖重試、cp950 測試 |
| 預設連網、送遙測、在背景更新，在公司環境容易被防毒或 proxy 擋下 | 不送遙測；只在使用者明確執行的步驟連網；不常駐背景 |
| 第三方內容的信任交給使用者自己判斷 | 名冊評估加上安全掃描；第三方的 hooks 與 MCP 預設不放行 |
| 平台的主動建議只看自己、只加不換 | 跨三個 agent、帶實測證據的替換建議 |

## 7. 要避開的坑

- 依熱門度排序推薦。
- 讓模型手動複製檔案。
- 掃描結果、查詢字串或遙測離開這台電腦。
- 印出 API key。
- 不會真的檢查東西的 doctor。
- 不釘版本。

- 對 Antigravity 用連結：它讀不到。

## 9. RIA 與 BMAD

查證結果：「RIA 是半成品」這個判斷大致成立。研究流程能用，但產品方向還在調整，對照實驗也還沒顯示增益。完整的查證報告含未發佈的內容，不放在這個公開 repo。

另外，整包拿 RIA 跟 BMAD 比並不對等：BMAD 是 30 個 skill 的開發方法框架，RIA 是單一研究 skill。

建議：

- **規劃與開發流程**：拿掉 RIA，現在就解凍。用 V1 情境比 BMAD、spec-kit、compound-engineering，以 agent 原生流程當基準。
- **產品研究與方向**：預設維持 BMAD（deep-recon），RIA 維持待評估。要再比的話：
  - 用你真實專案的需求當題目，提示裡不提醒「先查」；
  - 四組一起比：原生、search-first、BMAD deep-recon、固定版本的 RIA；
  - 執行與評分用不同家族的模型。
- **RIA 要先補的**：增益證據與停止條件、主動觸發、單一正式版本（commit、push、打 tag）、Claude Code 也能用、日常用的輕量模式。

2026-11-05 已定案：「規劃與開發流程」槽位解凍，RIA 不再當這兩個槽位的比較基準。
