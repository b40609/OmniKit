## 摘要

OmniKit v2 讓同事裝完就有一套適合自己、而且有證據支持的 agent 工具。流程是：可選的硬體與專案掃描，加上一段短訪談，依名冊（OmniKit 收錄的所有工具卡，是推薦的唯一來源）裡實測過的結果自動組出工具包，預覽之後安裝到 Claude Code、Codex 與 Antigravity。

裝完之後，它會持續做兩件事：清掉沒在用的工具，以及在有更好的選擇時通知使用者，讓使用者感覺有人一直在幫他顧設定。核心主張是：**不是幫你裝更多，而是只留證明有用的，而且三個 agent 一致。**

為什麼是現在：agent 工具每週都有新的，平台與目錄比的是誰裝得多，例如 skills.sh 依安裝數排名。但裝多了反而拖累 agent。2026-11-04 在維護者的電腦上實測，停用 Codex 沒在用的 skill 之後，同一個問題的 token 少了約 27%。

## 問題

- **同事不知道該裝什麼**：工具太多，評價只能靠星數與口碑；裝了也不知道有沒有用。
- **大家現在的做法**：照網路推薦一次裝一堆，或乾脆什麼都不裝；裝了之後沒有人回頭清理。
- **裝太多是有成本的**：agent 每段對話開頭都要載入整份 skill 清單。維護者電腦上的 Codex 原本載入 112 個 skill，光是清單就有 49,335 字元，實際用到的只有十幾個。
- **現在的 OmniKit 解決不了**：
  - 訪談只會產生規則，不會裝工具。
  - 名冊 116 張卡片中，預設（槽位推薦的工具）只有 11 張，其中 7 張是 agent 內建功能。
  - 104 張待評估，每週只能深度評估 2 個；預設工具也不會自動安裝。
  - 所以同事裝完會覺得很陽春。

## 解法

1. **一鍵安裝**：clone 下來直接跑 install，不用 fork。安裝前先檢查網路、proxy 與防毒，裝不了的會先說明原因。
2. **可選的掃描**：
   - 硬體：判斷能不能跑本機模型（GPU、VRAM），並記錄環境，方便出問題時除錯。
   - 專案：看主要語言與框架。
3. **訪談確認需求**：答案對應到槽位（一類需求，例如前端設計、審查與驗收），再用各槽位的預設工具自動組出工具包。名冊一改，工具包就跟著變。
4. **預覽後安裝**：每個工具都附理由與證據，使用者確認後才裝進三個 agent。第一次就用使用者的痛點實際跑一次，讓他看到效果。
5. **持續只留有用的**：
   - 每位同事都有自己的週報：列出 14 天、而且 10 個 session 都沒用到的工具，建議停用，同意後才執行。
   - 名冊裡有挑戰者（跟現任比較的候選工具）在團隊整理的真實工作情境中實測勝過現任（槽位目前的預設工具）時，通知並提供一鍵換。
   - 工作中遇到某類任務、而名冊有實測更好的工具時，主動建議，並控制頻率不打擾。
   - 名冊更新不會自動套用到同事電腦，一律先預覽、同意後才套用。
6. **團隊一起變好**：同事同意才把去識別的使用統計與評估結果匯出到非公開的共用資料夾 [ASSUMPTION]；同事也能提案新工具或實測結果，由維護者審核後併入名冊。

## 跟別人不一樣的地方

- **推薦根據的是實測，不是熱門度**：每個推薦都來自用真實工作情境做的比較，並記下理由。試點期間用的是維護者整理的團隊情境；之後才會開放同事用自己的情境評估。
- **會主動清理**：讀三個 agent 的使用紀錄，找出沒在用的工具。在 2026-11-05 的研究範圍內，被研究的十幾個工具都沒有這樣做。
- **公司電腦也能安心用**：安全底線不能放寬，裝之前可以預覽，隨時能還原；防毒擋掉第三方同步工具也照樣能裝。
- **誠實地說**：「一份設定接多個 agent」不是護城河，rulesync 做得更完整；目錄規模也遠小於 skills.sh。真正的優勢是篩選與汰換的紀律，加上團隊的實際使用資料，屬於執行面的優勢，不是技術門檻。

## 服務對象

- **主要：身邊 3 到 5 位試點同事**。工研院工程師，用 Windows 11，至少用 Claude Code、Codex、Antigravity 其中一個。他們要的是裝完就好用，不想自己研究工具。成功的樣子是：不用研究就用上適合的工具，偶爾收到 OmniKit 說「這個更好，要換嗎？」
- **次要：維護者（Ryan）**。維護名冊與評估，從同事回流的資料看哪些工具真的有用。
- **v2.0 不服務的對象**：想自己大量安裝工具的重度玩家。平台與 agent 的邊界見「範圍」。

## 成功指標

- **SM-1 裝了的工具有在用**：試點同事安裝 30 天後，OmniKit 裝的工具有 70% 以上在這 30 天內至少用過一次。偵測不到使用紀錄的工具類型不算進分母。[ASSUMPTION: 70%]
- **SM-2 同事接受換工具的通知**：同事接受之後，在 14 天試用期內沒有換回來的，占 50% 以上。通知少於 5 則時，改報實際數字。[ASSUMPTION: 50%]
- **SM-3 token 用量**：
  - 原本已經裝了工具的同事：同一個情境下，對話開頭載入的設定（例如 skill 清單）與每段對話的 token，比安裝前少 20% 以上。
  - 原本沒裝的同事：OmniKit 增加的每回合成本不超過上限。
  - [ASSUMPTION: 20% 與上限的數字]
- **反向指標（不追求）**：
  - 裝的工具數量：數字變大不代表變好。
  - 通知與主動建議的次數：合計每人每週最多 3 則，不能為了提高 SM-2 而多發。[ASSUMPTION]
  - 換回率：太高代表通知的品質差。
  - 同一個情境的檢查點通過數不能下降：避免為了省 token 拿掉有用的工具。

## 範圍

**v2.0 包含**：「解法」第 1 到 6 點全部，再加上兩件事：

- 補推薦內容：訪談會用到的槽位都要有實測過的預設，並新增「資料分析」槽位與候選工具。
- 評估流程加速。

**v2.0 不包含**：

- macOS 與 Linux。
- Claude Code、Codex、Antigravity 以外的 agent。
- 自己做 skill 安全掃描（改為直接採用既有的掃描結果）。
- 雲端服務或帳號系統。

## 願景

兩三年後，OmniKit 是團隊共用的 agent 工具顧問：每個人的設定都是用團隊實測與使用資料挑出來的最小集合。新工具出現時，OmniKit 先替大家評估，有證據了才推到每個人的 agent。

## 主要風險

- **評估量能**：104 張待評估。研究建議改成評估漏斗：
  - 前幾層用腳本與便宜模型做排除與排序，只有實測能決定要不要換；
  - 估計 6 到 8 週可以處理完非凍結槽位（目前暫停評估的槽位以外）的 57 張；
  - 研究也顯示大多數 skill 沒有顯著效果，所以預設要假設「沒效果」。
  - 詳見 `docs/v2/research.md` §5。
- **主動建議的打擾程度**：
  - 由本機的 hook（agent 在特定時機自動執行的腳本）比對，每個 session 最多 1 則；
  - 只主動提實測勝出的工具；
  - v2.0 先靜默記錄 2 週，讓同事標註哪些建議有用，誤報率夠低才打開提示。
  - 詳見 `docs/v2/research.md` §4。
- **RIA 的定位**（RIA 是使用者自己開發的產品研究工具）：查證後，「RIA 是半成品」這個判斷大致成立，所以 RIA 先不當成比較基準（已定案，見文首），詳見 `docs/v2/research.md` §9。
