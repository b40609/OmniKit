# 決定之前要有可比對的成果：影子比對與其他缺口

日期：2026-11-14。狀態：提案，使用者已同意影子比對的方向，尚未實作。

## 結論

- 試用到期要使用者決定留下或換回，但畫面上只有工具名稱與到期日。補一個**影子比對**：試用期間記下真實任務，到期前用舊工具在副本重跑，讓使用者盲選。
- 盤點後，同一類缺口（要使用者決定，卻沒有可比對的成果）共 5 個高嚴重度、6 個中、4 個低。根源是同一個：**OmniKit 的證據停在維護者那一邊，沒有帶到使用者決定的那一刻**。
- 查到的工具沒有一個把「個人試用期間的真實任務」拿去重跑舊工具再盲選；最接近的是換模型的重播與「有無 skill」的比較。

## 起因

2026-11-14 前端設計槽位開始兩個 14 天試用（unslop、taste-skill）。使用者問：沒有畫面或具體成果可以比，怎麼知道要不要換回？三輪實測（`data/evals/2026-11-1[34]-frontend-design-F1*.md`）正好示範了有成果可比時的做法：副本、同一個要求、盲選、灰階與配色分開。

## 業界做法

讀的是搜尋摘要與官方頁面，沒有實測這些工具；多數是廠商與實務文章，不是嚴謹研究。

| 做法 | 怎麼運作 | 可以借的 | 限制 |
|---|---|---|---|
| 影子測試、冠軍與挑戰者 | 新舊版本吃同樣的輸入，只有舊版生效；順序是離線重播、影子並行、小流量 | 整個形狀；影子不能有副作用 | 推論成本約兩倍 |
| OrcaReplay | 錄下 coding agent 的執行，從檢查點分岔換模型再比 | 從真實任務的起點重跑 | 換的是模型不是工具；重播時工具呼叫是真的 |
| Arize 的 coding agent 追蹤 | 從真實操作收資料集，並排比較（例如有無某個 MCP） | 從真實使用收題目 | 要架追蹤 |
| Tessl、skill-ab-test、Skill Forge | 有 skill 對沒 skill（或對上一版），預設跑 3 次 | 基準與多次執行 | 題目是合成的，不是使用者的真實任務 |
| Design Arena | 設計類盲選兩兩比較，不打分數 | 跟三輪實測的做法一致 | 群眾的品味不是使用者的品味 |

三個警告：

1. **重播不等於原場景**（arXiv 2608.10319）：換了 skill，agent 的走法就不同，後續追問沒辦法照搬。所以只重跑「起點 commit 加第一個要求」，後面追加的修改比不到，紀錄裡寫明。
2. **影子不能有副作用**：只在副本跑，不動真的專案、不 push。
3. **差距要大於雜訊，而且不能自己評自己**：有實務文章量到自評把分數灌高 60 分。評審用不同家族的模型，品味題最後由使用者盲選。

## 影子比對

1. **記下真實任務**：試用期間，新工具被叫用的對話，從對話紀錄記下專案、開始前的 commit、使用者的第一個要求。只記在這台（`%LOCALAPPDATA%\omnikit\`），不進 repo、不回流。
2. **挑題**：到期前 3 天挑 2 到 3 筆（有乾淨的起點 commit、要求看得懂的）。不夠 2 筆就照實說「試用期間用得太少，沒辦法比」，建議延長或換回。
3. **重跑**：每筆在 repo 外的副本，用舊工具、同一個起點與要求跑一次；新工具的成果用試用時真的做出來的那個 commit。
4. **比對**：
   - 有畫面的（前端）：新舊各開一個版本，隨機標籤、封存對照，先灰階再配色（沿用 F1c 的做法）。
   - 沒有畫面的：diff、測試結果，加上不同家族模型的兩兩比較。
5. **決定**：到期通知附上比對結果與截圖位置，使用者再說留下或換回。
6. **成本**：前端一筆約扣 5 小時額度的 5 到 10%（2026-11-13、14 實測）。超過額度就只做前後截圖，寫明沒有對照組。

已知的不公平：新工具的成果包含使用者後來追加的修改，舊工具只跑第一個要求。所以另外附上新工具「第一回合結束時」的 commit（有的話）當對照。

## 實作（2026-11-14，第 1、2 步）

業界做法沿用上面那一輪。盲選另外對照 Chatbot Arena、Design Arena 的做法：匿名、投完才揭曉。差別在這裡的版本不多（2 到 4 個），對照表很容易猜，所以加了雜湊封存，證明選完之後沒有被改過。

**第 1 步：盲選工具** `engine/skills/omnikit-eval/scripts/blind.py`（seal、serve、verify、shots、choose、reveal、stop）。

- 每個版本開在隨機的空 port，不沿用固定 port。第三輪給錯網址，就是舊的服務還佔著固定 port；2026-11-14 重做時，那 4 個舊服務（18780 到 18783）確實還開著。
- 開站後先自動檢查，通過才印網址：每個標籤回應的頁面要最像它自己版本的檔，而且明顯比其他版本像；彩色網址不能帶灰階樣式、灰階網址要有，灰階拿掉樣式要跟彩色一樣；兩個版本一模一樣也擋。檢查訊息只寫標籤。
- 灰階轉送改用 Python 寫（原本是 node），遇到 CSP 用頁面自己的 nonce。
- 對照表加亂數後存 base64，SHA-256 另外存；choose 會記下當時的雜湊，reveal 比對，對不上或換過封存都不算。每一段都選了才解封，`--force` 會記成強制解封。
- 實跑：`C:\omnikit-eval\lp-run` 的四個版本（原版不蒙）。網址檢查通過，每個標籤跟自己版本的相似度約 0.98、跟其他版本最多 0.59；灰階截圖確認生效。沒有請使用者重選（第三輪已經選過），用 `--force` 走完解封，紀錄標成強制解封。

**第 2 步：影子比對** `engine/scripts/shadow.py`（record、pick、prepare、rerun、compare、result、status），週報 skill 的入口是 `report.py shadow`。

- 真實任務從 Claude Code 與 Codex 的對話紀錄找（沿用 `usage.py` 的叫用判斷），記下專案、第一個要求、開始前與結束時（結束後 10 分鐘內）的 commit。對話結束時沒有新的 commit 的記成「沒有成果可以比」；`omnikit-eval`、`.t3` 底下的副本不算。只存在 `%LOCALAPPDATA%\omnikit\shadow\`。
- 副本分三份：base（開始前）、old（開始前加上舊工具）、new（開始前當基準，換成結束時的檔案）。不動專案自己的 `.gitignore`，排除規則寫在副本的 `.git/info/exclude`。
- 不到 2 筆就照實說沒辦法比；結果一律附上「只重跑第一個要求」。
- 通知（`notify.py`）：到期前 3 天內提醒可以做影子比對（每個替換一次，有結果就不提醒）；到期通知附上比對結果，沒有比對就寫明只能憑感覺。
- `swap.py adopt`：手動裝好的試用補記成替換。替換前的清單是補拍的（現在的清單拿掉新的工具）。已補記 unslop 與 taste-skill 在 Claude Code、Codex 各一筆，到 2026-11-28。舊的 frontend-design 在這台兩個 agent 的清單裡都沒有，所以換回只要拿掉新的。

**還沒驗證：**

- 試用今天才開始，還沒有真實任務。`record` 照實記 0 段，影子比對還沒用真的任務跑過，只在自我測試裡用假的 agent 跑過。等使用者試用期間實際用過，2026-11-25 左右再跑一次。
- `rerun` 走 T3 的 retis，跑的是 T3 子對話：那些對話不在 `~/.claude`，不會被 `record` 誤當成真實任務。但使用者如果在 T3 裡用試用工具做事，目前也記不到（T3 的對話紀錄位置待驗證）。
- 相似度門檻（至少 0.5、差距至少 0.02）是依這次實跑定的。只改幾行的版本，差距可能低於 0.02 而被擋下，到時候再調。

## 實作（2026-11-14，第 3 步）

業界做法（只取「決定的畫面上放什麼證據」這一點）：

| 做法 | 畫面上放什麼 | 借來用的 |
|---|---|---|
| Renovate Merge Confidence（[官方文件](https://docs.renovatebot.com/merge-confidence)） | 在 PR 上直接放 Age、Adoption、Passing、Confidence 四個徽章，讓人合併前一眼看到 | 證據跟著決定出現，不要另外去找 |
| A／B 測試報表（Optimizely 等，憑既有了解，待驗證） | 差距、信賴區間、樣本數，樣本不夠就標「還不能下結論」 | 差距一定配次數與雜訊；沒量到就照實說 |
| 模型卡（Mitchell 等 2019，憑既有了解，待驗證） | 評估資料、限制與沒涵蓋的情況 | 「沒驗證到的部分」固定一行 |

做法：新增 `engine/scripts/proof.py`，從 `data/evals/` 的紀錄讀出五項（差距、雜訊基準、執行次數、評審家族、沒驗證到），只讀檔、不猜。

- 「換」與「裝」的建議（`advise.py` 的 `proof_lines`）：依據指到實測紀錄就逐行列五項；`replaces` 這條路固定寫「沒有實測：名冊卡片只寫明它取代舊的」。只有文字紀錄的（例如手動盲選的 F1c）照實寫「沒有結構化的數字」，找不到紀錄也照實寫。
- E4 通知（`notify.py`）：排佇列時把五項濃縮成一句存進候選（`proof`），通知裡接在證據路徑後面，例如「4 勝 1 負 1 平、沒量雜訊基準、每組 6 次、評審 Gemini、沒驗證到 2 項」。加上證據路徑就是 FR-16 要的六項。讀 pyyaml 的部分只在排佇列時跑，hook 的路徑不碰。
- 評審跟執行同一家時會標「可能偏袒自家」。
- selftest：`proof.py --selftest`（含讀真實的 WR1 紀錄），已加進 `validate.yml`；`advise.py`、`notify.py` 的 selftest 各加檢查。

沒驗證到：
- 目前名冊裡沒有任何 E4 候選真的指到有數字的紀錄（WR1 是 Keep），所以還沒在真實的通知或建議畫面上看到這幾行，只在 selftest 與 `proof.py show` 看過。
- 挑戰者不只一個的紀錄，沒指定工具時不列差距（不猜是哪一個）。
