# 決定之前要有可比對的成果：影子比對與其他缺口

日期：2026-11-14。狀態：提案，使用者已同意影子比對的方向，尚未實作。

## 結論

- 試用到期要使用者決定留下或換回，但畫面上只有工具名稱與到期日。補一個**影子比對**：試用期間記下真實任務，到期前用舊工具在副本重跑，讓使用者盲選。
- 盤點後，同一類缺口（要使用者決定，卻沒有可比對的成果）共 5 個高嚴重度、6 個中、4 個低。根源是同一個：**OmniKit 的證據停在維護者那一邊，沒有帶到使用者決定的那一刻**。
- 查到的工具沒有一個把「個人試用期間的真實任務」拿去重跑舊工具再盲選；最接近的是換模型的重播與「有無 skill」的比較。

## 起因

2026-11-14 前端設計槽位開始兩個 14 天試用（unslop、taste-skill）。使用者問：沒有畫面或具體成果可以比，怎麼知道要不要換回？三輪實測（`data/evals/2026-11-1[34]-frontend-design-F1*.md`）正好示範了有成果可比時的做法：副本、同一個要求、盲選、灰階與配色分開。

## 業界做法

讀的是搜尋摘要與官方頁面，沒有實測這些工具；多數是廠商與實務文章，不是嚴謹研究。

| 做法 | 怎麼運作 | 可以借的 | 限制 |
|---|---|---|---|
| 影子測試、冠軍與挑戰者 | 新舊版本吃同樣的輸入，只有舊版生效；順序是離線重播、影子並行、小流量 | 整個形狀；影子不能有副作用 | 推論成本約兩倍 |
| OrcaReplay | 錄下 coding agent 的執行，從檢查點分岔換模型再比 | 從真實任務的起點重跑 | 換的是模型不是工具；重播時工具呼叫是真的 |
| Arize 的 coding agent 追蹤 | 從真實操作收資料集，並排比較（例如有無某個 MCP） | 從真實使用收題目 | 要架追蹤 |
| Tessl、skill-ab-test、Skill Forge | 有 skill 對沒 skill（或對上一版），預設跑 3 次 | 基準與多次執行 | 題目是合成的，不是使用者的真實任務 |
| Design Arena | 設計類盲選兩兩比較，不打分數 | 跟三輪實測的做法一致 | 群眾的品味不是使用者的品味 |

三個警告：

1. **重播不等於原場景**（arXiv 2608.10319）：換了 skill，agent 的走法就不同，後續追問沒辦法照搬。所以只重跑「起點 commit 加第一個要求」，後面追加的修改比不到，紀錄裡寫明。
2. **影子不能有副作用**：只在副本跑，不動真的專案、不 push。
3. **差距要大於雜訊，而且不能自己評自己**：有實務文章量到自評把分數灌高 60 分。評審用不同家族的模型，品味題最後由使用者盲選。

## 影子比對

1. **記下真實任務**：試用期間，新工具被叫用的對話，從對話紀錄記下專案、開始前的 commit、使用者的第一個要求。只記在這台（`%LOCALAPPDATA%\omnikit\`），不進 repo、不回流。
2. **挑題**：到期前 3 天挑 2 到 3 筆（有乾淨的起點 commit、要求看得懂的）。不夠 2 筆就照實說「試用期間用得太少，沒辦法比」，建議延長或換回。
3. **重跑**：每筆在 repo 外的副本，用舊工具、同一個起點與要求跑一次；新工具的成果用試用時真的做出來的那個 commit。
4. **比對**：
   - 有畫面的（前端）：新舊各開一個版本，隨機標籤、封存對照，先灰階再配色（沿用 F1c 的做法）。
   - 沒有畫面的：diff、測試結果，加上不同家族模型的兩兩比較。
5. **決定**：到期通知附上比對結果與截圖位置，使用者再說留下或換回。
6. **成本**：前端一筆約扣 5 小時額度的 5 到 10%（2026-11-13、14 實測）。超過額度就只做前後截圖，寫明沒有對照組。

已知的不公平：新工具的成果包含使用者後來追加的修改，舊工具只跑第一個要求。所以另外附上新工具「第一回合結束時」的 commit（有的話）當對照。

已經有足夠證據、不用處理的：換回是否完成（快照比對）、30 天沒用到與成本高才建議拿掉、設定被手動改過、回流匯出預覽、第 2 層客觀實測的判定。

另外，PRD 的成功指標 SM-2「14 天內沒換回的占一半以上」量的正是使用者憑感覺沒換回，補上影子比對之後要改成「看過比對後留下的比例」。
