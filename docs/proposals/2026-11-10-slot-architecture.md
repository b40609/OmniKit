## 1. 現有 17 個槽位的問題

1. **三種不同性質的東西放在同一層。**
   - 要交付的成果：前端設計、文件與簡報、資料分析、逆向工程。
   - agent 自己怎麼運作：記憶與交接、權限與通知、輸出精簡、工作階段管理。
   - OmniKit 自己的維護：工具發現、skill 製作與評估。
2. **領域幾乎只有軟體開發。** 講成果的槽位裡，不屬於軟體開發的只有文件與簡報、資料分析、產品研究三個。
3. **粒度差很多。** 「輸出精簡」和「指令輸出壓縮」是 agent 行為的兩個細節，各佔一格；「文件與簡報產出」要涵蓋計畫書、簡報、預算表，情境卻只有一句（`data/slots.yaml:90`）。
4. **平面清單，不能選。** 每個人看到同一張 17 格的表，不做逆向工程的同事也有這一格。每加一種業務就多一格。
5. **一個槽位只有一個預設，不分 agent**（`engine/scripts/validate.py:190-192`）。10 張內建功能的卡有 9 張把 Claude 與 Codex 併成一張。
6. **沒有分類規則。** 槽位是照你遇到需求的順序加的：`b6554f2` 加瀏覽器、`1534531` 加資料分析、`a93faac` 加工作階段管理。新增時沒有判準可以問「這該放哪」。

## 3. 新架構

### 3.1 三層

| 層 | 判準 | 誰啟用 |
|---|---|---|
| 基礎 | 不管做什麼工作都會遇到，是 agent 自己怎麼運作的問題 | 每個人都有 |
| 能力 | agent 要碰得到某種東西才做得了事：瀏覽器、Office 檔、桌面程式、影音檔。被兩個以上的領域用到才獨立出來，否則留在領域裡 | 由領域帶入，使用者不用選 |
| 領域 | 一種業務或職能要交付的成果 | 使用者選；掃描專案可以預選 |

### 3.2 槽位怎麼寫

- 一個槽位是一件要交付的工作，用動作加成果命名（撰寫計畫書、粗剪），不是工具類別。
- 一個模組 3 到 6 個槽位，超過就拆模組。
- 每個槽位至少一個情境，寫成可以實測的任務。
- 每個槽位對每個 agent 各有一個答案：內建就夠、建議裝某個工具、沒有好選擇、還不知道。
- 每個槽位有找候選用的關鍵字，候選池匯入與 agent 上網找都用它。

### 3.3 模組檔（示意）

```yaml
# data/modules/domain/proposals.yaml
id: proposals
kind: domain                 # foundation、capability、domain
name: 計畫書與專案管理
summary: 補助案與合作案的計畫書、經費表、進度與結案報告
requires: [office-docs, web-research]     # 會帶入的能力模組
signals:                     # 掃描與訪談用來預選這個模組
  files: ["*計畫書*.docx", "*經費*.xlsx"]
  keywords: [計畫書, 提案, 結案報告, 審查意見]
maps_to: [product-management, productivity]   # 外部目錄的類別，匯入候選時自動落位
slots:
  - id: proposal-draft
    name: 撰寫計畫書
    scenarios:
      - id: PR1
        text: 依徵求公告與前期成果，寫 <計畫> 的計畫書初稿；章節、字數、表格照補助單位的範本，引用的數據附出處。
    search: [grant proposal writing, 計畫書 範本 docx]
    answers:
      claude: {verdict: unknown}
      codex: {verdict: unknown}
```

`answers` 填好之後長這樣：

```yaml
    answers:
      claude: {verdict: native, reason: 內建的文件 skill 就能照範本產出, evidence: data/evals/…, decided_at: '2026-11-20'}
      codex: {verdict: tool, tool: some-docx-skill, reason: …, evidence: …, decided_at: '2026-11-20'}
```

工具卡（`data/tools/<id>.yaml`）不變，`slots` 改指新的槽位 id。「預設」這件事從卡片的 `status` 搬到槽位的 `answers`，卡片只留試用、待評估、拒絕、退役。

### 3.4 怎麼擴充新的業務情境

由輕到重三種，都不用改程式或 schema：

1. **加情境**：在自己的情境檔加一句，機制現在就有（`data/profiles/<名稱>/scenarios.yaml`）。
2. **加私有模組**：放一個模組檔到 repo 外的 `%LOCALAPPDATA%\omnikit\modules\`，通過 schema 驗證就生效。跟 profile 一樣不會被 commit。任職單位專屬的內容放這裡。
3. **提進公版**：把模組檔放進 `data/modules/`。

第 2 種可以讓 agent 代寫：使用者用幾句話描述工作，agent 草擬槽位、情境與關鍵字，腳本驗證、預覽、同意後才寫入。這跟現在產生 profile 的做法一樣（agent 出內容，腳本寫入）。

新模組一加進來，槽位的關鍵字就能拿去找候選，不用等有人實測；答案先是「還不知道」，之後才慢慢填。

### 3.5 啟用

profile 多一個欄位列出啟用的領域；基礎一律啟用，能力由領域帶入。訪談的第 1 題（`engine/skills/omnikit-setup/SKILL.md:38`）從四個固定選項改成選領域。

| 誰 | 選的領域 | 帶入的能力 | 看到的槽位 |
|---|---|---|---|
| 你 | 全部 7 個 | 全部 6 個 | 43 |
| 只寫程式的同事 | 軟體開發 | 瀏覽器 | 12 |
| 寫計畫書的 PM | 計畫書與專案管理 | 文件與簡報檔、網路研究 | 15 |
| 做量測分析的研究員 | 科研與工程數據分析 | 文件與簡報檔 | 14 |

這張表是啟用機制做好之後的樣子；現在每個人看到的還是全部 43 個（第 8 節第 4 步）。

## 7. 候選從哪來（修正上一輪的說法）

上一輪我用「Codex 沙箱不開網路」當理由，把 agent 即時上網找壓成最後手段。這個限制在你們的工作流不存在，那個結論要改。

三個來源並用：

1. **槽位的答案**：有答案就照答案。
2. **候選池**：批次匯入兩家官方目錄與 MCP Registry。但官方目錄以開發為主（第 2 節的數字），CAD、影片、計畫書這些領域幾乎沒有東西。
3. **agent 即時上網找**：對新領域是主要來源。用槽位的關鍵字與情境去找，找到的過同一套檢查（GitHub 現況、授權、是不是在「別裝」清單），標明「名冊外，剛查到」。使用者採用之後寫回成候選卡，名冊隨著使用長大，不靠維護者一個人看。

原本的顧慮改用做法處理，不用禁止：查詢只送槽位的關鍵字，不送專案名稱；查到的結果存檔，可以重看；外部的文字只當資料讀。
