# 架構、舊程式、重構

共通點：改之前先把現狀固定下來，決定寫成檔案。

### 舊程式沒測試沒文件，想整理又怕弄壞
- 缺的是：保護網。邊重構邊補測試，測試會配合新程式寫。
- 做法：分兩階段。第一階段完全不改舊程式，替它現在的實際行為寫測試（包含奇怪的行為），全部通過。第二階段才小步重構，每一步跑一次測試。途中發現的 bug 另外記下來，不順手修。
- 可以直接貼：「這段舊程式我想整理。第一階段先不要改它，替它現在的實際行為寫測試，包含奇怪的行為。測試全過之後，第二階段才小步重構，每步都跑測試。」
- 依據：Michael Feathers 的特徵測試。

### 一堆不敢刪的舊檔案與過渡層
- 缺的是：「它為什麼在這裡」的證據。
- 做法：查 git 歷史（誰加的、為了什麼、多久沒動）與引用關係。對每個候選問兩題：它當初解決的問題還在嗎？刪掉它，複雜度是消失還是只是搬家？列清單與風險，使用者核准再刪。
- 可以直接貼：「請從 git 歷史與引用關係，找出長期沒動、或只剩一個地方在用的檔案與過渡層。每個寫明當初為什麼加、那個問題還在不在、刪掉的風險。列清單給我核准再刪。」
- 依據：Chesterton 的柵欄（拆之前先弄清楚為什麼立在那）；變更熱點分析。

### 剛定案的架構決定，怕之後忘記為什麼
- 缺的是：寫下來的紀錄。對話關掉或壓縮後就沒了，程式碼只看得到選了什麼。
- 做法：寫一份短的決策紀錄放進版控（例如 `docs/adr/`）：背景、考慮過的其他做法、為什麼選這個、預期後果、什麼情況要重新考慮。在規則檔加一行指到它。
- 可以直接貼：「把我們剛才定案的決定寫成一份決策紀錄放進 docs/adr/：背景、考慮過的其他做法、為什麼選這個、什麼情況要重新考慮。規則檔加一行指到它。」
- 依據：架構決策紀錄（ADR）。

### 該重構還是整個重寫
- 缺的是：風險與可逆性的比較。模型偏好整個重寫。
- 做法：先看這個模組的變更頻率、外部呼叫有多少、藏了哪些業務規則。比較三條路：原地重構、在邊界上逐步替換（絞殺者模式）、重寫，各自的風險與能不能回頭。建議風險最小的切法。
- 可以直接貼：「不要直接建議重寫。請先看這個模組多常被改、多少地方呼叫它、裡面藏了哪些規則，然後比較原地重構、逐步替換、整個重寫三條路的風險與能不能回頭。」
- 依據：Martin Fowler 的絞殺者模式。

### 程式拆得太碎，接手的人看不懂
- 缺的是：評估「好不好懂」的標準。
- 做法：找出兩種地方：介面跟實作一樣複雜的薄包裝；理解一個概念要跳好幾個檔案的地方。用「第一次接手的人要付多少理解成本」排序，提合併建議。
- 可以直接貼：「假設明天有一位沒看過這個專案的工程師接手。請找出他最難懂的地方：只是轉手的薄包裝、要跳好幾個檔案才懂的概念，依理解成本排序，提簡化建議。」
- 依據：John Ousterhout 的深模組；mattpocock 的 improve-codebase-architecture skill。

### 好幾個套件不知道選哪個
- 缺的是：跟這個專案綁在一起的比較。直接問哪個好，只會得到通用的優缺點。
- 做法：先讀專案的相依設定。對每個候選查現況（最新版本、維護狀態，查官方文件與 repo，不憑記憶），比較：跟現有相依合不合、照我們的寫法長什麼樣、以後換掉的成本。整理成表，先不安裝。
- 可以直接貼：「先讀我們的相依設定。比較〔A〕與〔B〕：跟現有套件合不合、照我們的寫法會長怎樣、以後換掉要花多少。查官方文件，不要憑記憶。先不要安裝。」
- 依據：架構取捨分析；先做限時的小驗證。

### 要改資料庫欄位，怕資料遺失
- 缺的是：分階段、可以回頭的做法。預設會給一步到位的破壞性指令。
- 做法：先盤點所有讀寫這張表的程式。用「先擴充再收縮」：加新欄位並雙寫、回填、切換讀取、下一版才移除舊欄位。列出每個階段與回復方式，使用者審過再執行。
- 可以直接貼：「這次資料庫改動要能回復、不能丟資料。請先列出所有讀寫這張表的地方，然後用分階段的做法：先加新欄位、雙寫、回填、切換、最後才移除舊的。每個階段怎麼回復也寫出來，我審過再做。」
- 依據：Expand and Contract（平行變更）。
