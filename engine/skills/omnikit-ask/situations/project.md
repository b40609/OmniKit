# 拆任務、排順序、複盤

### 功能太大，不知道怎麼切
- 缺的是：切法。照技術層切（先做完資料庫、再做完 API）每一塊都沒辦法單獨驗證。
- 做法：先不寫程式。把功能切成「從頭到尾走得通的一小條路」：每一塊都能單獨測試、有明確的驗收指令、寫明先後順序，寫進計畫檔。一塊動到的檔案太多（例如超過 5 個）就再切。
- 可以直接貼：「這個功能太大。先不要寫。請切成幾個可以單獨驗證的小任務，每個都是從頭到尾走得通的一小段，寫明驗收指令與順序，寫進計畫檔給我看。」
- 依據：垂直切片與曳光彈開發。

### agent 產出太快，審不完
- 缺的是：分級。瓶頸從寫程式變成人審查。
- 做法：重構與新功能分開提交。交給人審之前，先讓獨立的審查子代理濾掉風格、型別與明顯的錯。每個改動標「不可逆」（資料庫、安全、公開介面）或「可以快速退回」，人只深審前者。每個改動附上實際跑過的驗證結果。
- 可以直接貼：「請把重構與新功能分成不同的提交。交給我之前先做一次獨立審查。每個改動標明是不可逆的還是可以快速退回的，附上實際跑過的驗證結果。」
- 依據：依風險分級審查；小批量交付。

### 方案看起來很順，想先找出會翻車的地方
- 缺的是：讓隱憂浮出來的方法。直接問「有沒有風險」只會得到樣板。
- 做法：做事前驗屍：假設 3 個月後這個方案已經失敗，從失敗往回推，列出最先出問題的 5 個假設、被忽略的邊界情況、現在就能加的便宜防護。可以交給沒看過討論的審查者做。
- 可以直接貼：「假設 3 個月後這個方案已經失敗了。請從失敗往回推：最先出問題的 5 個假設是什麼、我們忽略了哪些情況、現在能加哪些便宜的防護。」
- 依據：Gary Klein 的事前驗屍（HBR 2007）。

### 一直重複提醒同一件事，想讓它下次自己會
- 缺的是：把教訓放到對的地方的習慣。
- 做法：
  1. 整理素材。Claude Code：跑 `/insights`（讀近期的對話，列出卡點與建議）。其他 agent：回顧這段對話，列出使用者糾正過什麼、哪裡繞了遠路。
  2. `/insights` 不知道你已經裝了什麼。每一條建議先對照已有的 skill 與規則檔：已經有的就改那一份，不要新增重複的。
  3. 每一條決定放哪：能用工具擋的做成檢查（測試、lint、hook）；只有這個專案適用的寫進專案規則；每個專案都適用的寫進個人規則；是「怎麼問」的寫進問法庫。
  4. 列給使用者確認再改。規則檔保持短，新增一條時看有沒有可以刪的。
- 可以直接貼：「請回顧〔這段對話／最近的工作〕：我糾正過你哪些事、哪裡繞了遠路。每一條先看現有的規則與 skill 有沒有，再建議放哪：能用檢查擋的做成檢查，其他才寫規則。列給我確認再改。」
- 依據：mattpocock 的 retro skill（「Default to building the check over writing the rule.」）；官方 `/insights`；官方建議規則檔只放「糾正過兩次的事」。

### 一堆待辦不知道先做哪個
- 缺的是：分流的標準。
- 做法：不動手修。逐項確認問題是不是還在（能不能重現），估影響範圍與大小（小、中、大），依「多痛、影響多廣、要花多少」排序。替前 3 項寫好可以直接交辦的任務說明。
- 可以直接貼：「請幫我整理這些待辦，先不要動手。逐項確認問題還在不在，依影響多大、要花多少排序，替前 3 項寫好可以直接開工的任務說明。」
- 依據：缺陷分流；影響與投入矩陣。
