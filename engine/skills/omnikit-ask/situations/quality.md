# 測試、安全、效能、上線

共通點：要證據，不要「看起來沒問題」；審查的人不能是寫的那個。

### 測試很多，但感覺抓不到真的錯
- 缺的是：測試品質的檢查方法。覆蓋率高不代表抓得到錯。
- 做法：開新對話或子代理審查測試。看三件事：哪些測試只是在驗 mock 的回傳值；錯誤路徑（逾時、無效輸入、權限不足）有沒有測；故意把關鍵判斷改反，看測試會不會失敗（改完還原）。
- 可以直接貼：「請審查現有的測試，不要只看覆蓋率。哪些只是在測 mock？錯誤路徑有沒有測？試著把幾個關鍵判斷改反，看測試抓不抓得到，然後還原。」
- 依據：突變測試；測對外的行為而不是內部細節。

### 要上線了，想認真查安全漏洞
- 缺的是：唯讀的獨立審查者，以及每個發現都要有證據。
- 做法：用唯讀的子代理或新對話（Claude Code 有內建的 `/security-review`）。逐項檢查權限繞過、越權存取、注入、被吞掉的例外、寫死的金鑰。每個發現標「已確認」（附檔名行號與重現方式）或「懷疑」。沒發現問題的模組也寫檢查了什麼。
- 可以直接貼：「請用唯讀的方式做安全審查，不要改程式。每個發現標明『已確認』（附檔名行號與怎麼重現）或『懷疑』。沒問題的部分也寫出你檢查了什麼。」
- 依據：威脅建模；以可重現的路徑驗證風險。

### 系統變慢，不知道慢在哪
- 缺的是：量測。沒量就改，常常加了快取卻製造新問題。
- 做法：先不加快取、不改演算法。建立量測（計時、查詢計畫、profiler），找出最慢的前 2 個地方的證據，定出目標數字，再改；改完用同樣的方式量一次。
- 可以直接貼：「先不要加快取或改寫。請先量出慢在哪裡，給我前 2 個瓶頸的數據與目標，再改；改完用同樣的方法再量一次。」
- 依據：先剖析再最佳化。

### 大改動要合併上線，怕漏東西
- 缺的是：上線前的檢查清單。本機測試常靠殘留的設定才會過。
- 做法：不改動、不部署，只檢查：實際跑型別檢查、lint、測試、建置並貼出結果；看這批改動有沒有新增環境變數、寫死的網址、破壞性的資料庫變更、被吞掉的錯誤；最後給「可以上」或「不行」與阻擋的項目。
- 可以直接貼：「上線前請檢查，先不要改任何東西：跑完檢查、測試、建置並貼出實際結果；看這批改動有沒有新的環境變數、寫死的網址、破壞性的資料庫變更。最後告訴我可不可以上、卡在哪。」
- 依據：上線就緒審查。

### 出事時 log 看不出發生什麼
- 缺的是：事先設計的診斷線索。
- 做法：沿著一條關鍵流程（入口到資料庫到外部呼叫），在每個外部邊界與狀態轉換的地方加上結構化紀錄：關聯 id、耗時、帶上下文的錯誤。不記個資與金鑰。寫一頁「出事怎麼查」。
- 可以直接貼：「請沿著〔這條流程〕從入口到資料庫，在每個外部呼叫與狀態改變的地方補上紀錄：關聯 id、耗時、錯誤的上下文。不要記個資與金鑰。另外寫一頁出事時怎麼查。」
- 依據：可觀測性（紀錄、指標、追蹤）與維運手冊。

### 要串沒用過的外部 API
- 缺的是：對真實介面的查證，以及跟業務邏輯的隔離。
- 做法：先讀官方最新文件確認介面與錯誤碼，不憑記憶。設計一層轉接（逾時、重試、限速、回傳格式驗證），先給介面定義與測試規劃（429、500、格式錯誤），確認再實作。
- 可以直接貼：「先不要把這個 API 寫進業務程式。請讀官方最新文件確認介面與錯誤碼，設計一層轉接處理逾時、重試、限速，先給我介面與測試規劃。」
- 依據：防腐層與契約測試。

### 合併衝突一大堆
- 缺的是：對兩邊各自想做什麼的理解。圖省事會直接選一邊。
- 做法：對每個衝突的檔案，先看兩邊的提交紀錄：主線改了什麼、這個分支加了什麼。提出兩邊都保留的合併方式，解完跑測試確認兩邊的功能都還在。
- 可以直接貼：「解衝突時不要直接選一邊。每個檔案先看兩邊各自改了什麼、為什麼，提出兩邊都保留的寫法，解完跑測試。」
- 依據：依意圖合併。
