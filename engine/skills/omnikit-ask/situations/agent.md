# 跟 agent 協作

這一類多半有對應的官方功能，各家的叫法見 `../features.md`。

### 話還沒講完，它就開始大改
- 做法：用先規劃的模式（plan mode）：只讀不改，先探索相關的程式，寫出要動哪些檔、怎麼驗證的計畫，使用者核准才動手。
- 可以直接貼：「這一輪先不要改任何檔案。請先看相關的程式，寫出計畫：要動哪些檔、每一步怎麼驗證。我同意再開始。」
- 依據：三家都有 plan mode；人類的做法是設計文件先審。

### 每次新對話都要重講一樣的規矩
- 做法：把 agent 從程式碼看不出來的事寫進規則檔（Claude Code 是 `CLAUDE.md`，Codex 與 Antigravity 是 `AGENTS.md`）：怎麼跑測試與檢查、哪些地方不能照抄、不在 repo 裡的決定、已經糾正過兩次的事。架構與檔案結構不用寫，它自己會讀。保持短。
- 可以直接貼：「請把我這段對話重複交代過的事整理進規則檔：怎麼跑測試、哪些資料夾不能動、我們的慣例。只寫你從程式碼看不出來的，越短越好，給我看過再存。」
- 依據：官方「Keep CLAUDE.md short」：只放 Claude 從程式碼看不出來的事。

### 對話聊久了，它越改越笨
- 做法：換任務就清掉對話重新開始；同一件事做很久，壓縮並指定要保留什麼。清掉之前，請它把已確認的事、改過的檔、下一步寫成幾行摘要，新對話帶著這幾行開始。
- 可以直接貼：「請把目前確認的事實、改過的檔案、下一步寫成 10 行以內的摘要。我要開新對話接著做。」
- 依據：官方：每次請求都會重送整段對話；「`/clear` between unrelated tasks. It costs nothing」。

### 它說做完了，其實沒有
- 做法：給它一個檢查的方法，並要求附上實際輸出。開工時就講明「做完」的定義與驗證指令；回報完成時要有這一輪實際跑過的結果。不能有例外的檢查改用 hook 強制。
- 可以直接貼：「說完成之前，請實際跑〔測試或建置指令〕並貼出結果，逐條對照我的需求。沒跑過的要寫明沒跑。」
- 依據：官方「Give Claude a check to run」。

### 它卡在同一個錯誤裡打轉
- 做法：同一件事修正兩次還不對，就停。退回乾淨的狀態（rewind 或 git），清掉對話，重寫一則把學到的寫進去的提示詞。新對話先請它列出幾個不同的假設再選，不沿用原本的做法。
- 可以直接貼（新對話的第一句）：「之前的做法〔簡述〕試了兩次都失敗，不要沿用。已知：〔學到的事〕。請先提出 3 個不同的假設與驗證方式，我選了再動手。」
- 依據：官方：「after two failed corrections run /clear and write a better prompt instead of a third」。

### 要它查很多檔案，怕塞爆對話
- 做法：大範圍的搜尋、讀 log、跑大量驗證交給子代理，只帶結論與檔名行號回來。注意：子代理是為了隔離很長的輸出與平行，不會讓答案更聰明，而且各自花 token。
- 可以直接貼：「這個調查請交給子代理去做，只把結論與對應的檔名行號帶回來，不要把原始內容貼進這段對話。」
- 依據：官方「Know what subagents cost」。

### 叫它自己檢查，永遠說沒問題
- 做法：寫的與審的分開。開新對話或子代理（最好是唯讀），只給規格與改動內容，請它找出不符合規格、沒驗證到的地方。有訂第二家模型時，換一家審更好。
- 可以直接貼（給審查者）：「你沒看過這段程式是怎麼寫出來的。這是規格與改動。請找出不符合規格的地方、沒有被測試涵蓋的情況、沒有根據的假設。風格不用管。」
- 依據：官方：「A fresh reviewer does help, because it hasn't seen your reasoning」。

### 想同時開好幾個 agent，怕互相蓋掉
- 做法：每個獨立的任務各用一個 git worktree 與分支，各自改、各自測，完成後逐一審查合併。任務之間有共用檔案的不要平行。
- 可以直接貼：「這幾件事互不相干，請各開一個 worktree 與分支分別做，不要動到彼此的檔案，做完我逐一看過再合併。」
- 依據：三家都把 worktree 當平行開發的做法。

### 只要簡單功能，它蓋了一整套架構
- 做法：講明範圍：只做現在要的行為，不為假想的未來需求加抽象層與設定。改動超過預期的檔案數時先停下來問。
- 可以直接貼：「只做我講的這個行為，不要為以後可能的需求加抽象或設定。如果你覺得要改超過〔3〕個檔案，先停下來告訴我為什麼。」
- 依據：YAGNI；三次法則。

### 規則寫了，它還是照樣違反
- 做法：先看規則檔是不是太長或互相矛盾（Claude Code 有 `/doctor`）。只寫「不要用 X」的改成「用 Y 取代 X」並附原因。不能有例外的改用 hook 或權限設定強制。加強調字眼通常沒用，還會讓它過度套用。
- 可以直接貼：「請檢查規則檔：哪些太長、互相矛盾、或只說不要做什麼卻沒說該怎麼做。不能有例外的那幾條，請改成 hook 或權限設定。」
- 依據：官方「What you can stop doing」；「To block an action regardless of what Claude decides, use a PreToolUse hook」。

### 對話快滿了或要收工，怕脈絡斷掉
- 做法：寫交接檔再開新對話：已完成且驗證過的、卡住與未決的、已經定案不要重審的、確切的檔案路徑、下一步的第一個動作。裝了 `omnikit-handoff` 就說「交接」。寫之前先實際查狀態（git 紀錄、CI），不憑記憶。
- 可以直接貼：「我要換對話。請先實際確認目前狀態（git、測試），再寫交接檔：做完的、沒做完的、已定案的決定、檔案路徑、下一步第一件事。」
- 依據：輪班交接；EMNLP 2026 的 Handoff Debt 論文：接手時附上脈絡能明顯減少重新摸索。

### 把 agent 當搜尋引擎用，感覺不出它厲害
- 做法：不要問「這段怎麼改」然後自己複製貼上。改成交代目標、完成條件、驗證指令，讓它自己找檔案、改、跑測試，最後摘要改了什麼給你審。
- 可以直接貼：「〔功能〕現在會〔症狀〕。請你自己找相關的檔案、修好、跑〔測試指令〕，通過後告訴我改了什麼。」
- 依據：官方的例子：講症狀、位置、「修好」長什麼樣。

### 它一直停下來等我按確認，或權限開太大亂改
- 做法：依任務選模式：探索與規劃用唯讀；有測試保護的小改動自動接受編輯；沒人看著的背景執行，在任務說明開頭寫明不能做的事（不提交、不推送、不刪檔、不安裝），並設好允許清單。
- 可以直接貼：「這個任務請用〔唯讀／自動接受編輯〕的方式做。不能做的事：〔不提交、不刪檔、不安裝套件〕。」
- 依據：最小權限原則；各家的權限模式。

### 它用了不存在的函式或參數
- 做法：呼叫外部套件之前，先讀本機安裝的型別定義或原始碼，或查官方文件確認實際的寫法。找不到就停下來回報，不自己發明。
- 可以直接貼：「用〔套件〕之前，請先讀我們安裝的那一版的型別定義或官方文件，確認函式與參數真的存在。查不到就告訴我，不要猜。」
- 依據：先查一手的介面定義。

### 裝了一堆 skill 與規則，反而變笨
- 做法：定期清：模型升級時，拿掉為舊模型寫的補丁（要它一步一步想、叫它不要偷懶、全大寫強調）、模型現在自己會做的細節規定、用不到的 skill。Claude Code：`/doctor` 與 `/skill-doctor` 會列出沒在用的與太長的。
- 可以直接貼：「請檢查我的規則檔與已裝的 skill：哪些是為舊模型寫的、現在不需要了？哪些沒在用？列出來讓我決定，先不要刪。」
- 依據：Anthropic：harness 的每個元件都是「模型做不到某件事」的假設，模型升級就該重新檢查。

### 做到一半就停，或用省略號交差
- 做法：把步驟寫成檔案裡的清單，每做完一項就更新。講明什麼才算停（全部做完，或遇到真的需要使用者決定的事）。現在的模型多半會自己做完；真的停了說「繼續」就好，不要加「不准偷懶」這類話。
- 可以直接貼：「請把步驟寫進 todo 檔，每完成一項就勾掉並驗證。全部做完、或遇到一定要我決定的事才停。程式碼要完整，不要用省略。」
- 依據：檢查清單式執行；官方：叫它不要偷懶的話現在容易造成過度工作。

### 改了規則或 skill，不知道有沒有變好
- 做法：先收集 5 到 10 個過去真的失敗過的例子當測驗題，定好通過的標準。改之前與改之後各跑一次（最好各 3 次），比較。差距沒有明顯大於同一設定重跑的差異，就不算變好。
- 可以直接貼：「先不要憑感覺改。請用這 5 到 10 個以前失敗過的例子當測驗，改之前與改之後各跑幾次比較，沒有明顯變好就不採用。」
- 依據：Anthropic 的 evals 建議：從 20 到 50 個真實失敗開始。
