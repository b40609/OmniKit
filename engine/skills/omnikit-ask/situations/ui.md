# 前端與畫面

共通點：agent 看不到畫面，也不知道你心裡的「好看」是什麼。補的是截圖、參考、設計約定，以及讓它自己看到結果的方法。

### 畫面怪怪的，但說不出哪裡要改
- 缺的是：具體的設計詞彙。只說「改好看一點」，它只能猜。
- 做法：先不改。取得目前畫面的截圖（自己開頁面截，或請使用者貼）。從層級、留白、對齊、對比、資訊密度五個角度各列出看到的具體問題，每個問題對應到可以改的東西（哪個元件的間距、字級、顏色）。讓使用者挑要改哪幾項，一次改一項，改完截圖前後對照。
- 可以直接貼：「先不要改。這是目前畫面的截圖。請從層級、留白、對齊、對比、資訊密度各列出你看到的具體問題，每個問題寫出要改哪個元件的哪個屬性，讓我挑。」
- 依據：設計評審的規矩是不能只說「我不喜歡」，要指出哪個元素違反了哪個目標。官方建議把截圖直接貼進提示詞。

### 一看就是 AI 做的
- 缺的是：設計約定。沒有約定時，模型會收斂到最常見的樣子（紫藍漸層、發光陰影、清一色大圓角卡片）。
- 做法：動手前先定一份短的設計約定（字體、語意色票、間距尺度、圓角），寫成 `DESIGN.md`，之後所有元件只引用這份。同時列出這次要避開的預設樣式。裝了設計類的 skill 就用它的檢查。
- 可以直接貼：「先不要寫畫面。請依這個產品的用途提出一份設計約定：字體、色票、間距尺度、圓角，寫進 DESIGN.md 給我確認。之後的元件只能用裡面的值。這次不要紫藍漸層、發光陰影、清一色的大圓角卡片。」
- 依據：品牌與設計系統的做法是先定規範再出頁面。社群的 frontend skill 多半有「AI 預設樣式」的對照表。

### 想做出某個產品的質感，不知道怎麼描述
- 缺的是：把「像某某」拆成可以照做的規格。
- 做法：請使用者給 2 到 3 張參考截圖。先拆解它的視覺層級、字級比例、資訊密度、邊框與對比的用法，寫成設計約定給使用者確認；再用專案既有的元件實作。不照抄版面與文案。
- 可以直接貼：「這幾張是我喜歡的參考畫面。不要照抄版面。請先拆解它的層級、字級比例、資訊密度、邊框與對比怎麼用，寫成設計約定給我確認，再用我們現有的元件做。」
- 依據：設計界的情緒板與競品視覺拆解。

### 新頁面跟原本的風格不搭
- 缺的是：它沒先看專案裡已經有什麼。
- 做法：寫新元件之前，先讀現有的元件資料夾與樣式設定，列出已有的元件與色票。新頁面重用這些；真的需要新元件時先問。
- 可以直接貼：「寫之前先讀〔元件資料夾〕與樣式設定，列出已經有的按鈕、卡片、色票。新頁面要重用它們；需要新元件先問我。」
- 依據：官方的例子是「follow the pattern in HotDogWidget.php」，指一個現成的範例給它看。

### 只做了有資料的樣子
- 缺的是：狀態清單。只說「顯示列表」，它只做順利的那條路。
- 做法：先列出這個元件的所有狀態：載入中、沒資料（含引導）、出錯（含重試）、送出中、內容超長。逐一實作，每個狀態截一張圖。
- 可以直接貼：「這個元件請先列出所有狀態：載入中、沒資料、出錯、送出中、內容超長，逐一做完，每個狀態截圖給我看。」
- 依據：官方提到要它做完整版時要明講範圍（空狀態、錯誤狀態、鍵盤操作）。

### 手機版跑版，講了也修不準
- 缺的是：哪個寬度、長什麼樣。
- 做法：請使用者給出問題的寬度與截圖（或自己用瀏覽器工具重現）。查相關元件的換行、定位、層疊規則。改完在窄螢幕（約 375）與桌面（約 1280）各截一張驗證。
- 可以直接貼：「寬度小於〔768〕時〔導覽列與主內容重疊〕，截圖在這。請找出原因，改完在 375 與 1280 兩種寬度各截一張圖給我。」
- 依據：響應式測試的做法是固定幾個寬度逐一檢查。

### 它說版面修好了，打開還是歪的
- 缺的是：它自己看到結果的方法。
- 做法：改完樣式後，啟動開發伺服器、用瀏覽器工具開頁面截圖，自己看過截圖（換行、對齊、溢出）再回報。沒有瀏覽器工具時，請使用者截圖貼回來，不要只憑程式碼說完成。
- 可以直接貼：「改完不要只看程式碼。請開頁面截圖，自己檢查對齊、換行、有沒有溢出，把截圖附上再說完成。」
- 依據：官方把「給它一個檢查的方法」列為最重要的做法之一。

### 想要它認真審設計，不要只會說好
- 缺的是：評審標準，以及沒參與製作的審查者。
- 做法：開新對話或子代理（沒看過製作過程），只給截圖與評審標準（Nielsen 十項可用性原則，加上層級與訊噪比）。請它列出最嚴重的 5 個問題與修法，不需要寫優點。
- 可以直接貼：「請當作你第一次看到這個畫面。依 Nielsen 十項可用性原則逐項檢查，列出最嚴重的 5 個問題與修法。優點不用寫。」
- 依據：啟發式評估（Nielsen）。官方：沒看過推理過程的審查者才有幫助。

### 不知道鍵盤、色盲、螢幕閱讀器能不能用
- 缺的是：檢查清單與客觀的工具結果。
- 做法：依 WCAG 2.1 AA 檢查：可以點卻不是按鈕或連結的元素、表單標籤、對比、焦點順序。實際用鍵盤走一遍主要流程。能跑 axe 或 Lighthouse 就跑，附結果。
- 可以直接貼：「請依 WCAG 2.1 AA 檢查這頁：不是按鈕卻能點的元素、表單標籤、對比、焦點順序。用鍵盤走一遍主要流程，並跑 axe 或 Lighthouse，把結果附上。」
- 依據：WCAG 與 WAI-ARIA。這一項有客觀工具可以驗證。

### 按鈕按了沒反應，也沒有錯誤訊息
- 缺的是：執行時的證據。只看程式碼看不出卡在哪一層。
- 做法：先不改。從點擊事件沿著資料流往下追：表單驗證、停用條件、狀態管理、API 請求。用瀏覽器的 console 與 network 證實卡在哪一步，再改那一步。
- 可以直接貼：「先不要改。請從點擊事件一路追到表單驗證、狀態、API，用瀏覽器的 console 與 network 找出卡在哪一步，告訴我證據再改。」
- 依據：系統化除錯：先找到證據再動手。
