# 除錯

共通點：先有證據再動手。官方的例子就是「寫一個會失敗的測試重現它，再修」。

### bug 修好了，下次又再發生
- 缺的是：把根因鎖住的測試，以及「還有哪裡是同樣寫法」的排查。上次修的多半是症狀。
- 做法：先不修。第一步寫一個能穩定重現的自動化測試，跑給使用者看它失敗。第二步往回追根因（不是出錯的那一行，是為什麼會走到那裡），修根因，測試轉綠。第三步全專案搜尋同樣的寫法，列出來。第四步問：這個錯能不能用檢查擋住（測試、lint、hook）？能就加上，不要只寫進規則檔。
- 可以直接貼：「這個 bug 修過又再發生。先不要修。第一，寫一個能重現它的測試，跑給我看它失敗。第二，找出根因再修，測試要轉綠。第三，搜尋整個專案還有哪裡是同樣的寫法。第四，告訴我能不能加一個檢查讓它以後不會再發生。」
- 依據：回歸測試加橫向排查；事故複盤的做法是把教訓變成自動防呆。官方：先寫會失敗的測試再修。

### 修一個 bug，別的地方壞掉
- 缺的是：改動範圍的界線，與改完的全面檢查。
- 做法：講明這次只能動哪些檔案或資料夾。需要動到範圍外（共用工具、全域設定）時先停下來問。修完跑既有的全部測試。
- 可以直接貼：「這次只修〔問題〕，只能改〔檔案或資料夾〕。如果一定要動到別的地方，先停下來問我。修完跑全部測試。」
- 依據：最小改動原則；以全套測試當合併門檻。

### 一整頁錯誤訊息看不懂
- 缺的是：完整的原文。自己轉述或只截一半，會漏掉檔名與行號。
- 做法：請使用者貼完整的錯誤輸出（或自己重跑取得）。先用白話解釋為什麼發生、最初是哪一行觸發；找出相關的檔案，提修法，確認再改。
- 可以直接貼：「這是完整的錯誤訊息〔貼上全部〕。先用白話告訴我為什麼會發生、最初是哪一行觸發的，再提修法，我確認再改。」
- 依據：官方建議直接把輸出交給它，不要轉述。

### 有時候壞、有時候好
- 缺的是：可以驗證的假設。猜一次就改，只會把問題蓋住。
- 做法：不改邏輯。列出 3 個互斥、可以被推翻的假設（例如競態、沒清乾淨的狀態、時序或時區）。設計最小的重現方式（例如連跑 50 次）或在關鍵位置加上記錄，用證據排除，剩下的那個才修。不用隨意加等待時間當修法。
- 可以直接貼：「這個問題時好時壞。先不要改。請列出 3 個可以被驗證的假設，設計一個重現的方法（例如連跑 50 次）或加上記錄，用證據排除之後再修。」
- 依據：科學式除錯（Google SRE 的故障排除）。

### 同一類的坑一直踩，想徹底複盤
- 缺的是：把多次事故歸成共同原因的方法。
- 做法：收集這幾次的紀錄（提交、對話、錯誤）。對每一次問五次「為什麼」，找共同的結構性原因，不檢討人。結論分兩類：能用工具擋的做成檢查；需要判斷的才寫進規則。Claude Code 可以先跑 `/insights` 拿到近期卡點的整理再開始。
- 可以直接貼：「請看最近這幾次出錯與返工〔列出或指出範圍〕。找出共同的根本原因，不要逐件講。能用測試、lint 或 hook 擋住的，直接提出要加的檢查；其他才寫成規則。」
- 依據：無指責事故複盤與五個為什麼。mattpocock 的 retro skill：「Default to building the check over writing the rule.」

### 我的電腦正常，CI 或正式環境壞掉
- 缺的是：兩邊環境的差異。
- 做法：先列出可能不同的地方：環境變數、語言與套件版本、作業系統（大小寫、路徑）、權限、快取。在各層交界加上診斷輸出，兩邊比對，找到出問題的那一層之前不改業務邏輯。
- 可以直接貼：「這只在〔CI／正式環境〕發生。請先列出它跟我本機可能不同的地方，加上診斷輸出比對，找到是哪一層出問題再改。」
- 依據：環境對等檢查。
