# 需求與範圍

共通點：agent 會急著替你把空白補上。補的是「先問、先定界線、先定大小」。

### 有想法，但細節還沒定
- 缺的是：被追問的過程。直接叫它寫，它會自己決定你沒講的部分。
- 做法：先不寫程式。先讀現有的程式碼（程式裡有答案的不要問）。然後一次問一題，每題附你的推測與選項，問到邊界、資料流、例外處理都清楚，寫成 `SPEC.md`。寫完建議開新對話照規格做。
- 可以直接貼：「我想做〔功能〕，但還沒想清楚。先不要寫程式。請先看現有的程式碼，然後一次問我一題、附上你的推測與選項，問到你能寫出規格為止，寫進 SPEC.md。」
- 依據：官方：「Interview me until you could write the spec」。社群最多人用的是 mattpocock/skills 的 grill-me 與 superpowers 的 brainstorming。

### 腦袋空白，不知道提示詞怎麼寫
- 缺的是：把目標、背景、限制、做完的定義講出來的引導。不需要完美的咒語。
- 做法：問使用者 3 個最關鍵的問題（要達到什麼、現在卡在哪、怎樣算做完），再把答案整理成一段提示詞給他確認，確認後直接照做。
- 可以直接貼：「我想處理〔狀況〕，但不知道怎麼講清楚。請問我 3 個最關鍵的問題，然後幫我整理成包含目標、背景、限制、做完的定義的需求，我確認後你再開始。」
- 依據：OpenAI 的 Codex 提示詞文件用的四要素：目標、背景、限制、何時算完成。

### 只知道哪裡不方便，還不知道要做什麼
- 缺的是：從「解法」退回「痛點」的對話。
- 做法：先不提方案、不談技術。問情境（什麼時候遇到）、動機（想達成什麼）、理想結果，一次一題並附猜測。最後用一句話重述「真正要解決的問題」，使用者說對了才往下。
- 可以直接貼：「我只知道〔這件事〕很不方便，還不知道該做什麼。先不要提方案。請一次問我一題，了解我什麼時候遇到、想達成什麼，最後用一句話說出真正要解決的問題給我確認。」
- 依據：Jobs-to-be-Done 訪談。

### 需求越講越大，收不了尾
- 缺的是：寫下來的「這次不做」。
- 做法：動手前把需求分成「這次一定要」與「這次不做」兩份清單，寫進規格。之後出現新想法，先放進「下次」清單並告訴使用者，不直接做。
- 可以直接貼：「動手前請把需求分成『這次一定要』與『這次不做』兩份清單給我確認。之後我提新的想法，先記到『下次』，問我要不要調整範圍，不要直接加。」
- 依據：MoSCoW 與明寫的非目標。

### 不知道該做成小腳本還是完整系統
- 缺的是：願意投入多少的上限。模型預設往完整的架構靠。
- 做法：請使用者講投入上限（例如一個下午）。提 3 種規模的做法（最小的腳本、單檔工具、完整模組），比較各自的維護成本，以及什麼情況才需要升級到下一級。使用者選了再做。
- 可以直接貼：「這件事我最多想花〔一個下午〕。請提 3 種規模的做法：最小的腳本、單檔工具、完整模組，比較維護成本與什麼時候才需要升級，我選了再做。」
- 依據：Shape Up 的「先定胃口再定範圍」；YAGNI。
