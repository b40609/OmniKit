# 問法庫

使用者卡住時，缺的通常不是措辭，是這四樣之一：agent 看不到的資訊、判斷好壞的標準、做事的方法、驗證的方式。這份問法庫依情境寫出該補哪一樣、用哪個機制。

72 個情境來自 2026-11-17 的調研（官方文件、社群的 skill 合集、人類專業的做法）。2026-11-17 挑 11 條做過有它與沒它的對照：Claude Code（`docs/reviews/2026-11-17-ask-eval.md`）與 Antigravity 的 Gemini 4 Hydrogen、Gemini 3.8 Flash（`docs/reviews/2026-11-17-ask-eval-gemini.md`）；之後擴充到 72 條每條一題、每題兩種說法、30 題不該叫用（`docs/reviews/2026-11-17-ask-eval-expanded.md`）；使用者自己的實測還沒做。每一條的依據寫在條目裡；來源與核對狀態在 `SOURCES.md`。

## 怎麼用

1. **對情境。** 從下面的索引找最接近的一條。對到兩條以上或都不像時，問使用者一題，列 2 到 4 個選項讓他選；不要自己猜。
2. **讀那一類的檔案**（`situations/<類別>.md`），只讀對到的那一條。
3. **補缺的東西。** 你自己查得到的先查（讀檔、看 git 紀錄、截圖、跑指令）；只有使用者知道的才問，最多 3 題，每題附你的猜測讓他修正。
4. **先講你要怎麼做，再做。** 用一兩句說這個情境缺的是什麼、你接下來的做法，然後直接照做法進行。使用者只想要問法時，給他「可以直接貼」的那一句就好。
5. **用這個 agent 有的功能。** 做法裡提到的官方功能（清掉對話、先規劃、獨立審查、截圖）各家叫法不同，對照表在 `features.md`；這個 agent 沒有對應功能時，照做法的步驟自己做。
6. **做完講一句學到的。** 例如「下次這種情況，先給截圖和『修好長什麼樣』會更快」。只講一句。

寫問法時的原則（官方對新模型的建議）：

- 給資訊，不給口號。「從第一性原理」「仔細想」這類字眼是普通文字；有用的是症狀、位置、做完的定義。
- 講原因，不加強調。「嚴禁」「務必」會讓模型過度套用；說明為什麼，它會自己類推。
- 要它挑毛病時，換一個沒看過過程的審查者（新對話、子代理或別家模型），不要叫寫的那個自己審。
- 能用檢查擋的就不要只用講的：測試、lint、hook。

## 索引

### 前端與畫面（`situations/ui.md`）
- 畫面怪怪的，但說不出哪裡要改
- 一看就是 AI 做的（紫藍漸層、大圓角卡片）
- 想做出某個產品的質感，不知道怎麼描述
- 新頁面跟原本的風格不搭
- 只做了有資料的樣子，載入中、沒資料、出錯都沒做
- 手機版跑版，講了也修不準
- 它說版面修好了，打開還是歪的
- 想要它認真審設計，不要只會說好
- 不知道鍵盤、色盲、螢幕閱讀器能不能用
- 按鈕按了沒反應，也沒有錯誤訊息

### 操作流程與功能入口（`situations/ux.md`）
- 畫面太多太雜，想把功能與按鍵入口合併
- 做了功能，使用者卻找不到
- 操作步驟太多，想縮短又怕漏掉檢查
- 按鈕與訊息太像工程師寫的

### 除錯（`situations/debug.md`）
- bug 修好了，下次又再發生
- 修一個 bug，別的地方壞掉
- 一整頁錯誤訊息看不懂
- 有時候壞、有時候好
- 同一類的坑一直踩，想徹底複盤
- 我的電腦正常，CI 或正式環境壞掉

### 需求與範圍（`situations/requirements.md`）
- 有想法，但細節還沒定
- 腦袋空白，不知道提示詞怎麼寫
- 只知道哪裡不方便，還不知道要做什麼
- 需求越講越大，收不了尾
- 不知道該做成小腳本還是完整系統

### 架構、舊程式、重構（`situations/architecture.md`）
- 舊程式沒測試沒文件，想整理又怕弄壞
- 一堆不敢刪的舊檔案與過渡層
- 剛定案的架構決定，怕之後忘記為什麼
- 該重構還是整個重寫
- 程式拆得太碎，接手的人看不懂
- 好幾個套件不知道選哪個
- 要改資料庫欄位，怕資料遺失

### 測試、安全、效能、上線（`situations/quality.md`）
- 測試很多，但感覺抓不到真的錯
- 要上線了，想認真查安全漏洞
- 系統變慢，不知道慢在哪
- 大改動要合併上線，怕漏東西
- 出事時 log 看不出發生什麼
- 要串沒用過的外部 API
- 合併衝突一大堆

### 調研、比較、學習（`situations/research.md`）
- 剛接手陌生的大專案
- 懷疑自己一開始就問錯問題
- 擔心改動引發連鎖反應
- 想從別的領域借解法
- 調研只列幾個就停，還混進記錯的資訊
- 要用沒學過的技術，不想完全看不懂

### 文件、報告、簡報、資料（`situations/docs.md`）
- 一堆資料要分析，不想亂畫圖
- 寫出來的文章很像 AI 寫的
- 好幾份資料要綜合成有觀點的報告
- 簡報每頁都是文字牆
- 文件跟程式對不起來

### 跟 agent 協作（`situations/agent.md`）
- 話還沒講完，它就開始大改
- 每次新對話都要重講一樣的規矩
- 對話聊久了，它越改越笨
- 它說做完了，其實沒有
- 它卡在同一個錯誤裡打轉
- 要它查很多檔案，怕塞爆對話
- 叫它自己檢查，永遠說沒問題
- 想同時開好幾個 agent，怕互相蓋掉
- 只要簡單功能，它蓋了一整套架構
- 規則寫了，它還是照樣違反
- 對話快滿了或要收工，怕脈絡斷掉
- 把 agent 當搜尋引擎用，感覺不出它厲害
- 它一直停下來等我按確認，或權限開太大亂改
- 它用了不存在的函式或參數
- 裝了一堆 skill 與規則，反而變笨
- 做到一半就停，或用省略號交差
- 改了規則或 skill，不知道有沒有變好

### 拆任務、排順序、複盤（`situations/project.md`）
- 功能太大，不知道怎麼切
- agent 產出太快，審不完
- 方案看起來很順，想先找出會翻車的地方
- 一直重複提醒同一件事，想讓它下次自己會
- 一堆待辦不知道先做哪個

## 官方功能對照

「該用哪個功能、什麼時候用、三家各叫什麼」在 `features.md`。使用者問「/clear 是做什麼的」「什麼時候該開新對話」「有沒有省 token 的設定」這類問題時讀它。
